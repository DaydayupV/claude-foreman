下列耗时和内存表为首轮实现的历史实测；返工后的行为、额外成本及验证见文末，未重新测量性能。

明细缓存现在保存解析器状态、事件、行数、用量去重键和费用，不保存 `tail.records`。没有新行且窗口及任务关联上下文相同时，复用解析结果与费用；有新行只过滤、解析新增行。缓存键按解析器的任务时间顺序生成，避免车道活跃度排序变化导致无效重建；窗口边界用字符串编码，区分 Infinity、-Infinity 和 NaN。

同一 assistant message id 后来的行会移除旧 usage 事件；末行没有 usage 时也撤销旧用量。用量和费用按剩余事件原序重新累计，保留 null、零值、未知价格、浮点加法顺序及事件位置。工具、后台任务和已关联任务的状态跨追加保留。路径标签仍使用全窗最终 cwd，cwd 变化时只更新路径事件，之前已返回的快照保持不变。

from/end、任务集合或影响关联的任务字段变化时从源文件重建；截短通过新的 tail.version 清空解析状态。重建只接纳本轮尾读已确认的行，并发追加的行留给下一轮，避免重复计入。窗口重建遇到临时读错误时，下轮重试。首次读取的本批原始行仍会短暂存在；只有未完成行的字节片段继续保留，以支持 UTF-8 和半行追加。三文件 LRU 上限保持不变。

`read()` 中全部任务名、候选名和祖先名的查找改用 Set；原数组仍负责排序，选择顺序保持原语义。

`universe.readRuns(now)` 在 settleRun 判断后，非 running 且有效结束时间距 now 严格超过 300000 ms、缺少结果的任务也会 settle，包括进程不存在后判为 interrupted 的任务。已有 result 或终态 host 的立即 settle 规则保留。普通轮询跳过 settled 项的文件检查及消息重建；任务目录名称集合变化或距上次全量检查达到 30000 ms 时，重新检查缺 result 的 settled 项，拾取迟到结果。已读到结果的 settled 项继续复用缓存。

`feed.read()` 距最近一次成功列目录达到 10000 ms 时强制 dirty 并重列，即便 fs.watch 正常工作、客户端一直连接也生效；无 watcher 时仍每次扫描。服务每秒轮询，漏掉的新任务在接下来的十秒内被发现。兜底直接位于 read，无需依赖 server 的十五秒空闲检查，因此没有改动 server.mjs。

回放函数 `universe.replay()`、`feed.buildReplay()` 和网页均未修改。共用解析器的批量入口保持原输出，回放 SHA256 金标准通过。

返工补充：运行中的组和单任务范围使用稳定的开放窗口缓存键，实际过滤和 hostEnd 仍沿用当前 now 推导出的原有截止时间。另保存最早尚未进入窗口的有效行时间；该时间到达、窗口收缩或结束时间确定后才重建。返工前捕获的七个阶段输出 SHA256、versions、revisions 和 hostEnd 均保持一致；前三次未变日志轮询的累计全文打开次数由 [1,2,3] 降为 [1,1,1]，组和单任务两种范围都覆盖。

readLines 保存 dev、ino、birthtimeMs；身份变化或可见截短时重置尾读版本，并在读取新行前通知宇宙层清空累计状态。ino 为 0 时按原来的大小判断退回。预检实测原地截短再长回不会改变 inode 或 birthtime，因此还记下已读部分开头和末尾各 4 KB：身份可用、文件 size/mtime/ctime 发生变化时，核对这两段是否还在原处，不同则重置，相同才增量处理追加字节。日志未变时不读取正文，原始行仍不常驻；新行只做增量 JSON 解析。

这项校验只读两段 4 KB，代价和文件大小无关。返工时曾用整段已读前缀的 SHA256 做校验，追加时要重读并哈希全部已读字节（一百多 MB 的对话每秒都在追加），集成时改成了两段抽样：另外，上次读完整、这次大小没长但修改时间变了的，直接整份重读（只追加的日志不会这样），所以同样大小的原地改写不管改在哪里都能发现；只有"文件变大、同时中间被改、开头和末尾 4 KB 都没变"这种情况识别不了，日志文件实际不会这样改。新文件身份不同则直接重读，不先扫描旧内容。
