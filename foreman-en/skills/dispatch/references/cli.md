# Script reference: commands, check, models and result fields

SKILL.md keeps only the decision process and the common commands. Read the matching section here, not the whole file, when you need a command's full options, are troubleshooting the environment, helping the user pick models, or looking up what a field in the result JSON means. The fields of the live view, `status` and the start line (status words, times, counts, model labels, usage, tags and hints) are in English in both plugins; what models and Claude write is shown as written. Every subcommand prints its own usage with `--help` (or `-h`; `assets <action> --help` prints that action's options), and either one with no subcommand prints the overall usage. The exit code is 0 and no file is written. A `--help` or `-h` given as an option's value (`--title -h`, for example) doesn't count.

## Commands
The only entry point is `scripts/cli.mjs` in the dispatch skill's folder (written `<script path>` below).

```bash
node "<script path>" run    --cwd "<project dir>" --brief "<brief.md>" --title "<short title>" --level <simple|normal|complex> [--agent <agent>] [--add-dir "<dir>"] [--track "<path>"] [--group <name> --scope "<path>"] [--timeout minutes]
node "<script path>" resume --run <run_id|last> --brief "<rework.md>" --level <simple|normal|complex> --reason <rework|answer|recover> [--track "<path>"] [--file "<path>[:start-end]"]   (no --level when resuming an image task; no --reason when resuming a discussion)
node "<script path>" plan   --cwd "<project dir>" --module <discuss|run|review> --cell <simple|normal|complex> --group <name> --seat "<agent>[=<role>]" [--seat …] [--why "<reasons>"] [--host-role "<role>"] [--count-why "<reason>"] (these two for discussion and review plans only) [--target diff|files|claims|visual --file "<path>[:<start>-<end>]" --uncommitted | --base <branch> | --commit <sha> (review plans only)]
node "<script path>" submit --plan <plan_id> --report "<report.json>" [--model <Claude Code's current model>] [--author]
node "<script path>" run|discuss|review --plan <plan_id> --seat <n> --brief "<brief.md>" --title "<short title>" [--effort <effort>] [--file "<path>[:<start>-<end>]"] [--scope "<path>"]   (agent, level, directory and group come from the plan; for a review, so do the target and material)
node "<script path>" plan   --cwd "<project dir>" --module image --cell <generate|draw> --route <1|2|3|4> --group <group> --seat "<agent>" [--seat …] [--why "<reason>"]
node "<script path>" image  --plan <plan_id> --seat <n> --brief "<brief.md>" --title "<short title>" --scope "<output dir>" [--scope …] [--track "<path>"] [--effort <effort>]
node "<script path>" status [--run <run_id|last> | --group <name> | --plan <plan_id>] [--limit n]
node "<script path>" watch  [--run <run_id|last> | --group <name>]
node "<script path>" board  [--replay <conversation id|run_id|group|all> [--speed <N>] [--maxgap <sec>]] (without --replay: the live board)
node "<script path>" board --stop (shuts down the live board server)
node "<script path>" config [--cwd "<project dir>"] [--format json|md]
node "<script path>" check  [--agent <agent>] [--format json|md] [--reprobe]
node "<script path>" models [--format json|md]
node "<script path>" agy-guard <install|uninstall|status> (agy's global guard; see check below)
node "<script path>" tiers  [--model <name>]... [--all] [--cwd "<project dir>"] [--format json|md] (model tiers, overall scores, strengths and weaknesses; rules in references/model-tiers.md)
node "<script path>" await-busy (--group <name> | --run <run_id>) [--after minutes]
node "<script path>" cancel --run <run_id>
node "<script path>" judge  --run <run_id> [--accept "<ids>"] [--partial "<ids>"] [--reject "<ids>"] [--same "<id>=<run_id>:<id>,…"] [--clear "<ids>"]
node "<script path>" stats  [--module discuss|run|review|image] [--since <days>] [--by effort,cell,scene]
node "<script path>" assets <template|cut|check|diff|layers|patch|trace|capture|playback> … (options for each command in references/assets-cli.md)
```

- For a single-seat hands-on handoff, `--agent <agent>` can only pick one of the cell's candidates. Without it: a cell with one candidate uses it, a cell with one required agent uses that one, and otherwise `--agent` is required. If the cell has another required agent, a single-seat handoff is refused and you need a plan. When the cell is `"claude code"`, `--agent` can still name an agent (the result is marked `outside_cell`); for a discussion or review on such a cell, put the agent the user named in the plan's `--seat`, and the plan is marked `outside_cell` with the built-in default effort. Which tasks an agent can do is in `capabilities.modes`: `api` agents can take part in `discuss` and `review` (text only, never a `visual` review); `opencode cli` and `pi cli` agents can do `review` and `discuss`, and `run` too when the config gives them `run_access`; `agy cli` agents can only do `review` and `discuss`. Old IDs from before the upgrade (such as `codex`) still work, and the script says what the new ID is.
- When the user asks for a specific effort ("run it with ultra"), give `--level` as usual and add `--effort <effort>`: it only changes the effort, and the agent is still picked from the cell.
- When the user asks for a specific model, add `--model <model>`. It can only switch to a model from the same provider: `codex cli` and `api` agents can switch to any model, while for `opencode cli` and `pi cli` the new model must have the same `provider/` prefix as the old one; the result is marked `model_overridden` when the model changed.
- Who gets the work, the model, reasoning effort, sandbox, approval policy and time limits come from the config file; anything not configured for Codex comes from its own `~/.codex/config.toml`. If you're unsure of the current settings, run `config --cwd "<project dir>"` first.
- The checks and output of `plan`, `submit` and `status --plan` are in their own section below; `judge` and `stats` are in the last section.

## check
Tests whether the environment works: Node.js, Git, and every agent in the config, with results under `agents.<ID>`. opencode, pi and API agents each get one tiny real request (a few dozen tokens), and agy gets one small request that reads a file (about 10–20K input tokens from agy's plan quota, plus a sandbox probe the first time), which costs a little on pay-as-you-go keys; use `--agent` to check just one.
- **Codex CLI**: whether it starts and is signed in; then the efforts the cells configure are checked against Codex's own model list (no requests sent), with results under `efforts`; and for each sandbox mode the task types actually use, `codex sandbox` runs an echo inside the sandbox (no model call), with results under `sandbox`; `danger-full-access` doesn't use a sandbox and isn't tested. When the sandbox won't start on Windows, it also tries the unelevated sandbox and says so in `fix` when that works.
- **API**: whether the key is set, plus a tiny request to confirm it connects.
- **opencode**: whether it starts, whether `opencode models` lists the model, plus a tiny request to confirm it works; each reasoning effort (variant) the cells configure for it is first checked against opencode's model list, failing at once if it isn't there, and every other one gets one more tiny request; results are under `variants`.
- **pi**: whether it starts, whether its model list has the model, plus a tiny request to confirm it works; efforts are only checked against the model list (pi doesn't report an unsupported level; it quietly switches to the nearest one, so a request can't reveal it), with results under `efforts`.
- **agy**: whether it starts and `agy models` lists the model; the guard self-check (project and global config, the guard files, the hooks agy actually loads); the sandbox probe (run once per agy version, system and disk, then cached); then one request asking the model to read a temporary file with `read_file` and reply with its contents, confirming the guard allowed it and left a decision record; finally the quota, with a note when any quota bucket is below 10%. It leaves a session in agy's history. When the guard is missing, its files don't match or other hooks exist, `fix` says what to do.

`agy-guard install` installs the guard under `~/.gemini/config/` (backing up `hooks.json` first), `uninstall` removes the entry and files, and `status` is read-only and reports whether it's installed, whether the files match, and the agy runs in progress. Install and uninstall take a cross-process lock and refuse while agy runs are active. **Only run `install` after the user agrees** (the `/foreman-en:setup` popup, or an explicit request): it changes agy's global config in the user's home folder.

The overall `ok` only counts Node.js and the agents the cells use (image cells included); a failure in an unused agent is reported but doesn't block anything. For each failed item, `fix` in the result says what to do; pass it on to the user.

`summary` in the result is the overview of the whole config: `modules` gives each cell's candidates with their model, effort, whether they're required (`required`) and whether they passed (with a `problem` if not), `agents` gives the cells each agent is used in (`used_at` is written `modules.<module>.<cell>[index]`), and `warnings` lists things worth noting (unused agents, keys written in plain text in the config, shell access for hands-on work or drawing, Codex agents with no read-only sandbox for discussions or reviews (`readonly_audited`), stale old IDs, and leftovers from older versions that can be removed: the unused `dispatch.max_seats` (`obsolete_max_seats`), an `api_key_env` that has no effect because `api_key` is also set (`obsolete_key_env`), old config backups (`old_backups`), and the `levels` note left for old plugin versions (`legacy_levels_note`, to keep)). `config` also outputs `summary`, without check results.

`config`, `check` and `models` all take `--format md`: instead of JSON they print laid-out Markdown tables, which `/foreman-en:setup` pastes for the user as they are. `check` prints two parts, "Environment" and "Configuration"; `config` prints only "Configuration", without the check column; `models` prints tables of every model. The default is `--format json`. To show the user the configuration, use the output of `check --format md` (or `config --format md`) instead of building tables yourself.

## plan, submit, image and status --plan
To hand hands-on work to several seats, create a dispatch plan first; discussions, reviews and image tasks always need a plan, however many seats:

```bash
node "<script path>" plan --cwd "<project dir>" --module <discuss|run|review> --cell <simple|normal|complex> --group <name> --seat "<agent>[=<role>]" [--seat …] [--why "<reasons>"] [--host-role "<role>"] [--count-why "<reason>"] [--target <diff|files|claims|visual>] [--file "<path>"]… [--uncommitted | --base <branch> | --commit <sha>]
node "<script path>" submit --plan <plan_id> --report "<report.json>" [--model <model>] [--author]
node "<script path>" plan --cwd "<project dir>" --module image --cell <generate|draw> --route <1|2|3|4> --group <name> --seat "<agent>" [--seat …] [--why "<reasons>"]
```

- Every check runs before any request goes out: the cell is open (not `"claude code"` or `null`); every seat is one of the cell's candidates (old IDs are mapped to new ones); every required agent has a seat; hands-on and draw seats can do hands-on work; seats of a `visual` review can read images (`reads_images`); generate seats can make images.
- A review plan also checks the gap seat (role `gap` or `补漏`): a plan has at most one, and a discussion plan can't have one. The gap seat's base model has to differ from every other seat's, or the plan is refused; when the gap seat starts, it also has to differ from the model the Claude Code seat reported with `submit --model`. When the level's `gap` is on and there is still a suitable candidate (outside the main seats, with a base model different from every main seat's) but the plan lists no gap seat, when `gap` is off but the plan lists one, or when in scene mode the gap seat isn't the next candidate in order, the plan needs `--count-why` or it is refused. Different spellings of one model count as the same model: a `provider/` prefix, Bedrock's `…anthropic.` prefix, a Claude version written with a dot (`claude-fable-5.1` is `claude-fable-5-1`), and the official aliases listed under `aliases` in the plugin's price table `prices.json` (for example `deepseek-v4.1-flash` is `deepseek-flash`). `stats` uses the same rules to put one model on one row.
- Discussion and review plans also check the number of external seats (a review doesn't count a gap seat, i.e. one whose role is `gap` or `补漏`; in other modules that role name counts as usual): it must equal `min(the level's seats, the number of different usable candidates in the cell)` (for a level written per scene, the value for the `--scene` scene), where a `visual` review only counts candidates that can read images. Otherwise the plan needs `--count-why "<reason>"` or it is refused; `--count-why` on any other module is refused too. The plan records `seat_target` (the number above; `null` for an `outside_cell` plan, which skips this check) and `count_why` (`null` when not given).
- Scenes: `--scene <scene>` and `--scene-why "<reason>"` are for discussions and reviews only, and go together. They are required when the level writes `seats` or `gap` per scene; the scene name must be in `scenes.names` of the `config` output; they are refused when no scenes are defined; and while `scenes.problems` isn't empty, no discussion or review plan can be created. In scene mode the plan also checks that the external seats were taken in candidate order: the required agents plus the candidates counted down the list (skipping those that can't do the task and those with the same base model as an earlier one), deduplicated by agent, must match the plan's main seats, or the plan needs `--count-why`. The plan records `scene`, `scene_why` and `gap` (the gap switch in effect for this plan). These checks only run when the plan is created, not when a seat starts, so existing plans still start after the config changes.
- Discussion and review plans come with the Claude Code seat: `host` at the top of the plan (`seat` 0, `role` from `--host-role`, otherwise `null`); external seats stay in `seats`, numbered from 1. `--host-role` on another module is refused. `discuss` and `review` without `--plan` stop with an error. A discussion or review cell set to `"claude code"` in the user config can still get a plan (for when the user names an agent): the plan is marked `outside_cell: true` with an empty `required`, each seat's agent must support the module, and the effort is the built-in default. Old plans without `host` still count only `seats` and need no report before starting.
- Image plans also check:
  - `--route` is required, must be 1–4, and must use that cell: ① bitmap uses generate only; ② bitmap + vector mix uses generate and draw; ③ pure vector with a reference image first uses generate (reference image only) and draw; ④ pure vector / code uses draw only. A plan covers one cell, so a route ④ draw plan ignores required agents in the generate cell. Other modules refuse `--route`.
  - Generate seats take no roles (`--seat agent=role` is refused): Claude writes the picture requirements into the brief.
  - The confirmation record: the plugin's hook (`hooks/record-answers.mjs`, on PreToolUse and PostToolUse, AskUserQuestion only) records pop-ups whose question or header contains "Image route" (or the Chinese "图像路线", case doesn't matter) per Claude session in `answers/<session id>.jsonl` in the config folder: an `asked` line when the pop-up opens and an `answered` line once the user answers (with `answers`, keyed by the question text; the value is the chosen option's label, or the user's own text when they picked Other). Other pop-ups aren't recorded, and files older than 30 days are removed. `plan --module image` reads the file for the `CLAUDE_CODE_SESSION_ID` environment variable and looks at the latest route pop-up: with no session id, no route pop-up, no answer to the latest one (cancelled or still open), an answer that isn't one of the options starting with ①–④, or a route different from `--route`, no plan is created. When one pop-up asked about the routes of several deliverables, any of them matching `--route` counts. One answer can back several plans.
- A review plan fixes what to review and the material when it's created: `--target`, `--file` and the range options only go on a review plan (other modules refuse them), they're checked as for a single-seat `review`, and a `diff` with no changes gets no plan. The plan's `review` records those options and the material's fingerprint (`null` for a `diff` in a folder without git). In a `diff` review plan, a seat other than Codex whose run-time budget (200,000 characters for opencode, pi and agy, 300,000 for API) can't hold the material without generated files makes the plan refused right away, naming those seats and their sizes and suggesting Codex seats or a narrower range; the seat isn't left to fail at start with a plan that never gets its result.
- For a `diff` review, opencode, pi and API receive patches computed by the script with git. Generated files whose Git `linguist-generated` attribute is `set` or `true` stay in the file list but have no patch. When the list and patches exceed 200,000 characters, opencode and pi replace patches that do not fit with line ranges only for `uncommitted` and `base`, whose new side is the working tree, and read those lines inside the project directory. Only hunks with a positive new-side line count give ranges; files with none get a deletion, rename or permission-change notice instead (new files are read in full; deleted files are marked as unavailable). A `commit` review cannot read historical versions by line range and is refused if it still exceeds the limit after generated files are left out. A file list with location notices that exceeds the limit is also refused. API cannot read files and refuses a prompt that still exceeds 300,000 characters after generated files are left out. Use `--commit` to review one commit at a time, or switch to Codex (it reads the changes itself and has no such limit). The material fingerprint still includes generated files, so changing one invalidates the original material.
- Once it passes, the plan is written to `plans/<plan_id>.json` in the run directory and printed: `plan_id`, `module`, `cell`, `group`, `seats` (each seat's number `seat`, `agent`, `role`, `model`, `effort`, `required`), `required`, `why`, `review` (review plans only; a `diff` review without range options is recorded as `uncommitted: true`), `route` and `route_confirmation` (image plans only: the route number and the answer it rests on: `tool_use_id`, question, answer and when it was answered), plus `file` (the plan file) and `commands` (the start command for each seat; replace the placeholders for the brief, title, scope and output dir with the real ones).
- Start each seat with `run / discuss / review --plan <plan_id> --seat <n> --brief …`: the agent, effort, directory, level and group all come from the plan, and `--agent` isn't allowed; add `--effort` to change the effort or `--model` to change the model (same rules as a single-seat handoff); hands-on seats still need `--scope`; review seats leave out `--target`, `--file` and the range options, and the script works out the material again from the plan and refuses to start when the fingerprint no longer matches (the material changed after the plan was created), so recreate the plan for the current material. At start the whole plan is checked again against the current config, so a changed config (including a changed model or effort for that seat), or changed required agents means it's refused, and you create a new plan. Each seat can be started only once; rework uses `resume`, which keeps the plan and seat, and a seat from a plan can't change level on resume. A review seat that returned no valid result (failed, stalled, cancelled, or `verdict` is `incomplete`) can be started again with the same command; it's refused while a round of that seat is still running or once the seat has returned a valid result. Hands-on, discussion and image seats normally can't be started again; only when no round of the seat returned a valid result and the latest round has neither a session id nor a `messages.json` in its record folder (its first round failed before it got a session, so it can't be resumed) can it be started again with the same command. Rounds of a seat are ordered by run id (run ids are generated under the start lock and always increase).
- Seats of an image plan start with `image --plan <plan_id> --seat <n> --brief … --title … --scope <output dir>`: no `--level` (the plan sets the cell), at least one `--scope` (needed for the write-scope check within the group; output dirs inside the working directory that `.gitignore` hides are added to `--track` automatically so change tracking sees them, while the working directory itself and dirs that aren't ignored are left out), and the other options (`--track`, `--effort`, `--model`, `--add-dir`, `--timeout`, `--stall`) work as for `run`. It runs as hands-on work: snapshots, the hands-on report, change attribution, `generated_images` and `image_calls` are the same as for `run`; the record has `mode` `run` and `kind` `exec`, plus `module: "image"`, `cell`, `step` (the cell) and `route`, with `level` set to `null`. Resume with `resume --run <run_id> --brief … --reason <rework|answer|recover>` and no `--level`: it picks from the image cell, never checks the run levels, and doesn't check the confirmation record again.
- `submit` records the Claude Code seat's report:
  - The report is JSON, checked against `discuss.schema.json` for a discussion plan and `review.schema.json` for a review plan; if it doesn't match, the problems are listed. Plans that aren't discussion or review plans, or have no `host` (old plans), are refused.
  - It checks and registers under the start lock that external seats use too. A discussion takes one report per round: the round is the highest round already submitted plus one, can't exceed `dispatch.discuss_max_rounds`, and `parent` points to the previous report. If any record under the lock can't be read (it might be a report), it refuses rather than miscount the round. A review takes one report only, and the material fingerprint is recomputed from the plan and must match it.
  - The run folder gets `meta.json` (`mode: "submit"`, `participant: "host"`, `agent: "claude-code"`, `agent_type: "host"`, `model` (the `--model` value, otherwise `null`), `model_source` (`"self_reported"` when `--model` was given), `plan`, `seat: 0`, `role`, `round`, `parent`, `author`, `report_sha256`, `submitted_at`, plus `review_fingerprint` for a review; `status` is `done` from the start and there is no process ID), the report snapshot `report.json`, and `result.json` (`report` holds the report content, `usage` is `null`).
  - It prints JSON: `run_id`, `plan`, `seat`, `round`, `submitted_at`, `report_sha256`, `run_dir`, and `commands` (the external seats' start commands in round 1, their resume commands in later discussion rounds). Later rounds also carry `resumable` (every seat that can be resumed: `seat`, `agent`, `model`, `run_id`) and `note`: the script doesn't know model tiers, so breadth seats aren't resumed; Claude runs only the seats going on to the next round.
  - Admission: for a plan with `host`, starting or resuming an external seat requires the Claude Code seat's report for that round: one for a review, and for a discussion a report whose round is at least the round being started (round 2 needs a round 2 report; extra reports for an earlier round don't count). Otherwise it's refused with a hint to `submit` first. Restarting a failed review seat isn't affected (the report is already there). A deleted plan file doesn't skip the check: if the plan already has a report, it's treated as having a Claude Code seat; a plan file that exists but can't be parsed stops the start.
  - A report record never counts as running, takes no parallel slot and isn't listed among unfinished runs at session start; `resume` and `cancel` refuse it; `judge` works as usual, and `--same` can link it with external seats of the same plan.
- A plan takes no parallel slot; each seat counts against its agent's limit as usual when it starts.
- `status --plan <plan_id>` prints JSON: for each seat its `run_id` (the latest round), `runs` (all its rounds), `status` (`not_started` if never started) and `ok` (only once it has ended: it finished normally and returned a valid result; for a review that means a structured report whose `verdict` isn't `incomplete`, and without a report only the text of Codex's built-in review counts); `state` is `complete` (every seat that must return a valid result did: every seat of a hands-on or image plan, the required seats of a discussion or review plan; a discussion or review plan with no required seats needs every seat ended and at least one valid), `incomplete` (one of the seats that must return a valid result ended without one, for example failed, cancelled, out of quota or waiting for an answer) or `pending`; `missing` lists the seats that must return a valid result and don't have one yet, with their status, and `missing_required` only the required ones among them; `running` lists the seats still running (`seat`, `agent`): an optional seat can still be running when `state` is `complete`; which seats are required follows the plan's `required` list; each seat's `stale` is the `stale` of its latest review result (`null` when it isn't a review or has no result yet), and image plans add `route`. Plans with `host` also have `host`: `seat` (0), `role`, `status` (`submitted` or `missing`), `rounds` (each report's `round`, `run_id`, `submitted_at`, `report_sha256`, `model`, `author`) and `before_external_start` (whether the first report came before the earliest external run of the plan started; `null` while there's none). Until the Claude Code seat submits, `state` can't be `complete` and `missing` has an entry with `seat: 0`, `agent: "claude-code"`, `status: "not_submitted"`; `missing_required` lists only required external agents. Discussion and review plans also carry the plan's `seat_target`, `count_why`, `scene`, `scene_why` and `gap` (`null` for older plans without them). For seats whose material changed during the review, the live view and `status --group` write "material changed during the review (stale)" on that seat and on the plan's line; the plan still counts as complete. The plan line in the live view and `status --group` is worked out from this plan's runs in the group across all Claude sessions, so resuming from another session doesn't make other seats look unstarted.
- A gap seat is a seat whose role is `gap` (the Chinese plugin writes `补漏`). When its agent isn't required and the plan has required seats, `state` only looks at the required ones, so the plan can show `complete` while the gap seat hasn't finished. `gap_unfinished` therefore lists the gap seats with no valid result yet (not started, still running, failed, or with an invalid result), each with `seat`, `agent` and `status`, and is an empty array when there are none; the live view and `status --group` add "gap seat not finished: …" to the plan's line, naming each seat and where it stands (not started, running, no valid result, or a status word such as failed).

## models
Lists the model lists built into the local Codex, opencode, pi and agy (with the efforts each model supports; for agy the levels are split off the model ID suffix) and the model names each API agent's endpoint lists (without efforts), and checks whether the configured models are listed, suggesting the closest names when not. Read-only; it sends no model requests. Use it when the user asks which models are available, or wants to change a model or effort.

## Result fields
The results of `run`, `image`, `resume`, `discuss` and `review` are printed to stdout as JSON. The main fields:
- `report`: the agent's structured report: a hands-on report, a discussion report or a review report. A review report has `verdict` (`issues_found` / `no_issues` / `incomplete`), `findings` (each with `id`, `location`, `issue`, `trigger`, `severity`, `evidence`, `suggestion`; empty is a valid result), `coverage` (`checked`, `not_checked`) and `unverified`. Codex's built-in review (a `diff` with neither a brief nor `--file`) has no structured report: `report` is `null` and the findings are English text in `last_message`. When a report isn't valid JSON (for opencode, pi and API, still invalid after one repair), there's only `last_message` too.
- `last_message`: when there's no `report`, the text of the agent's last reply, cut to the first 8000 characters; the full text is in `run_dir/last-message.txt`.
- `changes`: changes inside the working directory, as tracked by the script. Each file has `by`: `agent` means a tool event shows the agent doing the work changed it (records from before the rename say `codex`); `reported` means only its report claims the change, which is common for files written by commands or scripts; `unknown` means it isn't known who did. A path the report gives as a directory (ending in `/`, or a directory on disk) counts as a prefix: every tracked file under it is `reported`, and `notes` only says it's outside tracking when no tracked file is under that prefix (the working directory itself doesn't count). Files marked `group_run` are inside the write scope of another hands-on run in the same working directory (any group or session), outside this run's own scope and `--track`, and that run's running time overlaps this one (from its start to its end, up to now while it's still running, and up to its last activity for an old record with no end time; a run that ended before this one started doesn't claim anything); a file that both scopes cover, or that several other runs cover, stays `unknown`; the rounds of one seat (resumes, or restarts of the same plan seat) count as one run, and the file goes to its latest round. `group_total` counts them; the live view's final line and the group panels don't count them as of unknown origin and write "from other runs in the group" instead. Snapshots compare the files' raw bytes: line endings aren't converted by the project's `.gitattributes`, and clean filters, ident and the like don't run, so when the project changes those settings, files whose bytes didn't change aren't reported as changed, and line endings in `diff.patch` match the files on disk.
- `changes.outside_cwd`: hands-on tasks record writes outside the working directory found in tool events or the report as `{ path: <absolute path>, by: "agent" | "reported", in_scope: <inside --scope / --track> }`. Paths are deduplicated with tool events taking priority; up to 30 are listed and `outside_cwd_total` gives the full count. Both fields are absent when there are none. Detection works without snapshots, including `--no-snapshot` and snapshot failures. Entries with `in_scope: false` produce a warning; those inside the write scope only produce a note explaining that the changes are absent from snapshots and patches. Neither is described as reported but untracked. Discussions and reviews still use `readonly_violation`.
- `notes`: informational messages, such as changes of unknown origin, files the agent reported but tracking didn't see, Codex's sandbox being unable to start commands, or opencode recovering from an error mid-run (see below).
- When opencode hits an error mid-run (such as the stream timeout "Timed out waiting for response data"), retries on its own and its last step finishes normally (`step_finish` with reason `stop`), or its event stream ends with a completed reply (opencode sometimes exits right after the reply without a `step_finish`), the run isn't counted as failed: the error text goes to `notes`, not `errors`, even though opencode exits with a non-zero code. The reply may then be split into pieces, with the last one not a valid report; in that case the usual repair request goes out once, asking it to send the whole report again. The pieces are never stitched together. An error with no normal finish afterwards still makes the run `failed`; if the run ends up failed, cancelled or timed out anyway (for example the repair request fails), the recovered errors go to `errors` as well and there's no such note.
- `warnings`: problems to look at, such as the material changing while a review ran; a plain hands-on task that generated images ("not through the image module"); a route ③ or ④ draw task that made bitmaps (on route ③, bitmaps only come from the generate step as a reference); SVG files written or changed by a route ③ or ④ draw task that embed bitmaps (`<image>`, including a namespace-prefixed `<svg:image>`; only that seat's own changes are checked; with no snapshot, or a `--scope` outside the working directory, the untracked parts are checked only through the SVG files in its tool events and report, which `notes` points out); `meta.json` that couldn't be written at the end of the run (another program, usually backup or sync software, held it; the write is given up after about 15 seconds), in which case it keeps the last content written and the result is in `result.json` as usual (this warning is only in the printed result, not in `result.json`).
- `questions` and `needs_decision`: things the agent needs answered; see "When an agent needs an answer" in `references/recovery.md`.
- `session_id`, `run_dir`: `run_dir/diff.patch` is this run's patch (files with `by` set to `agent`, `reported` or `unknown`), and `run_dir/diff.all.patch` holds every change seen between the two snapshots (also the files marked `group_run`); `shortstat` and `patch_bytes` in `changes` describe the first, `all_shortstat` and `all_patch_bytes` the second. A review's patch is in `run_dir/review.patch`. `changes.unstable_files` lists files that kept being rewritten while a snapshot was taken and so are missing from the start or end snapshot (`path`, `phase`): their changes can't be compared and are in neither patch. When there are more than 20, only the first 20 are listed, `changes.unstable_total` gives the total and `changes.unstable_list` points to the full list (`unstable-files.json` in the record folder). Taking a snapshot gets 60 seconds in all; files still unconfirmed by then are listed in `unstable_files` too, and `changes.incomplete` is true. A read-only audited run needs a complete snapshot (any unstable file, or running out of the 60 seconds, makes it incomplete): it doesn't start when the start snapshot is incomplete, and counts as failed when the end snapshot is.
- Token use: `usage` is this call's input, cached and output tokens (when `usage_scope` is `session_total`, it's the whole session's total); `last_request` is the size of the latest request and the model's context window; `rate_limit` is how much of the Codex quota is used; `quota_resets_at` is when the quota is expected to reset. Codex usage is read from its own session log, which gets a running total as soon as each request finishes, so a cancel during a command still counts it. A cancelled or timed-out run only has usage for the requests that finished before it was stopped (providers report nothing for the request in flight); if none finished, `usage` is `null` and `notes` says why. For a timed-out run, the first entry in `errors` says which time limit (in minutes) was hit. `errors` says whether it was the `cancel` command, the user pressing x in the live view, or a termination signal to the dispatcher. How `cancel` handles each kind of run is under "cancel and status" below. When an API agent's provider never reported usage, `usage` and `usage_scope` are both `null`, `notes` says so, and `stats` counts the round in `missing_runs`. `output_tokens_per_s` is the round's average output speed: this round's output tokens (reasoning included) divided by this round's `duration_s`, which includes taking snapshots, running commands, waiting for the provider and report repair requests, but not the time spent queueing locally for a slot. It is measured differently from the web board's generation estimate (which estimates generation time only), so the two can't be compared directly. The terminal usage line shows it as `run avg N tok/s`; cancelled, timed-out and stalled rounds only count requests that finished, so their speed is low and is marked `(partial usage)`. It is given only when `usage_scope` is `this_run`, there is output and the duration is not 0, and is `null` otherwise.
- `agent`, `model_shown`, `effort`: which agent this call went to, and the model and effort actually used. `model_overridden` is `true` when `--model` changed the model this time; `outside_cell` is `true` when the cell is `"claude code"` and the call named an agent with `--agent`.
- `module`, `cell`, `plan`, `seat`, `role`: the module and cell this call belongs to; for a call started from a plan, also the plan's `plan_id`, the seat number and the role (`null` when not started from a plan). Image tasks add `step` (generate or draw) and `route` (1–4), with `level` set to `null`. Discussion and review results from API, opencode and pi agents have no change tracking (`changes.available` is `false`); for API agents `files` lists the files that were attached, and every agent's result has `cost_usd` (US dollars at the model's official API price, `null` when the model isn't in the price table) and `cost_source` (`api_price` or `unknown`), which `status` and the live view show after the token use; the cost opencode and pi report themselves is kept in `reported_cost_usd` for the record.
- `isolation`, `run_access`: for hands-on work by opencode or pi, these say there's no OS sandbox (`tools`) and which access level was used.
- `generated_images`: the original files of the images that appeared during this round (Codex keeps them in its image folder). Every image-capable adapter provides this and `image_calls` through the same interface.
- `viewed_images`: the images Codex opened with view_image in this round, as `[{ path, ok }]` (read from the Codex session log; "unknown" when the path was a variable that can't be read; `ok` is `true` when the image was read, `false` when the call didn't get an image, `null` when no outcome was found or when one piece of code opened several images and the number read doesn't match, so it can't tell which one failed). Mentions of view_image inside a patch (apply_patch) don't count. An "Opened image …" line shows up in the live view's timeline. `commands_executed` doesn't include these.
- `image_calls`: the arguments and outcome of each image call in this round, read from the Codex session log: `transparent_background`, `referenced_image_paths` (null when not passed; "unknown" when passed through a variable that can't be read, or when several calls can't be matched to their images), `num_last_images_to_include` (can also be "unknown"), `status` ("not_run" for a call written in the code that never ran), `saved_path`, `failure`. When the brief mentions `referenced_image_paths` but none of the calls in this round passed reference images, `warnings` says so.
- `review_target`, `review_scope`: what the review covered (`diff`, `files`, `claims`, `visual`), with its range, file count and material fingerprint; `review_scope.kind` is `uncommitted` / `base` / `commit` for a `diff` and the target itself otherwise. A `diff` in a folder without git has no `review_scope`. `native_review` is `true` when Codex's built-in review ran. For a `diff` with `--file`, the fingerprint includes the attachments' content too; untracked files over 1 MiB are sent without their content, but their content hash goes into the fingerprint.
- `stale`: the material fingerprint is worked out again when a review ends; `true` when it differs from the start (the review may not cover the latest version, and `warnings` says so too), `false` when it matches, `null` when there's no fingerprint.
- `readonly`: how a discussion or review stayed read-only: `tools` (opencode, pi, API), `sandbox` (Codex in a read-only sandbox) or `audited` (Codex with no read-only sandbox, held only by the rules and a snapshot comparison afterwards).
- `readonly_violation`: writes with evidence behind them during a discussion or review, as `[{ path, by }]`; `status` is then `failed`, `errors` explains it, and nothing was reverted automatically. With a usable snapshot, files it says it changed that the snapshot doesn't cover (ignored by `.gitignore`, in a folder the snapshot excludes, or outside the working directory) count too, with `by` `reported`; files the snapshot covers and saw no change in don't. When what it says it changed is a folder, the folder counts as outside the snapshot if it holds (or held when the run started) ignored files that no `--track` covers; if the command that works out the snapshot's coverage fails, everything it says it changed counts.

## cancel and status
- What counts as running: `meta.json` says `running`, the dispatcher's pid is still alive, and that process started no later than the run's `started_at` (the dispatcher writes `started_at` itself, so a program that reuses the pid always started later). An old run killed before it wrote a result, whose pid has since gone to another program, counts as interrupted: it no longer takes a concurrency slot or shows up in `stats`' `running_skipped`. `status`, `stats`, the live view, the concurrency check and the session-start reminder all decide it this way: they pick out the few runs that say `running` with a live pid and look up all their start times at once (one PowerShell call on Windows, with no window), and skip the lookup when there are none; the answers are cached within a process, so the live view doesn't look them up every second. When dispatching, the lookup happens before taking the start lock; only a run that existed before the lock but couldn't be checked then (rare) is looked up inside it, and runs registered after the lock was taken count as running. Inside the lock, unreadable `meta.json` files are re-read for about 1 second in total; any still unreadable stop the start, and the error lists them: once you've confirmed that run is long finished and only its record is broken, move its record folder away to dispatch again; the session-start reminder gives the lookup at most 3 seconds. When a start time can't be read, the run still counts as running.
- `result.json` is written only when a run ends. Once it exists, `status`, the live view, `cancel` and the session-start reminder all go by its status, not by the dispatcher's pid: a run that couldn't write `meta.json` at the end leaves `meta.json` at `running` on disk, and that pid may later be given to another program. When `cancel` meets such a run and the dispatcher has exited, it writes the final status back to `meta.json`; read-only commands don't write.
- `cancel --run <run_id>` prints JSON; `ok` says whether it got something done:
  - A running run: it first checks that the pid still belongs to the original dispatcher (by comparing the process's start time, looked up with PowerShell on Windows, without opening a window), then leaves a cancel marker and waits up to 30 seconds for the run to stop and write its result (`ok: true`, `status` is what the run wrote). If it doesn't stop, it checks again and kills it only when it's still the same process, writes a minimal result (with whatever usage the session log has) and prints `forced: true`.
  - If the start time can't be read, it doesn't kill anything and leaves the records alone: `ok: false`, `status: "running"`, and `error` says how to handle it by hand.
  - If the pid now belongs to another program (it started after the run did), or the dispatcher exited on its own during the wait without leaving a result, it ends no process and only marks the run handled (`status: "interrupted"`, `dismissed: true`), with `note` saying which case it was.
  - A run that ended without finishing normally (`interrupted`, `stalled`, `timeout`, `quota_exhausted`, `needs_input`) is marked handled (`dismissed: true`), and the session-start reminder stops listing it.
  - Any other run that has ended (`done`, `failed`, `cancelled` and so on): `ok: false`, with `note` saying there's nothing to cancel.
  - If `meta.json` can't be written: marking handled returns `ok: false` with `error`; a kill still returns `ok: true`, with `warning`.
- A run that ended normally (`done`) but returned no valid result (no proper report for hands-on, image and discussion runs; for a review, a `verdict` of `incomplete`, or no report without being Codex's built-in review) shows as ✗ "no valid result" in `status` and the live view and counts as failed in the group summary, matching `ok` in `status --plan`. When a seat of a plan was started again, its earlier rounds count as resumed in the `status --group` summary, and the live view only shows the latest round.
- The `status` list leaves out runs whose `meta.json` can't be read (another program holds it without read sharing, or its content is incomplete), and a last line says how many. When `status --run <run_id>` can't read `meta.json` but can read `result.json`, it prints `result.json` with a note at the end of `warnings`; when neither can be read, it fails with an error.
- For a run marked handled that has no end time, the duration runs to the newest file in the run directory other than `meta.json` and `verdict.json` (marking it handled rewrites `meta.json`, and `judge` often writes `verdict.json` long afterwards).

## judge and stats
After a review or discussion ends and Claude has checked it, record what happened to each point with `judge`; `stats` sums these records and the usage up into local results for each model.

```bash
node "<script path>" judge --run <run_id> [--accept "F1,F3"] [--partial "F4"] [--reject "F2"] [--same "F1=<run_id>:F3,…"] [--clear "F5,…"]
node "<script path>" stats [--module discuss|run|review|image] [--since <days>] [--group <name>] [--plan <plan_id>] [--by effort,cell,scene]
```

**judge**
- Only reviews and discussions (run and image tasks are refused), and only once the run has ended. Ids start with a letter and use only letters, digits and `. _ -`, 32 characters at most; separate several with commas.
- Ids: a review with a structured report uses the report's `id`s (F1, F2…), and an id that isn't in the report is refused; a discussion uses the numbers Claude gave the points in the decision record (P1, P2…), and a review without a structured report uses the numbers Claude gave in its report; those two kinds aren't checked. Each id gets one verdict: `accept` (holds), `partial` (partly holds) or `reject` (doesn't hold; for a review, a false positive).
- The same issue: when several seats found the same issue, add `--same "<id here>=<the other seat's run_id>:<its id>"` on one of them. Links have no direction and chain together, so writing one side is enough. They can only point to a peer: another seat of the same plan, or without a plan, a run in the same group, from the same Claude session and the same module. Another round of the same seat (or the same resume chain) isn't a peer: a participant's point repeated in later rounds keeps its original id. The id before the `=` needs a verdict (given in the same call or recorded before); when the other side is a review with a structured report, its id must be in that report. If the other run is still running, the link is refused (its ids aren't settled yet); link to it after it ends and has been checked.
- Removing wrong entries: `--clear "<ids>"` removes those entries along with their `--same` links. The ids must already be recorded, and one id can't be in both `--clear` and a verdict or `--same` in the same call. Links to them from other runs stay as they are; `stats` ignores links it can't find. When nothing is left, `verdict.json` is deleted and the run counts as not judged again (a review round whose structured report is `no_issues` goes back to counting as judged with 0 points automatically).
- The result goes to `verdict.json` in the run's record folder (written to a temporary file, then renamed). Only one `judge` writes a run at a time: a second one waits up to 5 seconds, then fails without writing. The lock is the highest-numbered file among `verdict.json.lock.<n>`, and releasing it leaves a `.done` marker; when the process holding it is gone, the next `judge` takes over, and no lock someone still holds is ever deleted. A process that can't be probed for lack of permission (one running in an administrator terminal, for example) still counts as alive. When a lock file's content can't be read, or the holder's process ID now belongs to another program, the wait runs out with an error, and deleting that lock file as the message says fixes it: the script doesn't guess a process's identity from timestamps, so a clock jump can't take a lock from a live holder. The start lock (`.start.lock.<n>` in the run directory) works the same way. Once taken, both locks also hold the `verdict.json.lock` / `.start.lock` that older plugin versions use, following the old protocol, so old and new versions running at once exclude each other just as old versions do among themselves. Running it again only changes the ids it names: a new verdict replaces the old one, an id named in `--same` gets its links replaced with the ones given this time, and every other entry stays as it was.
- It prints the content of `verdict.json` (`run_id`, `module`, `plan`, `seat`, `group`, `claude_session`, `agent`, `model`, `updated_at`, and `items`: each one's `verdict`, `same_as` and `at`), plus `file` (the file's path; `null` when `--clear` removed everything and the file was deleted), `unjudged` (ids in the report with no verdict yet; `null` without a structured report), and, when `--clear` was given, `cleared` (the ids removed this time).

**stats**
- Changes no records; reads every run in the records folder. Runs whose `meta.json` can't be read, and resumes whose parent can't be read so they can't be placed in a seat, go in `totals.unreadable`; running rounds go in `totals.running_skipped`; seats that failed without ever calling the agent (`not_started` true in the result, for example a change snapshot that failed before the start) go in `totals.not_started` (absent when there are none); none of these are counted, and a seat whose root run is still running isn't counted at all.
- Seats: a run with no parent, together with all its resumes (later rounds of a discussion, rework, answers to questions), counts as one seat. `--since <days>` filters by that root run's start time, `--module` by the root run's module (older records with no `module` are worked out from `kind`), and `--group` and `--plan` by the root run's group and plan (to look at one batch while several conversations run at once; `totals.running_skipped` then counts that batch only, while `totals.unreadable` can't be told apart by group and still counts everything).
- One row per (base model, module). The base model is the model name without everything up to the last `/` (the provider prefix), in lower case, so one model reached through opencode, pi and api lands in one row. Seats and rework count toward the root run's model; each round's time, usage, cost and verdicts count toward that round's own model (rework at a higher level may have switched models). The Claude Code seat's reports get a row of their own (`participant: "host"`, `self_judged: true`, with the self-reported model when there is one), counted as one seat per plan + seat 0, never merged with external model rows, and with no usage, cost or `missing_runs`; for "only it found" it still takes part in the overlap check, which makes the external seats' numbers more honest. `notes` says its verdicts are self-judged, aren't directly comparable with external seats, and shouldn't be used to change model tiers.
- `--by effort,cell,scene` (any of them is fine, and the option can be given more than once) also splits rows by reasoning effort (`effort`), level (`cell`, or `level` for older records) and/or scene (`scene`, taken from the plan the run belongs to; `null` when there is no plan or the plan has no scene), and those rows get fields of the same names; without it rows stay per (base model, module) with none of these fields. As with the model, seats, rework and seat duration go by the root run's effort and level, and each round's usage, cost and verdicts by that round's own (rework at a higher level may have changed them). To compare before and after a tier change (such as reviews going from xhigh to high), combine it with `--since` or `--module review`.
- Fields of each row:
  - `seats`, `runs`: the number of seats and of rounds.
  - `findings_reported`: how many findings the review reports listed in total (reviews only); `judged_runs`, `judged`: how many rounds and points have verdicts (a review round whose structured report is `no_issues` with nothing listed needs no `judge` and counts as judged with 0 points); `accepted`, `partial`, `rejected`: how many held, partly held, and didn't; `accepted_weighted`: the points that held plus half the points that partly held.
  - `unique`: how many confirmed issues (partly holding included) only this model found. Points with the same id across one seat's rounds are one point, and the peers' points are then joined into issues by `--same`, and an issue reported only by seats of this one base model adds one here. It's only counted when at least two different base models in one plan (without a plan: one group and Claude session) have verdicts; `unique_basis_runs` is how many rounds that covers, and with none `unique` is `null`.
  - `rework` (run and image only, `null` for other modules): `seats`, `reworked`, `rate`. A seat counts as reworked when a resume asked it to fix or complete the original task's work (`resume --reason rework`, including resumes that also answered questions), at most once per seat; `answer` resumes (only answering questions, adding material or giving a decision) and `recover` resumes (continuing from where it stopped) don't count. Older resumes with no declared reason are inferred by the old rule: rework only when the previous round had handed in its report normally (a partial report counts) and wasn't handing back questions. Several records from restarting the same seat of a plan count as one seat.
  - `rework_basis` (run and image rows only): `inferred_seats` is the number of seats with at least one resume that declared no reason and was inferred by the old rule; `inferred_reworked` the number of seats counted as reworked only by inference, with no declared `rework`. Every resume of the other `seats - inferred_seats` seats has a declared reason.
  - `duration_s`: `total` (all rounds added up), `median_per_seat` (the median of seat totals, over seats with no running round where every round has a duration), `p90_per_seat` (the 90th percentile of the same seats, by nearest rank: the ⌈0.9 × seats⌉-th smallest) and `missing_runs` (rounds with no duration).
  - `tokens`: `input`, `cached_input`, `output`, the number of rounds with usage `runs` and without it `missing_runs`. A resume that recorded the session's running total (`usage_scope` is `session_total`) only counts what that round added. A Codex round with no recorded usage that is the last round of its session (no resume after it, running ones included) is read again from Codex's own session log; if that fails it counts in `missing_runs`, never as 0.
  - `output_tokens_per_s`: average output speed over the rounds that have both usage and a duration (their output tokens divided by their total time), measured like the field of the same name in results (time on commands and waiting included, so it can't be compared directly with the web board's generation estimate); `null` when there are no such rounds.
  - `speed_basis`: the rounds behind the speed, `runs`, `seconds` and `output_tokens`, and the rounds left out in `excluded`: `no_usage` (no usage recorded), `no_duration` (no duration), `mixed_session_total` (the previous round had no usage, so this round's session-total difference also holds that round's output). Cancelled and timed-out rounds aren't left out; their speed is low.
  - `cost_usd`: `total`, `runs`, `missing_runs`. Always computed from each model's official API price (the plugin's price table, `scripts/prices.json`), so it may differ from what is actually charged. Models missing from the table have no cost and count in `missing_runs` (the Claude Code seat doesn't).
- Plan time, `plans`: reads the plan files in `plans/` in the records folder (`*.json` only; the `*.decision.md` files there are decision records) and sums up, per (module, level), each plan's wall-clock time from creating it (`created_at`) to the end of its last external seat (`ended_at` in each round's `meta.json`, resumes included), which includes queueing, waiting for a slot, the Claude Code report and resumes. `--module`, `--since`, `--group` and `--plan` filter plans as well (`--since` by when the plan was created). Only plans where every seat has started, none is running and every round has an end time are counted; the rest go in `unfinished`, and a seat that ended in failure still counts as ended. Plans with no external seats don't appear. Fields: `counted`, `unfinished`, `unreadable` (plan files that can't be read or have no `created_at`), and `rows`: each with `module`, `cell`, `plans` (plans counted in the time), `unfinished` and `wall_clock_s` (`median`, `p90`, counted like `p90_per_seat`, to one decimal place, `null` with no plans). The number of plans created at a level is `plans + unfinished`.
- It prints JSON: `runs_dir`, `module`, `since_days`, `group`, `plan`, `by` (the dimensions given to `--by`, `[]` without it), `generated_at`, `totals` (`runs`, `seats`, `judged_runs`, `running_skipped`, `unreadable`, `unreadable_verdicts`), `rows` (discussion, review, run, image in that order, within a module the rows with more seats first, and with `--by` then by level simple, normal, complex and by effort), `plans` and `notes` (how the figures above are counted).
- How to use it: the preference files can point to these figures to change a model's tier (such as "in local results deepseek-v4.1-flash finds many issues no one else does in reviews; treat it as strong for reviews"), and then they win; the script never ranks models and never changes the config or tiers. When few rounds have verdicts (see `judged_runs` and `unique_basis_runs`), take the figures as a rough guide only.
