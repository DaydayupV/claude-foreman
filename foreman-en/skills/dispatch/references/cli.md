# Script reference: check, models and result fields

SKILL.md keeps only the decision process and the common commands. Read this when troubleshooting the environment, helping the user pick models, or looking up what a field in the result JSON means. Every subcommand prints its own usage with `--help` (or `-h`; `assets <action> --help` prints that action's options), and either one with no subcommand prints the overall usage. The exit code is 0 and no file is written. A `--help` or `-h` given as an option's value (`--title -h`, for example) doesn't count.

## check
Tests whether the environment works: Node.js, Git, and every agent in the config, with results under `agents.<ID>`.
- **Codex CLI**: whether it starts and is signed in; then the efforts the cells configure are checked against Codex's own model list (no requests sent), with results under `efforts`; and for each sandbox mode the task types actually use, `codex sandbox` runs an echo inside the sandbox (no model call), with results under `sandbox`; `danger-full-access` doesn't use a sandbox and isn't tested. When the sandbox won't start on Windows, it also tries the unelevated sandbox and says so in `fix` when that works.
- **API**: whether the key is set, plus a tiny request to confirm it connects.
- **opencode**: whether it starts, whether `opencode models` lists the model, plus a tiny request to confirm it works; each reasoning effort (variant) the cells configure for it is first checked against opencode's model list, failing at once if it isn't there, and every other one gets one more tiny request; results are under `variants`.
- **pi**: whether it starts, whether its model list has the model, plus a tiny request to confirm it works; efforts are only checked against the model list (pi doesn't report an unsupported level; it quietly switches to the nearest one, so a request can't reveal it), with results under `efforts`.

The overall `ok` only counts Node.js and the agents the cells use (image cells included); a failure in an unused agent is reported but doesn't block anything. For each failed item, `fix` in the result says what to do; pass it on to the user.

`summary` in the result is the overview of the whole config: `modules` gives each cell's candidates with their model, effort, whether they're required (`required`) and whether they passed (with a `problem` if not), `agents` gives the cells each agent is used in (`used_at` is written `modules.<module>.<cell>[index]`), and `warnings` lists things worth noting (unused agents, keys written in plain text in the config, shell access for hands-on work or drawing, Codex agents with no read-only sandbox for discussions or reviews (`readonly_audited`), stale old IDs). After `check`, tell the user with a table of cells and the warnings, as in the last step of `/foreman-en:setup`. `config` also outputs `summary`, without check results.

## plan, image and status --plan
To hand one task to several seats, create a dispatch plan first; image tasks always need a plan, however many seats:

```bash
node "<script path>" plan --cwd "<project dir>" --module <discuss|run|review> --cell <simple|normal|complex> --group <name> --seat "<agent>[=<role>]" [--seat …] [--why "<reasons>"] [--target <diff|files|claims|visual>] [--file "<path>"]… [--uncommitted | --base <branch> | --commit <sha>]
node "<script path>" plan --cwd "<project dir>" --module image --cell <generate|draw> --route <1|2|3|4> --group <name> --seat "<agent>" [--seat …] [--why "<reasons>"]
```

- Every check runs before any request goes out: the cell is open (not `"claude code"` or `null`); every seat is one of the cell's candidates (old IDs are mapped to new ones); every required agent has a seat; hands-on and draw seats can do hands-on work; seats of a `visual` review can read images (`reads_images`); generate seats can make images; the seats don't exceed `dispatch.max_seats`.
- Image plans also check:
  - `--route` is required, must be 1–4, and must use that cell: ① bitmap uses generate only; ② bitmap + vector mix uses generate and draw; ③ pure vector with a reference image first uses generate (reference image only) and draw; ④ pure vector / code uses draw only. A plan covers one cell, so a route ④ draw plan ignores required agents in the generate cell. Other modules refuse `--route`.
  - Generate seats take no roles (`--seat agent=role` is refused): Claude writes the picture requirements into the brief.
  - The confirmation record: the plugin's hook (`hooks/record-answers.mjs`, on PreToolUse and PostToolUse, AskUserQuestion only) records pop-ups whose question or header contains "Image route" (or the Chinese "图像路线", case doesn't matter) per Claude session in `answers/<session id>.jsonl` in the config folder: an `asked` line when the pop-up opens and an `answered` line once the user answers (with `answers`, keyed by the question text; the value is the chosen option's label, or the user's own text when they picked Other). Other pop-ups aren't recorded, and files older than 30 days are removed. `plan --module image` reads the file for the `CLAUDE_CODE_SESSION_ID` environment variable and looks at the latest route pop-up: with no session id, no route pop-up, no answer to the latest one (cancelled or still open), an answer that isn't one of the options starting with ①–④, or a route different from `--route`, no plan is created. When one pop-up asked about the routes of several deliverables, any of them matching `--route` counts. One answer can back several plans.
- A review plan fixes what to review and the material when it's created: `--target`, `--file` and the range options only go on a review plan (other modules refuse them), they're checked as for a single-seat `review`, and a `diff` with no changes gets no plan. The plan's `review` records those options and the material's fingerprint (`null` for a `diff` in a folder without git).
- Once it passes, the plan is written to `plans/<plan_id>.json` in the run directory and printed: `plan_id`, `module`, `cell`, `group`, `seats` (each seat's number `seat`, `agent`, `role`, `model`, `effort`, `required`), `required`, `why`, `review` (review plans only; a `diff` review without range options is recorded as `uncommitted: true`), `route` and `route_confirmation` (image plans only: the route number and the answer it rests on: `tool_use_id`, question, answer and when it was answered), plus `file` (the plan file) and `commands` (the start command for each seat; replace the placeholders for the brief, title, scope and output dir with the real ones).
- Start each seat with `run / discuss / review --plan <plan_id> --seat <n> --brief …`: the agent, effort, directory, level and group all come from the plan, and `--agent` isn't allowed; add `--effort` to change the effort or `--model` to change the model (same rules as a single-seat handoff); hands-on seats still need `--scope`; review seats leave out `--target`, `--file` and the range options, and the script works out the material again from the plan and refuses to start when the fingerprint no longer matches (the material changed after the plan was created), so recreate the plan for the current material. At start the whole plan is checked again against the current config, so a changed config (including a changed model or effort for that seat), changed required agents or a cell the project closed means it's refused, and you create a new plan. Each seat can be started only once; rework uses `resume`, which keeps the plan and seat, and a seat from a plan can't change level on resume.
- Seats of an image plan start with `image --plan <plan_id> --seat <n> --brief … --title … --scope <output dir>`: no `--level` (the plan sets the cell), at least one `--scope` (needed for the write-scope check within the group; output dirs inside the working directory that `.gitignore` hides are added to `--track` automatically so change tracking sees them, while the working directory itself and dirs that aren't ignored are left out), and the other options (`--track`, `--effort`, `--model`, `--add-dir`, `--timeout`, `--stall`) work as for `run`. It runs as hands-on work: snapshots, the hands-on report, change attribution, `generated_images` and `image_calls` are the same as for `run`; the record has `mode` `run` and `kind` `exec`, plus `module: "image"`, `cell`, `step` (the cell) and `route`, with `level` set to `null`. Resume with `resume --run <run_id> --brief …` and no `--level`: it picks from the image cell, never checks the run levels, and doesn't check the confirmation record again.
- A plan takes no parallel slot; each seat counts against its agent's limit as usual when it starts.
- `status --plan <plan_id>` prints JSON: for each seat its `run_id` (the latest round), `runs` (all its rounds), `status` (`not_started` if never started) and `ok` (only once it has ended: it finished normally and returned a valid result; for a review that means a structured report whose `verdict` isn't `incomplete`, and without a report only the text of Codex's built-in review counts); `state` is `complete` (every required seat returned a valid result; with no required seats, every seat has ended and at least one is valid), `incomplete` (a required seat ended without a valid result, for example failed, cancelled, out of quota or waiting for an answer) or `pending`; `missing_required` lists the required seats with no valid result yet and their status; each seat's `stale` is the `stale` of its latest review result (`null` when it isn't a review or has no result yet), and image plans add `route`. For seats whose material changed during the review, the live view and `status --group` write "material changed during the review (stale)" on that seat and on the plan's line; the plan still counts as complete.

## models
Lists the model lists built into the local Codex, opencode and pi (with the efforts each model supports) and the model names each API agent's endpoint lists (without efforts), and checks whether the configured models are listed, suggesting the closest names when not. Read-only; it sends no model requests. Use it when the user asks which models are available, or wants to change a model or effort.

## Result fields
The results of `run`, `image`, `resume`, `discuss` and `review` are printed to stdout as JSON. The main fields:
- `report`: the agent's structured report: a hands-on report, a discussion report or a review report. A review report has `verdict` (`issues_found` / `no_issues` / `incomplete`), `findings` (each with `id`, `location`, `issue`, `trigger`, `severity`, `evidence`, `suggestion`; empty is a valid result), `coverage` (`checked`, `not_checked`) and `unverified`. Codex's built-in review (a `diff` with neither a brief nor `--file`) has no structured report: `report` is `null` and the findings are English text in `last_message`. When a report isn't valid JSON (for opencode, pi and API, still invalid after one repair), there's only `last_message` too.
- `last_message`: when there's no `report`, the text of the agent's last reply, cut to the first 8000 characters; the full text is in `run_dir/last-message.txt`.
- `changes`: changes inside the working directory, as tracked by the script. Each file has `by`: `agent` means a tool event shows the agent doing the work changed it (records from before the rename say `codex`); `reported` means only its report claims the change, which is common for files written by commands or scripts; `unknown` means it isn't known who did. A path the report gives as a directory (ending in `/`, or a directory on disk) counts as a prefix: every tracked file under it is `reported`, and `notes` only says it's outside tracking when no tracked file is under that prefix (the working directory itself doesn't count). Files marked `group_run` are inside the write scope of another run in the same group whose running time overlaps this one (from its start to its end, up to now while it's still running, and up to its last activity for an old record with no end time; a run that ended before this one started doesn't claim anything), and `group_total` counts them; the live view's final line and the group panels don't count them as of unknown origin and write "from other runs in the group" instead.
- `notes`: informational messages, such as changes of unknown origin, files the agent reported but tracking didn't see, or Codex's sandbox being unable to start commands.
- `warnings`: problems to look at, such as the material changing while a review ran; a plain hands-on task that generated images ("not through the image module"); a route ④ draw task that made bitmaps; SVG files written or changed by a route ③ or ④ draw task that embed bitmaps (`<image>`; only that seat's own changes are checked; with no snapshot, or a `--scope` outside the working directory, the untracked parts are checked only through the SVG files in its tool events and report, which `notes` points out); `meta.json` that couldn't be written at the end of the run (another program, usually backup or sync software, held it; the write is given up after about 15 seconds), in which case it keeps the last content written and the result is in `result.json` as usual (this warning is only in the printed result, not in `result.json`).
- `questions` and `needs_decision`: things the agent needs answered; see "When an agent needs an answer" in SKILL.md.
- `session_id`, `run_dir`: the full diff is in `run_dir/diff.patch`, and a review's patch in `run_dir/review.patch`.
- Token use: `usage` is this call's input, cached and output tokens (when `usage_scope` is `session_total`, it's the whole session's total); `last_request` is the size of the latest request and the model's context window; `rate_limit` is how much of the Codex quota is used; `quota_resets_at` is when the quota is expected to reset. Codex usage is read from its own session log, which gets a running total as soon as each request finishes, so a cancel during a command still counts it. A cancelled run only has usage for the requests that finished before the cancel (providers report nothing for the request in flight); if none finished, `usage` is `null` and `notes` says why. `errors` says whether it was the `cancel` command, the user pressing x in the live view, or a termination signal to the dispatcher. How `cancel` handles each kind of run is under "cancel and status" below.
- `agent`, `model_shown`, `effort`: which agent this call went to, and the model and effort actually used. `model_overridden` is `true` when `--model` changed the model this time; `outside_cell` is `true` when the cell is `"claude code"` and the call named an agent with `--agent`.
- `module`, `cell`, `plan`, `seat`, `role`: the module and cell this call belongs to; for a call started from a plan, also the plan's `plan_id`, the seat number and the role (`null` when not started from a plan). Image tasks add `step` (generate or draw) and `route` (1–4), with `level` set to `null`. Discussion and review results from API, opencode and pi agents have no change tracking (`changes.available` is `false`); for API agents `files` lists the files that were attached, and opencode and pi agents add `cost_usd` (the cost in US dollars at the vendor's prices), which `status` and the live view show after the token use.
- `isolation`, `run_access`: for hands-on work by opencode or pi, these say there's no OS sandbox (`tools`) and which access level was used.
- `generated_images`: the original files of the images that appeared during this round (Codex keeps them in its image folder). Every image-capable adapter provides this and `image_calls` through the same interface.
- `viewed_images`: the images Codex opened with view_image in this round, as `[{ path, ok }]` (read from the Codex session log; "unknown" when the path was a variable that can't be read; `ok` is `true` when the image was read, `false` when the call didn't get an image, `null` when no outcome was found or when one piece of code opened several images and the number read doesn't match, so it can't tell which one failed). Mentions of view_image inside a patch (apply_patch) don't count. An "Opened image …" line shows up in the live view's timeline. `commands_executed` doesn't include these.
- `image_calls`: the arguments and outcome of each image call in this round, read from the Codex session log: `transparent_background`, `referenced_image_paths` (null when not passed; "unknown" when passed through a variable that can't be read, or when several calls can't be matched to their images), `num_last_images_to_include` (can also be "unknown"), `status` ("not_run" for a call written in the code that never ran), `saved_path`, `failure`. When the brief mentions `referenced_image_paths` but none of the calls in this round passed reference images, `warnings` says so.
- `review_target`, `review_scope`: what the review covered (`diff`, `files`, `claims`, `visual`), with its range, file count and material fingerprint; `review_scope.kind` is `uncommitted` / `base` / `commit` for a `diff` and the target itself otherwise. A `diff` in a folder without git has no `review_scope`. `native_review` is `true` when Codex's built-in review ran.
- `stale`: the material fingerprint is worked out again when a review ends; `true` when it differs from the start (the review may not cover the latest version, and `warnings` says so too), `false` when it matches, `null` when there's no fingerprint.
- `readonly`: how a discussion or review stayed read-only: `tools` (opencode, pi, API), `sandbox` (Codex in a read-only sandbox) or `audited` (Codex with no read-only sandbox, held only by the rules and a snapshot comparison afterwards).
- `readonly_violation`: writes with evidence behind them during a discussion or review, as `[{ path, by }]`; `status` is then `failed`, `errors` explains it, and nothing was reverted automatically.

## cancel and status
- `result.json` is written only when a run ends. Once it exists, `status`, the live view, `cancel` and the session-start reminder all go by its status, not by the dispatcher's pid: a run that couldn't write `meta.json` at the end leaves `meta.json` at `running` on disk, and that pid may later be given to another program. When `cancel` meets such a run and the dispatcher has exited, it writes the final status back to `meta.json`; read-only commands don't write.
- `cancel --run <run_id>` prints JSON; `ok` says whether it got something done:
  - A running run: it first checks that the pid still belongs to the original dispatcher (by comparing the process's start time, looked up with PowerShell on Windows, without opening a window), then leaves a cancel marker and waits up to 30 seconds for the run to stop and write its result (`ok: true`, `status` is what the run wrote). If it doesn't stop, it checks again and kills it only when it's still the same process, writes a minimal result (with whatever usage the session log has) and prints `forced: true`.
  - If the start time can't be read, it doesn't kill anything and leaves the records alone: `ok: false`, `status: "running"`, and `error` says how to handle it by hand.
  - If the pid now belongs to another program (it started after the run did), or the dispatcher exited on its own during the wait without leaving a result, it ends no process and only marks the run handled (`status: "interrupted"`, `dismissed: true`), with `note` saying which case it was.
  - A run that ended without finishing normally (`interrupted`, `stalled`, `timeout`, `quota_exhausted`, `needs_input`) is marked handled (`dismissed: true`), and the session-start reminder stops listing it.
  - Any other run that has ended (`done`, `failed`, `cancelled` and so on): `ok: false`, with `note` saying there's nothing to cancel.
  - If `meta.json` can't be written: marking handled returns `ok: false` with `error`; a kill still returns `ok: true`, with `warning`.
- The `status` list leaves out runs whose `meta.json` can't be read (another program holds it without read sharing, or its content is incomplete), and a last line says how many. When `status --run <run_id>` can't read `meta.json` but can read `result.json`, it prints `result.json` with a note at the end of `warnings`; when neither can be read, it fails with an error.
- For a run marked handled that has no end time, the duration runs to the newest file in the run directory other than `meta.json` (marking it handled rewrites `meta.json`).
