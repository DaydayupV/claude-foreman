# Discussion (/foreman-en:discuss)

Read this when a discussion is levelled 1 or higher, or the user asks to discuss something with other models, before writing the topic and picking participants; the rules for picking seats and for the Claude Code seat are in `references/seats.md`. The levels are under "Levels" in SKILL.md.

**Claude Code makes the final decision**: every participant's views, the Claude Code seat's own report included, are input only. They're accepted or rejected on the strength of the arguments, not because someone insists, and not by majority vote. To write the topic brief, you may first read code and data and run read-only statistics to get the facts straight. When `resolved_modules.discuss.<level>` is `"claude code"`, that level uses no outside model; Claude thinks it through itself.

## Choosing the mode
Once the level is set and outside models are involved, choose between the normal mode and role mode:
- Level 1 always uses the normal mode. Levels 2 and 3 use the normal mode by default: the same brief for everyone, each giving an independent proposal (see "The process" below).
- At levels 2 and 3, suggest **role mode** when any of these holds: the topic has several goals pulling against each other (such as security and convenience, implementation cost and user experience, compatibility and a rewrite); the user asks for it; the preference files say to use it for this kind of topic. Don't use role mode for checking facts, bugs whose root cause is unknown, or questions with an objective answer.
- In role mode each participant gets a role card, roles are assigned by tool access (a hard gate), strengths and model tier (only a guide), and one model per role comes first; a participant below a role's suggested tier takes it as a breadth seat that only joins round 1. Before starting, **always show a pop-up for the user to confirm the assignment**, even when `dispatch.auto` is `true`. Read `references/roles.md` first for how to do it (role cards, preset roles, assignment rules, the pop-up, round 2, the decision record); model tiers are in `references/model-tiers.md`.
- If the user picks "Use a normal discussion instead" in the pop-up, go ahead in the normal mode.

## The process (round limit set by `dispatch.discuss_max_rounds`, 2 by default)
1. **Round 1, independent proposals**: the topic brief only gives the background, the problem to solve, constraints, known facts, relevant code locations, and the specific questions to report. **Don't include Claude Code's own leaning**, so the participants don't just go along with it. Pick the participants from `resolved_modules.discuss.<level>` per `references/seats.md` and create a plan with `plan --module discuss --cell <level> --group <name> --seat <agent>[=<role>] … [--host-role "<role>"]` (when the level writes `seats` per scene, also add `--scene <scene> --scene-why "<which line of the preferences it follows>"`; see "Scene mode" in step 3 of seats.md; the group name is an ASCII code name plus the date, such as `config-rework-1013`, used only on command lines; a different name for each discussion within a conversation, kept for its later rounds; a single external participant still needs a plan). Next, write your own report per "The Claude Code seat" in seats.md and `submit` it, adding to the topic any facts that writing it showed were missing. Then start one `discuss --plan <plan_id> --seat <n>` per external seat: the same brief (in role mode, the same shared body with each participant's own role card at the end), all started in the background in the same message.
2. **Round 2, critique each other**: only when the proposals (the Claude Code seat's included) really disagree, or a participant's conclusions include something Claude Code hasn't checked that would change the outcome; if they broadly agree, go straight to deciding (role mode has its own trigger, see `references/roles.md`). First write this round's challenges to each proposal as your report and `submit` it (the script requires it before the other seats are resumed). Then label the proposals anonymously as "Proposal A / Proposal B / …", the Claude Code seat's among them, and continue each external participant with `resume --run <that participant's round 1 run_id>` (except breadth seats; again in parallel, in the same message), asking it to find the weakest points of the other proposals and compare them with its own. Send only summaries and the points of disagreement, not the full reports.
3. **Round 3 and later (optional)**: only when a key disagreement is unresolved, another round could really change the conclusion, and the round limit isn't reached. If the script refuses the resume, rule on the results you have.
4. **Claude Code decides**: accept or reject each participant's points (its own report's included) with reasons, and settle the final plan. Judge by evidence, constraints and reversibility; a conclusion all participants share can still be wrong.
5. **Record the verdicts**: after deciding, record what happened to each of each participant's points in that round's record with `judge`, the Claude Code seat's on its report record (the run_id `submit` printed), using the point numbers from the decision record: `judge --run <run_id> --accept "P1,P3" --partial "P4" --reject "P2"`. A point a participant repeats in a later round keeps its number and is recorded only on the round where it first came up; don't record that number again on the later round (`--same` can't link two rounds of the same seat either; the script refuses it). When two participants made the same point, add `--same "P1=<the other one's run_id>:P5"` on one of them. `stats` uses these records to sum up how each model actually did.

- **Level 1 (a one-off question) keeps it short**: Claude Code still submits a short report first (its own judgment, confidence and basis) before starting the external seat; no round 2, and no decision record or `judge`, for the external seats either. Check the participants' reports, then tell the user the conclusion and its basis plainly, and say why if it differs from your own first judgment. Attachments, the live view and busy handling work as usual.
- Later rounds keep round 1's level (`resume` needs `--level` too; discussion resumes take no `--reason`), and a resume keeps the original plan and seat. Each participant has its own run_id, and the round limit applies to each participant separately. Each participant takes one of its own agent's parallel slots; when that agent's slots are full, its dispatch command queues on its own and starts once a slot frees up. Don't skip that participant or switch its agent.
- If one participant fails (for example `quota_exhausted` from a low balance, an API error, a missing key, or `cancelled` because it was stopped), the others carry on: tell the user which one failed and why, and continue with the other participants' results. If the one that failed is required, the discussion counts as incomplete; handle it per seats.md. Don't change the config just to get every participant in. An API participant with `key_set` `false` in `agents_status` fails outright: before the discussion, remind the user to either fill in `api_key` for that agent in `~/.claude/foreman/config.json` (takes effect immediately), or set the environment variable named by `api_key_env` and restart Claude Code.
- Discussion is read-only: Codex can read code and run read-only commands to back up its points, but can't change files. The result's `readonly` says how read-only was enforced this time; a write with evidence behind it makes that participant fail, handled as in "Read-only" in `references/review.md`. API, opencode, pi and agy agents can't change files.
- With API participants, start the queue check in the background after starting them (see "When an API participant is busy" in `references/recovery.md`).

## Reporting to the user: the decision record
Don't paste the raw exchange. Write it up plainly as follows (not needed for level 1 questions):
- **Topic**: one sentence
- **Options**: the Claude Code seat's and each participant's, each with its core idea and trade-offs
- **Each participant's main points**: listed per participant, called by model name (such as gpt-6-astra, deepseek-v4-pro), with the Claude Code seat as "Claude Code" (self-judged); numbered across the whole record (P1, P2…), each marked ✅ accepted / ❌ rejected / ⚠ partly accepted, with the reason; `judge` uses these numbers
- **Final plan**: and what changed from the Claude Code seat's original proposal. The two cases under "Deciding" in "The Claude Code seat" in seats.md are called out here
- **To confirm**: things the user needs to decide or that need checking first
- The plan's plan_id, and each participant's run_id, model, effort and token use (the self-reported model for the Claude Code seat, whose usage isn't measured), plus where the decision record file is, so the user can look at the raw record
- Role mode adds the assignment table, the role cards and any missing viewpoints, and names each point "model [role]"; see `references/roles.md`

## After the discussion
- If the user only asked for advice: stop at the decision record and let them decide whether to go ahead.
- If the user wants the thing done: when the final plan has nothing the user needs to decide, carry on with the final plan into hands-on work (deciding who does it per "Who does what" in SKILL.md first); anything involving business trade-offs, preferences, risk tolerance, wider scope, extra spending or irreversible steps goes to the user first. Don't decide those for them.
- If the discussion was about the result of changes already made: when the conclusion is a different way to reach the same goal, `resume --reason rework` the original agent for a rework (it counts as one, see "Rework" in `references/acceptance.md`); when the direction or goal changed, or it calls for something the original brief didn't cover or explicitly left out, treat it as a new task and level it again (see the last point of "Rework" in `references/acceptance.md`); when the result is already good enough, level the review.
