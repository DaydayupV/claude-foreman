# Checking the result and rework

Read this when the result of a hands-on or image task comes back, before checking it. Hands-on work Claude did itself is checked the same way. Image tasks have their own checks and regeneration rules in `references/image.md`; when a result didn't finish normally (stalled, out of quota, waiting for an answer and so on), see `references/recovery.md` first.

## Checking the result (every time)
1. Look at `status` and `report.status` first. If it isn't `completed`, read `open_issues` first. A run that ended normally but returned no proper report shows "no valid result" in status and the live view; treat it as failed.
2. Read `run_dir/diff.patch` (this run's patch; files other runs changed at the same time are in `diff.all.patch`) and compare it with `changes.files`:
   - Any files changed outside the scope? Does `report.files_changed` match the actual changes?
   - For files with `by` set to `reported`, check the diff to confirm they are changes this task should have made. Files with `by` set to `unknown` may have been changed by Claude itself or another session, or written by the agent with a command it didn't report. Find out who changed them first; **don't just revert them**. Those marked with `group_run` are inside the write scope of another hands-on run that ran at the same time in the same directory and outside this run's own scope, so most likely that run changed them; review them with it (they are only in `diff.all.patch`). Files in `changes.unstable_files` kept being rewritten while a snapshot was taken, so their changes can't be compared: don't take them as unchanged, look at them yourself (when there are many, only the first 20 are listed there; `changes.unstable_list` points to the full list).
   - Is the logic right? Any defensive overkill, needless abstraction, redundant tests?
   - **Was it overdone?** The change is clearly bigger than the "Size" section expected (say, more than twice), or it adds options, settings, abstraction layers, compatibility branches or tests nobody asked for. Trim small things yourself; if there's a lot, use `resume --reason rework` for a rework and list what to remove in the rework brief.
   - Do names, comments and messages follow the brief, and are they plain and readable: are names plain and consistent; can comments and messages be understood at a glance; any wordiness, stiff phrasing or over-commenting? Fix small problems yourself without a rework. If there are many text problems, put the corrected wording in the rework brief.
   - Only changes inside the working directory are tracked; if the task involved paths outside it, check those separately.
3. **Actually run it**: run the full tests, build or script from "Final check" once on the final version. Don't rely on the agent saying it passed. The targeted tests the agent already ran don't need a separate rerun, since the full suite covers them; after a failure, a fix or any further change, run it again as usual. Exit codes in the agent's event stream can't replace this step: some are made up from tool status, and compound commands and redirected output can hide failures.
4. **Take a closer look at runs without an OS sandbox** (`isolation` is `tools` in the result; currently opencode and pi):
   - With `run_access` set to `edit`, it can't run commands: Claude runs every test and script itself, and a report saying "passed" counts for nothing.
   - With `run_access` set to `shell`, its commands can reach outside the working directory, where change tracking can't see. Go through the diff file by file; if the task touches outside paths, installs dependencies or goes online, check what it actually did (`opencode.jsonl` or `pi.jsonl` in `run_dir` has every command it ran).
   - Write-tool events count as evidence of who changed a file (`by: agent`); files the report merely claims don't.
5. Once it passes (including after any rework), you usually level the review next ("Levels" in SKILL.md); if the result still needs discussing with other models, level that discussion first. If the review is level 0, report to the user.

## Rework
- If it isn't good enough, use `resume --reason rework` for one rework, with a brief that says exactly what's wrong and how to fix it. If the cause was underestimating the task, move up one level for the rework (simple → normal → complex); if that level is `"claude code"` in the config, don't resume, and Claude takes over instead; if the higher cell doesn't list the original agent, has another required agent, or the original run was a seat in a plan, the script refuses the resume, so hand it off again as a new run at the new level (picking agents as usual; it still counts as this rework). Otherwise keep the same level. Image tasks have no levels: a resume keeps the original cell and takes no `--level`.
- A resume can only continue the latest round, and only once it has ended: the script refuses to resume a run that is still running or has already been resumed, and the error gives the latest round's run_id. A resume keeps the original group (`--group` can't change it) and `--add-dir`; a Codex resume passes the extra folders together with the writable folders configured under `[sandbox_workspace_write]` in `~/.codex/config.toml`, and when that setting can't be read it passes neither and the script warns that the extra folders aren't writable this time.
- A resume needs `--level` (except for image tasks), and the previous round's agent must be a candidate in that cell; a run handed to a named agent (marked `outside_cell` in the result) is exempt and resumes with that agent. A resume at a different level is refused when the new cell has another required agent, and a seat from a plan can't change level on resume; to change it, create a new plan for the new level. The model is worked out again from the level you give, so moving up a level for a rework may switch models. If no model is configured anywhere, the previous round's model is kept.
- If it still isn't good enough after the rework, or the agent times out or errors, Claude takes over and finishes it, and tells the user why. Images are the exception; see "Rework" in `references/image.md`.
- A new requirement beyond the original task is not a rework and not a resume: level it as a new task and hand it off on its own. The original brief draws the line: reaching a goal or completion criterion it states by another route is a rework; something it doesn't mention, or says is left out this time, is a new requirement.
