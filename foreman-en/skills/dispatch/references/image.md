# The image module: routes, who does what, and the workflow

Read this once you see that the work is graphics, before showing the route pop-up. Prompts, backgrounds, slot templates, the whole workflow for code work and edits are in `references/image-assets.md` (every "section N" below means that file), and the options of the `assets` subcommand are in `references/assets-cli.md`.

Image generation and hand-drawing both go through the image module, never `run`. Image tasks have no levels: `plan`, `image` and resumes never take `--level`, and the effort is the one written in the image cell; image quality depends on the image model, not much on reasoning effort. If the same piece of work also changes code (such as wiring the image into a page), level the code part separately as hands-on work. A visual check that only reads screenshots (`review --target visual`) is a review and doesn't come through here.

## The two cells
- Image generation goes to the agents in `resolved_modules.image.generate`, hand-drawing (pieces that bend, pure vector art) to those in `resolved_modules.image.draw`, each with the effort written in its cell. generate only takes image-capable agents (`capabilities.images` is `true`, currently only the `codex cli` type), draw takes agents that can do hands-on work; with several candidates, pick per `references/seats.md`.
- **When a cell is off**: if generate is `null`, the user has turned image generation off, so tell the user no images will be made this time and don't patch it together some other way; if draw is `null`, Claude draws the pieces that bend and the pure vector art itself. If `image_configured` is `false` (the config has no image block yet, for example one rewritten from an old config), treat both cells as off and suggest the user run `/foreman-en:setup` to add the two image cells.

## Workflow and rules
1. **Scope**: what a model has to draw comes here, whether the deliverable is a bitmap or SVG, HTML, canvas or an animation: photos, illustrations, textures, sprites, covers and hero images, characters and mascots, scenes, illustrated icons, the visuals of UI components, assets to be cut into single pieces or turned into SVG (including illustrations used as whole pieces in SVG, HTML and canvas work and animations), removing the background from an existing image, changes to existing images, plus hand-drawing pieces that bend from the final image and pure vector art. When the user explicitly asks for hand-written SVG or pure code, don't generate images (the pop-up still comes, for route ④).
2. **Ask for the route**: before work starts on each new graphic deliverable, have the user choose the route in an AskUserQuestion pop-up, even when `dispatch.auto` is on or the user's own words already settled the route. The route decides which cells are used:

   | Route | How | Cells used |
   |---|---|---|
   | ① Bitmap | Generate a new image or edit an existing one; deliver a bitmap | generate |
   | ② Bitmap + vector mix | One final image; Claude cuts out the pieces that move as a whole with `assets layers`; pieces that bend are hand-drawn as SVG from the final image | generate, draw |
   | ③ Pure vector, reference image first | The reference image only sets the style; the result is all paths, no embedded bitmaps | generate (reference image only), draw |
   | ④ Pure vector / code | No image tool is called | draw |

   - **How to write the pop-up**: put "Image route" in the question (for example "Image route: how should we make the home-page mascot?") and use "Image route" as the header; start the four option labels with ①②③④ as in the table (for example "② Bitmap + vector mix"). That's how the script recognizes the route pop-up and reads which route was chosen.
   - Say in the pop-up (in the question or the option descriptions): which model generates and which hand-draws; whether reference images get uploaded to the model service; the rework rule: no cap on regenerations, but if three regenerations in a row don't improve the same problem, stop and ask the user, and follow any limit the user sets. Whether to produce a few candidate images is a second question in the same pop-up.
   - When the user's own words already settled the route, still show the pop-up, with that option first and "(your choice)" at the end of its label.
   - Don't ask again for rework, partial regeneration, patches or technical retries of the same deliverable. Ask again when switching routes, adding a deliverable, widening the scope, or changing the agent or vendor.
   - When a role assignment also needs confirming, combine both in one pop-up.
3. **The confirmation record**: the plugin's hook records the questions and answers of route pop-ups per Claude session in `~/.claude/foreman/answers/<session>.jsonl`. `plan --module image` looks only at the latest route pop-up in this session: it creates the plan only if the user chose the route given by `--route`. If the user cancelled, hasn't chosen yet, picked Other and wrote something else, or chose a different route, no plan is created; act on the user's answer and ask again if needed. One answer can back several plans for that deliverable (for example the generate and draw plans of route ②). Only the hook writes the answers file; never write, edit or delete it yourself: the record guards against forgetting to ask, it can't stop forgery, and forging it breaks the rules. If you did show the pop-up, the user did choose, and `plan` still says there's no answer, the hook most likely isn't running (for example the plugin's hooks are disabled): tell the user plainly, and don't fall back to generating images through `run`. The hook was tested in the desktop app on 2026-10-19; the command-line version wasn't tested.
4. **Create the plans**: one plan per cell the route uses, with `plan --module image --cell <generate|draw> --route <route number> --group <group> --seat <agent ID> --why "<reason>"`. Route ① only needs generate; route ② needs generate first (final image, background plate, local variants) and draw once the pieces are taken (the pieces that bend); route ③ needs generate first (reference image only), then draw (the pure vector result); route ④ only needs draw. A deliverable that uses both cells gets one plan per cell, both backed by the same route answer.
   ```bash
   node "<script path>" plan --cwd "<project dir>" --module image --cell generate --route 2 --group <group> --seat <agent ID in the generate cell> --why "<reason>"
   ```
5. **Start**: `image --plan <plan_id> --seat 1 --brief <brief> --title <short title> --scope <output dir> [--track "<path>"] [--effort <effort>]`, with no `--level`. Don't generate images through `run`: the script points out in the result that the images didn't go through the image module. After starting, tell the user and add the board link as "When you hand off" in SKILL.md says. An image takes tens of seconds, so the live view sitting on the previous step meanwhile is normal; once the image is ready, a "Generated image …" line appears in the timeline.
6. **Who does what**: Claude decides what to draw: subject, style, purpose, aspect ratio, the parts list and names, the palette and the final image; for any text in the image, give the exact wording and require it to be used as is. Codex only generates. Removing backgrounds, splitting parts, taking pieces from the final image, naming, reducing colors, vectorizing and checking are done by Claude running the `assets` subcommand locally (see `references/assets-cli.md`), not handed out and not given to Codex; tracing and deforming the pieces that bend is the exception, given to Codex, which runs `assets trace`, `capture` and `playback` itself to check its work. Never use a script to fake what the model should draw, but scripts may process what the model drew.
7. **One source: Codex draws whole pictures, never single pieces**: image models can't hit joint pivots, contact points with things drawn in code, or seams between two generations, and pieces they take out on their own come back enlarged and redrawn (tests in October 2026 were often off by a sizable fraction of the part's length, and pieces taken out alone were enlarged 1.09–2.06 times). So two areas of pixels that meet must come from the same image, or one side must be drawn in code. Every piece of the work comes from the final image: pieces that move as a whole are cut out where they are by Claude with `assets layers`; pieces that bend themselves or must touch things drawn in code exactly go to the draw cell, traced from the final image as paths with their deformation; physics, mechanics, text and UI are drawn in code. The four kinds of image Codex makes and how pieces are taken are in the general rule and step 1 of section 6. Routes ③ and ④ deliver paths only: never pass off a PNG embedded in an SVG as vector art, and route ④ makes no bitmaps at all.
8. **The user sees the final image first**: write it from the final-image template in step 2 of section 6 (only things visible in the picture, no list of pieces or how to split them); make the plate and take pieces only after the user approves it. Joins go on the edge of something that already covers them in the final image. Don't ask the model to take a piece out on its own, to remove a piece and finish the edge, or to paint in parts of a character hidden behind something. Expressions (a blink, an open mouth) are local edits of the final image laid over as patches with `assets patch`: never a whole swapped image, and never traced.
9. **Hand-drawing the pieces that bend**: goes to the draw cell (route ②). Claude takes the pieces first, then writes the brief from the template in step 6 of section 6: the inputs, a ready page harness and interface, the pivots, the motion formulas, what the joins must do and what to self-check. When it comes back, Claude takes its own screenshots and measurements to check it and doesn't rely on the agent's self-check. In the October 2026 comparison the two sides tied on the metrics, and in the blind review Codex's version looked more natural. The drawing for the pure vector routes (③, ④) goes to the draw cell too.
10. **Tell the user before starting** which pieces move as a whole, which go to Codex to be traced and bent, which are drawn in code, and why. **Before delivering an animation**, check one loop with `assets playback` (flicker, the loop seam, jumps) and give the user the playback file to watch; it isn't fully checked until someone has watched it play.
11. **Brief**:
    - Spell out the call (arguments in section 1). A new image: `tools.image_gen__imagegen({prompt, transparent_background})`. Editing, generating from a reference, splitting or layering: also pass `referenced_image_paths: ["<absolute path>", …]` and refer to them in the prompt as "Image 1", "Image 2" in order. Without this argument the tool generates from scratch and the reference has no effect. Reference images are uploaded to the model service, so don't use sensitive or unlicensed ones.
    - Don't give pixel sizes, only the aspect ratio (1:1, 3:2, 2:3, 3:1); for other sizes, use the SVG or scale when delivering.
    - For assets that need a transparent background, set `transparent_background: true`, and write the background, spacing, style and exclusions from the templates in sections 2 and 3.
    - Two or more parts: name them with the slot template in section 4, not by their order on the sheet: the model reshuffles them.
    - Give the path in the project for each image; copy the original as is, without converting or compressing. Unless the user asks for variants, generate each source image once.
12. **Checking**:
    1. `module`, `step` and `route` in the result say which cell and route the task belongs to. `generated_images` lists the original files of the images that appeared in this round, and `image_calls` lists the arguments each image call actually passed (read from the Codex session log). If a step that needed a reference has no `referenced_image_paths` in `image_calls`, the reference had no effect, so rework it (`warnings` points this out). If both fields are missing, where the image came from is unverified; look at the run folder and output before concluding anything. A warning that a route ④ task made bitmaps or a route ③ or ④ SVG embeds one (`<image>`) means rework.
    2. For assets to be cut or vectorized, run `assets cut`: anything `fail` in its `checks` goes straight back for rework; Claude judges the `needs_review` items by looking.
    3. Open the image with Read (for cut assets, the `sheet.png` contact sheet): is each slot the right part, are details, style and colors right, is any text used as given.
    4. Hand-drawn (draw) work that comes back is checked per step 6 of section 6, with its diff checked as in `references/acceptance.md`.
13. **Rework**: resume the original image task with `resume --run <run_id> --brief … --reason rework`, without `--level` and without asking again. There's no fixed number of generations; regenerate whenever an image isn't right, and change something each time (the prompt, the references, the area to change) instead of retrying the same call. The thresholds for regenerating are in step 9 of section 6; the main three: a moving piece in the final image is covered by another with no outline or cover between them; the measured alignment (`measured`) of the plate or a local variant is more than 3 pixels off or more than 1% scaled; the plate still shows traces of the subject. A join that drifts apart or a sudden change of line weight once things move is not an image problem: the pieces share a source and line up to begin with, so fix the deformation code (pivots, weights, positions) and don't enlarge hand-drawn parts to cover it; deformation Codex wrote goes back for rework under "Rework" in `references/acceptance.md`. When a built-in command reports it isn't sure, follow the thresholds; don't write a registration or fitting script to get around it. If three regenerations in a row don't improve the same problem, stop and give the user the problem, what was tried, how many images were generated and the options; if the user set a limit on generations, follow it. Images don't follow the "Claude takes over" rule in "Rework": Claude can't draw bitmaps, and must never use a script to fake what the model should draw. For a partial fix, pass the original as the reference and say "change only X, keep everything else" (section 7); when delivering, replace only the changed part and keep the files of the other parts from the previous version.
14. **Vectorizing**: turn only flat assets with few colors into SVG (step 7 of section 6). Keep characters and images with gradients or much detail as PNG by default, embedded with `<image>` in the SVG or page, and tell the user that part isn't pure paths; that's how routes ① and ② work, and it isn't allowed when the user chose ③ or ④.
