# Review (/foreman-en:review)

Read this when a review is levelled 1 or higher, or the user asks for a review, before choosing what to review and creating the plan; the rules for picking reviewers and for the Claude Code seat are in `references/seats.md`. The levels are under "Levels" in SKILL.md.

A review judges something that already exists and returns a list of issues (which may be empty). Say what's under review with `--target`:

| `--target` | What it reviews | Material |
|---|---|---|
| `diff` (default) | Code changes | The range of changes the script works out with git; see "How to review" |
| `files` | Existing files, changed or not, such as a design document already written, a module or a config | The files listed with `--file` |
| `claims` | Conclusions and their evidence, such as the evidence review before research conclusions are recorded (see `references/research.md`) | The review brief lists the conclusions one by one; the evidence files go in with `--file` |
| `visual` | Screenshots, playback files, renders, such as the visual check before an animation or page is delivered | The images listed with `--file`; only goes to agents that can read images (`capabilities.reads_images`; for now only Codex) |

When `resolved_modules.review.<level>` is `"claude code"`, that level gets no outside review; Claude reviews it carefully itself, and handles what it finds as in "After the review".

## Levels
The level table is under "Levels" in SKILL.md; decide in this order:
- First check for level 3: the change alters the behaviour of money and billing, deleting or migrating data, concurrency, auth and security, or irreversible operations; or there's concrete evidence from call paths, config or failures that it may affect them, and that can't be ruled out. A file that merely sits in a related folder, changes only to comments and formatting, and mechanical changes checked not to alter behaviour don't count. Small size, tests or easy rollback never bring a level 3 hit down.
- Without a level 3 hit, choose between levels 0–2. Being unsure about a review doesn't move it up a level by itself: check the call paths, what's affected and the existing verification; if a high-risk effect can't be ruled out, use level 3, otherwise level it by the effect you've established and put what's unconfirmed in the review brief.
- Don't inherit the hands-on level, who made the change, or how hard it was to find the cause: for a bug whose cause was unknown or took long to find, look at what the finished change touches. Level 3 hands-on work Claude did itself is reviewed at level 2 at least (the author's own review isn't an independent source), but that doesn't raise it to level 3.
- Put the reason for the level in `plan --why`: for level 3, the high-risk area hit and where; for level 2, one sentence on why it isn't level 3.
- When a reviewer's report points out that the material really is level 3 and Claude confirms it, review it once more at level 3 (a new plan) and say so in the report.

## How to review
- Review changes an agent delivered with `review` in a **new session**; don't have it review its own work in the session that did it.
- Pick reviewers per seats.md: a different model from the one that did the work where possible; when only the same model is available, review as usual and say in the report that it was the same model in a new session. For `visual`, pick only agents that can read images. API agents can review too (text only, never `visual`), and they receive the patch or the file contents: don't pick one when the preference files or the project don't allow sending material to its provider; when you do pick one, start the queue check as in "When an API participant is busy" in `references/recovery.md`.
- Reviews always use a plan, even with a single reviewer: create it with `plan --module review --cell <level> --group <name> --target <target> [--file …] [--base <branch> | --commit <sha>] --seat … [--host-role "<role>"]`. What to review and the material are fixed when the plan is created, and the script records the material's fingerprint. When the cell is configured per scene, also add `--scene <scene> --scene-why "<which line of the preferences it follows>"` (see "Scenes" in step 3 of seats.md).
- Next, Claude Code writes its own list of issues per "The Claude Code seat" in seats.md (review schema) and `submit`s it, adding `--author` when the changes are its own. Problems found and fixed during checking don't go in. If the material changed after the plan was created, both `submit` and the external seats are refused, so recreate the plan for the current material.
- Then start one `review --plan <plan_id> --seat <n> --brief …` per external seat, without `--target`, `--file` or the range options. When different angles are needed (for an evidence review, say), seats can carry roles (`--seat <agent>=<role>`), with each role card written into that seat's review brief; assign them and confirm with the pop-up as in `references/roles.md`.
- Every external seat is a new session. Reviews can't be resumed; follow-up questions and second reviews are new reviews (a new plan, where the Claude Code seat submits first again), and a disputed finding can get a targeted second look the same way, including findings from the Claude Code seat. When an external review seat in a plan failed, stalled or didn't finish reviewing (returned no valid result), start that seat again with the same `review --plan <plan_id> --seat <n>` command (the material must be the same as when the plan was created); a seat that already returned a valid result can't be started again. The Claude Code seat submits one report per review plan.
- Always pass a review brief with `--brief`: intent of the change, the kinds of risk and what to look at, known facts (failure logs, reproduction steps, problems the user reported) and what has been verified (which commands passed on which version, and what isn't covered); a specific diagnosis Claude Code hasn't confirmed stays out of the brief and goes into its own report. The review rules tell reviewers not to rerun tests the brief says have passed, and to run targeted read-only commands only for a specific suspicion; a reproduction that would write files goes into `unverified` for Claude to run. For `claims`, list the conclusions one by one, each with where its evidence is and the key numbers. `--file` works for all four targets: Codex, opencode and pi only get the paths (listed as "Key files") and read them themselves; API agents get the file contents. opencode, pi and agy can only read files inside the project directory: when the material is outside it (a patch in the scratchpad, for example), a plan with them in it is refused, so copy the material into the project directory first, or give those seats to Codex or API agents. Codex runs its built-in review only for a `diff` with neither a review brief nor `--file`: that output is plain English text with no structure and doesn't follow these review rules, so always pass a brief.
- For `diff`, the script works out the range with git first, matching what Codex's native review means; with no changes at all, it stops with an error instead of handing anything off:
  - `--uncommitted` (the default): staged and unstaged changes plus untracked new files;
  - `--base <branch>`: from the merge-base with that branch to the current working tree, both committed and uncommitted, without untracked files;
  - `--commit <sha>`: the changes that commit introduced.
- `files`, `claims` and `visual` need no changes in the repository, and the folder needn't be a git repository; to review existing files in a folder without git, use `--target files`.
- `review_target` and `review_scope` in the result say what was reviewed, how many files, and the material's fingerprint; for a `diff`, the full patch is saved as `review.patch` in the run directory. If the material changed while the review ran, the result is marked `stale: true` and `warnings` says so: the review may not cover the latest version, so review again if it matters.
- Codex reads the changes and files itself. opencode, pi and agy get the patch the script computed (for `diff`) or the file paths, plus read-only tools for context; opencode and pi can't run commands, while agy can run read-only commands inside its sandbox when that works on this machine. API agents only see the attached material: the patch or the file contents, plus the project file list. A patch over about 200,000 characters for opencode, pi or agy, or material over about 300,000 characters for an API agent, is refused: review commit by commit (`--commit`) or file by file, or give the review to Codex.

## Gap pass
When the level's gap switch (`resolved_modules.review.gap`, or the scene's value when a scene was picked) is on, after the seats of a multi-seat review finish and Claude Code merges duplicates (the Claude Code seat's list included), run one gap pass: a new review by a suitable model from the cell that hasn't taken part yet (a base model different from every earlier seat, the Claude Code seat included, with tools that can handle the material), asking only "what does this list still miss?" The Claude Code seat can't be the gap seat.
- **Seat**: the gap seat is one seat of the original plan; it comes on top of the configured `seats` (no `--count-why` needed), and a plan has at most one. When the switch is on and the cell still has a suitable candidate, put it in when creating the plan, as `--seat <agent>=gap`; `plan` checks this. When the switch is off, don't add one. Start the other seats first, and start this one after they have all finished and Claude has merged the duplicates. When every candidate in the cell is already one of the independent reviewers, there's no gap pass. A gap seat reserved in the plan must be run: when the gap seat's agent isn't required and the plan has required seats, `state` only looks at the required ones and can show `complete` while the gap seat hasn't finished, so `status --plan` lists gap seats with no valid result yet in `gap_unfinished` and the live view marks them on the plan's line ("gap seat not finished").
- **Brief**: the original review brief plus the merged list of issues (the Claude Code seat's included; each with its location and the issue in one sentence, without Claude Code's verdicts), asking only for issues not on the list, and empty `findings` if there are none.
- **Checking**: verify its findings one by one as usual and record them with `judge`; one that is really the same as an issue on the list gets linked to it with `--same`.
- The gap seat isn't an angle to check from, so it gets no pop-up of its own; when role mode needs a pop-up anyway, list it in the assignment table.
- Skip it when the cell has no suitable model left, and say in the report that there was no gap pass and why. Levels whose switch is off have no gap pass.

## Read-only
Discussions and reviews may not change project files. The result's `readonly` says how that was actually enforced:

| `readonly` | Who | What it means |
|---|---|---|
| `tools` | opencode, pi, agy, API | Only tools for reading, searching and listing files, or no tools at all; agy also has read-only commands in its sandbox |
| `sandbox` | Codex with a `read-only` sandbox set for this kind of task | The OS sandbox blocks writes |
| `audited` | Codex without a read-only sandbox | Only the rules hold it back, plus a snapshot comparison afterwards |

- `audited` needs a change snapshot: without one the run doesn't start, and `--no-snapshot` isn't allowed. When `summary.warnings` in `config` or `check` has `readonly_audited`, pass the fix it describes on to the user.
- When there's evidence of a write (a tool event, or the agent saying in its report that it changed something), that participant is marked failed: `status` is `failed`, `readonly_violation` lists the files, and the diff is in `diff.patch` in the run directory. Its findings stay in the result and can still be used; say in the report that it overstepped. Nothing is reverted automatically: changes are attributed by whole file, and the same file may also hold changes by the user or other tasks, so only revert the parts you can show it made in this run; leave anything you can't tell apart and let the user handle it.
- Changes of unknown origin (`by: unknown`) aren't a violation; most likely someone else made them, so don't revert them. When the material under review changes like this, the review result is marked `stale`.

## After the review
1. **Verify each finding**: the findings are in the result's `report`: `verdict` (`issues_found`, `no_issues`, or `incomplete` when the reviewer didn't finish), `findings` (each with an ID, location, issue, trigger, severity, evidence and suggested fix), `coverage` (what was checked and what wasn't) and `unverified` (what the reviewer wasn't sure of). Merge duplicate findings across seats (the Claude Code seat's report included), then verify each one: only issues that really exist count, and the Claude Code seat's own findings get verified too; drop false positives and say briefly in the report why they don't hold. A `verdict` of `incomplete`, or key parts under `coverage.not_checked`, means the review is incomplete; review the rest if it matters. With no `report` (Codex's built-in review, or no valid format after two tries), the findings are in the text of `last_message`.
2. **Record the verdicts**: once checked, record what happened to each finding of every seat with `judge`, the Claude Code seat's on its report record: `judge --run <run_id> --accept "F1,F3" --reject "F2"` (`--partial` for findings that partly hold), using the ids in the report. When several seats found the same issue, link them on one seat with `--same "F1=<the other seat's run_id>:F4"`; `stats` uses this to tell which model alone found an issue. Seats recorded as failed for writing files still get their findings recorded. Without a structured report (Codex's built-in review), use the numbers Claude gave the points in its report. A seat whose structured report is `no_issues` with nothing listed needs no record; `stats` counts it as 0 points by itself.
3. **Who fixes them**:
   - A review Claude asked for on its own: Claude fixes small issues itself; if there are many, or they touch the logic, put the verified issues in a rework brief and `resume --reason rework` the agent that did the work, which counts as one rework (see "Rework" in `references/acceptance.md`). If Claude made the change, Claude fixes it.
   - A review the user started with `/foreman-en:review`: the user only asked for a review, so first tell them the verified issues and how you plan to fix them, and fix once they agree (or if they already said to fix them).
4. **Check again after fixing**: rerun the build, tests or scripts on the final version. Whether to review again goes by the risk of the fix itself, not the level of the first review: review once more when the fix hits level 3 under "Levels", otherwise not (a disputed issue can still get its own targeted check). A second review goes like this:
   - A new plan (new sessions), its group name the original one plus `-rr`, with "re-review" in the title; the Claude Code seat submits its report first as usual.
   - It checks only three things: whether the issues accepted last time are fixed, whether the fixes brought in new issues, and how the fixes interact directly with the original change. The brief lists each accepted issue (ID, location) and how it was fixed, plus the callers and data constraints affected; the reviewer may read files outside the fix, and the brief says not to report again the issues already verified last time.
   - When the fix has a clear boundary and doesn't widen interfaces or the risk scope, use only one seat: the cell's required strong model (or a strong-tier candidate if none of the required ones is strong), with `--count-why "targeted re-review of the fix only"`, no roles and no gap pass. When the fix widens interfaces or the risk scope, or its boundary is unclear, review with the level's usual seats and gap rule.
   - Review the fix itself: when the fix is a commit of its own, use `--commit <sha>`; when the version reviewed last time is committed and only the fix comes after it, use `--base <that commit>` (untracked files aren't included, so `git add` new files from the fix or attach them with `--file`) or `--uncommitted` (when the working tree holds only the fix); otherwise use `--target files --file <files the fix changed>`, which reviews whole files rather than a diff, so say in the brief where the fix is.
   - At most one second review; if issues remain or key parts weren't covered, report them as unresolved or incomplete.
5. **Say so in the report** when the reviewer was the same model as the agent that did the work, when a review result is marked `stale`, when a reviewer wrote files it shouldn't have, or when there was no gap pass.
