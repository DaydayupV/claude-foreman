# Picking seats: candidates, required agents, seat counts and the Claude Code seat

Read this before starting external seats for the first time: always for discussions and reviews, and for hands-on work when the cell has several candidates or a required agent. It covers whom to pick from a cell's candidates, seat counts, how plans are created, and Claude Code's own seat in discussions and reviews.

## When a cell has several candidates
A cell can list several candidates, some marked required (`required`). When the cell is used, Claude picks in this order:
1. Drop the ones that can't do it: missing capabilities (making images, reading images, hands-on access), material that may not go to that provider (per the preference files or the project), or quota already used up.
2. Add every required agent.
3. For discussions and reviews, fill the configured number of external seats: how many external models each level uses is in `resolved_modules.<discuss|review>.seats.<level>` (defaults under "Candidates and required agents" in `references/config.md`; not counting the Claude Code seat or a gap seat); when the cell has fewer usable candidates than that, use them all. Required agents count toward that number, and Claude fills the rest from the candidates with different base models; the same model reached through api, pi or opencode counts as one base model (the script normalizes names with the identity table in `scripts/models.json`, the same table `plan` and `stats` use). `plan` refuses a plan whose external seats don't match the configured number; when it really needs more or fewer (the user changed the role assignment in the pop-up, one vendor can't receive the material, one agent is out of quota), add `--count-why "<reason>"` saying why. Mid and weak models can take seats too, as breadth seats that only join round 1 and whose points Claude checks one by one. In normal mode, mid and weak participants are breadth seats; in role mode it depends on whether they meet the role's suggested tier (see `references/roles.md`). The gap seat of a level 3 review comes on top of the configured number (see "Gap pass" in `references/review.md`).
4. For hands-on work, one executor per work package: complex tasks go first to strong models that can run commands and have a sandbox; mechanical tasks can use cheaper ones; when splitting work, different parts can go to different agents in the same cell, each using its own parallel slots.
5. Reviewers should be a different model from the one that did the work where possible; when only the same model is available, review as usual and say so in the report.
6. Basis: each candidate's `tier` in the `config` output and the strengths from the `tiers` command are the starting point (rules in `references/model-tiers.md`); the preference files can change it, and can point to local results (`stats`) to override a tier. The script only sums things up and never ranks models. By default, don't change a tier on speed (tok/s) alone: look at verified quality first, then compare time and cost on similar tasks; when the user clearly puts speed first you can choose by speed, but don't take it as a sign that the model is more capable.
7. Each time, tell the user in one sentence whom you picked, why, and whom you left out.

When you pick several seats, first create a dispatch plan with `plan`, with the reasons in `--why`, then start each seat with `--plan <plan_id> --seat <n>` (`plan` prints the start command for each seat). A seat can't be started twice: use `resume` for rework; a review seat that returned no valid result can be started again (see `references/review.md`); so can a seat whose first round failed before it got a session and so can't be resumed, with the same command. Discussions and reviews always use a plan, even with a single external seat (the plan holds the Claude Code seat); the script refuses `discuss` and `review` without one. For hands-on work with a single seat you can skip the plan and use `--level` directly (with `--agent` to name one); if the cell has another required agent, the script refuses, and you need a plan.
- When a required agent is at its parallel limit, don't skip it: the dispatch command queues automatically in arrival order by default (for up to 60 minutes, writing its place in line to stderr) and starts as soon as a slot frees up, so start dispatches in the background. If the wait runs out, it exits with a queue-timeout message; dispatch again then.
- When a required agent fails, runs out of quota or is cancelled, the task counts as incomplete (`state` in `status --plan <plan_id>` is `incomplete`, and `missing_required` says who is missing). Handle it per `references/recovery.md`; another candidate doesn't stand in for it. Say so when reporting to the user.
- When the project config closes a whole cell (`closed_by_project`), the step for that cell's required agents counts as "not done". Tell the user plainly; don't do it yourself and call the requirement met.
- `state` being `complete` only means the required seats returned valid results; when a level 3 review reserved a gap seat that hasn't finished, look at `gap_unfinished` (see `references/review.md`).

## Roles on seats
Any plan with several seats can give its seats roles (`--seat <agent>=<role>`), with the role card written into that seat's brief. What that means differs by module:
- Levels 2 and 3 of discussions and reviews: a role is an angle to check from, assigned by `references/roles.md` (tool access is a hard gate, tiers are only a guide, core roles are never merged, as many external seats as the level's configured `seats`). The Claude Code seat is assigned by the same rules and gets its role with `plan --host-role "<role>"`. Before starting, always show a pop-up for the user to confirm the assignment, even when `dispatch.auto` is `true`. Level 1 takes no roles. A review's gap seat is written `=gap`, but it isn't an angle to check from and never triggers the pop-up.
- Run and draw: a role is a work package with its own write scope (such as "implementation" and "tests"), sent out by "Splitting work to run in parallel" in `references/run.md`; tell the user in one sentence how it was split, with no pop-up.
- Generate: no roles; Claude sets what the picture needs as a whole.
- When the image-route pop-up and the role-assignment pop-up are both due, combine them into one.

## Four kinds of participants: what each can see
This applies to discussions and reviews alike.
- **Codex**: can read the code and run read-only commands to check things itself.
- **opencode agents** (`type` is `opencode cli`): models called through the Opencode CLI on this machine. The script gives them only the read, search and list tools, so they can look through the project's code themselves but can't run commands or change files. They can only read files inside the project directory; put material from outside the project into the brief itself. Every file they read is another request, so they use more quota than API agents; put premium models with tight subscription limits at level 3. `cost_usd` in the result is priced from the model's official API price; the cost it reports itself is kept in `reported_cost_usd` for the record and not reported.
- **pi agents** (`type` is `pi cli`): models called through the Pi CLI on this machine. Like opencode agents they only get the read, search and list tools, and reading is limited to the project directory (checked by the guard extension foreman injects). `cost_usd` is priced from the model's official API price; the cost pi reports itself is kept in `reported_cost_usd` for the record. pi uses the user's own pi config and sign-ins, but doesn't load their installed extensions, skills or MCP servers.
- **API agents** (`type` is `api`, such as DeepSeek): see only the brief and the attached material and can't look through the code themselves. Attach the relevant files with `--file "<path>"` (can be given more than once; `--file "<path>:<start>-<end>"` attaches just those lines), including the code the brief mentions and the core modules under discussion or review. There's a size limit (about 300,000 characters); the script errors if it's exceeded, so pick files more carefully or use line ranges; it also attaches the project's file list. The attached material is sent to that provider, so don't add API agents for projects whose preference file or project config says not to. Files it asks for in `open_questions` get attached with `--file` in the next round. An API agent with `key_set` `false` in `agents_status` fails outright: before picking it, remind the user to either fill in `api_key` for that agent in `~/.claude/foreman/config.json` (takes effect immediately), or set the environment variable named by `api_key_env` and restart Claude Code. With an API participant, start the queue check in the background as "When an API participant is busy" in `references/recovery.md` says.
- When `--file` is passed to Codex, an opencode agent or a pi agent, the script only lists the paths as "key files" without their contents; they read the files themselves.
- Check what any participant says about the code against the source before accepting it.

## The Claude Code seat
Whenever a discussion or review sends out external seats, Claude Code takes a seat of its own as well. Apart from Claude Code making the final decision, this seat is the same as any external seat: the same report, the same timing, the same cross-examination, the same verdict records.
- **Scope**: levels 1–3 of discussions and reviews. Level 0, and levels set to `"claude code"` with no outside model (Claude Code thinks it through or reviews it again on its own), don't use it; hands-on work and images don't either.
- **The report**: JSON in the same format as the external seats: `schemas/discuss.schema.json` for discussions, `schemas/review.schema.json` for reviews. Level 1 can be short: `options` and `critiques` may be empty, but `position`, `open_questions` and `confidence` are required; don't invent points just to fill out the report. A review report covers the material fixed in the plan; problems found and fixed during checking don't count as findings of this round.
- **Submit first, then start the external seats**: once the plan exists, record the report with `submit --plan <plan_id> --report <report.json>`; external seats can start only after it, and the script checks this at admission. Later discussion rounds work the same way: submit this round's challenges to the proposals as a report, then resume the other seats. The script keeps a snapshot of the report, its fingerprint and the time, and `host.before_external_start` in `status --plan` says whether it came before the external seats started. That can't prove the results weren't read, so read no participant's result before submitting.
- **The shared brief**: if writing the report shows that the topic or review brief lacks facts the external seats need (relevant user preferences, routes already rejected and why, facts from checking, reproduction steps, problems the user reported), add them before starting. The brief states facts, not a specific diagnosis or leaning Claude Code hasn't confirmed; those go only into its own report. Key facts that can't be added (for example because they may not be sent out) are noted in the decision record with the conclusions they affect.
- **Sending it out**: the report goes anonymously to the external seats in round 2, so write it within what every participant in this session may receive; give only the conclusion for anything that rests on user preferences or private context, and mark key evidence that can't be sent as restricted.
- **Seat count**: it doesn't count toward a level's `seats`.
- **Model**: the user picks Claude Code's model inside Claude Code. Add `--model <current model ID>` when submitting, using the model ID given in Claude Code's system prompt (such as `claude-opus-5-5`) and writing it the same way every time, since `stats` groups by it (self-reported; the script doesn't check it). When filling external seats with different base models, Claude Code's model counts as one, and an external candidate on the same base model doesn't add an independent model.
- **Authorship**: when reviewing changes Claude Code wrote itself, or discussing a design it proposed, add `--author` to `submit`. The seat then doesn't count as an independent source, and outside review is no less needed because of it; the same holds when an external seat uses the author's base model.
- **Roles**: assigned by the same rules as the external seats, by what it can actually do (`plan --host-role "<role>"`), writing its report around the role card's checks (the report format doesn't change; the role card's text goes into the decision record); it can be the general cross-check seat, but that seat isn't reserved for it. List it in the assignment table and the confirmation pop-up.
- **What it doesn't do**: it can't be the gap seat (it took part in the first round), and the "every seat is a new session" rule applies only to external seats.
- **Deciding**: Claude Code makes the final decision. Its own points are numbered too, with reasons for each verdict, recorded with `judge` on its report record; `stats` marks them self-judged. Anonymity doesn't work for Claude Code itself, since it knows its own proposal, so bias is kept down by submitting first, point-by-point evidence and written reasons. Two cases are called out explicitly in the decision record for the user to look at: the final plan is essentially Claude Code's own original proposal and external objections were rejected; one of its key claims was contradicted by reproducible external evidence and was kept anyway.
- **Archive**: a level 2 or 3 decision record is also saved as a Markdown file at `plans/<plan_id>.decision.md` in the run directory; a revised decision is saved as a new version (`<plan_id>.decision.2.md`) instead of overwriting the old one.
