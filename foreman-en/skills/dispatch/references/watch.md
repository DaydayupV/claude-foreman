# The live view and the web board

Let the user see live progress after handing work off. While the web board is on (`dispatch.watch.web` is `true`), the points under "When you hand off" in SKILL.md are enough, and this file is only needed when the user asks about the board, wants a replay, or the board server isn't up; while the web board is off and the terminal live view should open, read this before the first handoff.

## Which way in
The switches are in `dispatch.watch`, and `web` decides:
- **`web` is `true` (the web board is on)**: use only the web board and don't open a terminal live view on your own. After handing work off, write the "Handed off" sentence with the board link in your reply text, and while runs are still going end every turn's reply text with the board link; see "The web board" below. A user who wants the terminal view uses `/foreman-en:watch`.
- **`web` is `false`**: with `terminal` `true` (the default), open the terminal live view by yourself once the work has started in the background, and bring the terminal panel up, as in "The terminal live view"; with `terminal` `false`, don't open it, just tell the user they can check with `/foreman-en:watch`.

## The terminal live view
- **Open the terminal panel first, then the tab** (Claude desktop app; don't skip this, opening a tab doesn't bring the panel up): first call the tool that shows panes (its name contains `show_pane`; load it together with `run_in_terminal` in one ToolSearch) with `pane` set to `terminal` and no `tab_id`; once it returns, open the tab with `run_in_terminal`. While the panel is open, a newly opened tab comes to the front by itself, so the user sees watch's few-second intro from the start; the other way round, opening the tab first and showing the panel afterwards, there are often more than ten seconds between the two calls and the intro has finished by the time the panel appears. If there's no tool that shows panes, just open the tab.
- **Open it with `run_in_terminal`**: run `node <run dir>/watch.mjs --run <run_id>`, titled "<model>: <short title>". Discussions and reviews are always in the plan's group, so open a single tab: `node <run dir>/watch.mjs --group <name>`, titled "Discussion: <short title>" or "Review: <short title>"; the group view puts the Claude Code seat first (seat 0) and shows its report's conclusion like any other seat's. A group of parallel hands-on parts is also `--group <name>`, titled "Run: <short title>". The run directory defaults to `~/.claude/foreman/runs`, written as `C:\Users\<username>\.claude\foreman\runs` on Windows; go by the `config` output. The script generates this launcher so that `run_in_terminal`'s ASCII-only rule is met even when the plugin path has non-ASCII characters. If `watch_launcher_ascii` is `false` in the `config` output (the run directory path has non-ASCII characters), `run_in_terminal` will refuse the command: send the user the command in a code block instead, ask them to run it in their own terminal, and pass on the fix from `watch.fix` in the `check` output.
- The run_id is in the first line of the background output ("run dir …/<run_id>"). Without `--run`, watch follows whichever run is in progress, but other sessions may be running tasks too, so pass it when you can.
- Once the tab is open, call the tool that shows panes again with `pane` set to `terminal` and `tab_id` set to the tab_id you just got, so the panel stays on that tab (this brings it back if the user switched the panel away in the meantime or another panel covers it). Then send the user the tab link `[<title>](#terminal/<tab_id>)`.
- **If `run_in_terminal` isn't available** (for example in the Claude Code CLI), send the user the full watch command in a bash code block and ask them to run it in another terminal.
- When the run ends, the live view stays on screen: the user can scroll through the whole record and, in a group view, open a seat by its number; after they press q the record stays in the tab to look back at. Don't close the tab. On a resume: a group view (`--group`) follows every run in the group to its latest round by itself, so resuming a run in a group needs no new tab; a discussion's next round is in the same group tab too, and only when you want that round on its own open another `--group <name>`, titled "Discussion: <short title> (round N)". Resuming a single run outside a group opens a new tab with the new run_id `resume` prints; the old single-run tab shows that the run was continued and can follow it with n. The terminal panel holds at most 6 tabs: when it's full, close the oldest live-view tab that has finished before opening a new one.
- The default view is concise. Add `--verbose` when the user wants every detail.

## The web board
When a handoff command (`run`, `resume`, `discuss`, `review`, `image`) starts, it prints two lines right after its first line:
- `foreman: web board <url>`: this conversation's board address. If the board server isn't running, the handoff command starts it first, so normally this line is always there.
- `foreman: tell the user (…): Handed off: gpt-6-astra low · Codex CLI, level simple · [web board](<url>)`: a ready-made sentence whose model, effort and level match the first line; a resume says "Resumed", and an image task gives the cell and route.

**On every handoff**, write the sentence after the colon in your reply text. Not only the first handoff after a user message: one made after waking up on a completion notice, a rework resume and a discussion's next round get it too; for several runs handed off together, make it one sentence (with each one's model and level) and the link once; whom you picked and why can follow it. Write that sentence in the body of your reply; the user can't see it in your thinking. The same goes when you keep working in the same turn after the handoff: write the sentence as reply text before your next tool call. A plugin hook also shows the link right before the handoff command runs, but the desktop app folds it into the tool calls where it's easy to miss, so it doesn't replace yours.

**While runs are still going**, end the reply text of every turn with `[web board](<url>)` on a line of its own: the turn that handed off (even if the "Handed off" sentence came earlier), turns that report progress after a completion notice while other runs haven't finished, and turns where the user asks about something else in the meantime. The user reads the latest message; a link last given many turns ago means scrolling back for it. The final report, once everything has finished, ends with that line too (the board shows each seat's usage and cost). You don't have to look back for the address: the result JSON a handoff command prints when it ends, and the output of `status --run` and `status --plan`, carry `board_url` (only while the board is on and its server is running); without it, run `board` as below.

When a turn ends, a plugin hook checks whether this conversation started a run during it (recognised from the command; a handoff command also leaves a time mark for this conversation as soon as it runs, so any way of writing the command counts, queued ones included) and whether the reply text has a board link; if not, it stops the turn so you add one. When that happens, add the sentence as asked, without explaining it to the user.

When the user config has `dispatch.watch.web_open` set to `true`, the first handoff of each conversation makes the script open the board in the default browser by itself, and the output has one more line, "opened the web board in the default browser". Mention after the "Handed off" sentence that the board is open; write the link all the same (the user can reopen it after closing the tab). The switch is off by default and is the user's choice: don't suggest it on your own.

When those two lines are missing and the output says the web board isn't ready yet (the board server couldn't start), and when the user asks where the board is, says they didn't see the link, or asks you for it, run `node "<script path>" board` and read its JSON:
- `enabled` is `true`: send the user the `url` as a link, for example `[web board](<url>)`, saying it opens in their default browser, straight into this conversation's board; zooming out shows every conversation on this computer. **Don't open it with any browser tool** (neither the app's browser pane nor Claude in Chrome); the user clicks the link. With `web_open` on, it is the script that opens it, as the user set; you still don't use a browser tool.
- `enabled` is `false`: just say "The web board is off", optionally adding that `/foreman-en:setup` or setting `dispatch.watch.web` to `true` in the config turns it on.
- One board server is shared by every conversation on this computer: `board` reuses it when it's already running (`started` is `false`) and starts one in the background only when it isn't. If the command fails, pass on the error; the handed-off work isn't affected. The server exits by itself after 30 minutes with nobody watching and no task running, and when the plugin is removed or updated; when the user wants it closed now, run `board --stop`.
- The board is live only. When the user wants a finished conversation played back in time to look into a problem, use `board --replay <conversation id, run_id, group or all> [--speed <N>] [--maxgap <sec>]`. It starts a separate, temporary replay server; send its `url` as a link the same way. When the records are too large (over 256 MB) or the target isn't found, pass the error on as it is. Don't use it when handing off work.
