The user wants an agent to review something. Arguments:

$ARGUMENTS

Follow "5. Review" in the `foreman-en:dispatch` skill (load it first if it isn't loaded). The user asked for it, so skip the level 0 check:

1. Decide the working directory and what to review (`--target`): if the user gave one, use it. Otherwise pick by what's under review: `diff` for code changes (uncommitted changes by default; use `--base` or `--commit` if given); `files` for files that haven't changed or a design document already written; `claims` for conclusions and their evidence; `visual` for screenshots, playback files and renders (only agents that can read images can take it). For anything but `diff`, list the files to review with `--file`; in a folder that isn't a git repository, review existing files with `files`.
2. **Always write a review brief** and pass it with `--brief`: where the material came from and what it's for, the kinds of risk, known facts (failure logs, reproduction steps, problems the user reported), and any focus given in the arguments; a specific diagnosis Claude Code hasn't confirmed stays out of the brief and goes into its own report; for `claims`, list the conclusions one by one, each with where its evidence is and the key numbers. When Codex reviews a `diff`, only a brief (or `--file`) gets a structured report that follows the review rules; without one, Codex's built-in review runs instead and returns English text.
3. Pick the level: if the user gave `--level`, use it; otherwise pick `--level` from levels 1–3 by the skill's review criteria (`--level` is always needed); add any `--effort` or `--model` the user gave. Pick reviewers from `resolved_modules.review.<level>` per "When a cell has several candidates" in the skill; if the user named an agent, use it (it must be one of the cell's candidates). However many reviewers you pick, create a plan with `plan` first, putting the target, `--file` and range options on the plan. Next write your own list of issues per "The Claude Code seat" in the skill and record it with `cli.mjs submit` (add `--author` when the changes are Claude Code's own), then start one `review --plan <plan_id> --seat <n> --brief …` per external seat. Run `cli.mjs review` in the background, tell the user in the chat which model and effort it uses (taken from the first line the script prints), then open the live view as in the skill's "Live view"; when an API agent reviews, also start the queue check `await-busy` in the background.
4. When the results are in, merge the seats' `report.findings` (or `last_message` when there's no `report`) with the Claude Code seat's own list and check each issue: list the real ones and how you plan to fix them; for false positives, say why they don't hold. Once checked, record each seat's verdict on every finding with `judge`, the Claude Code seat's included (see "After the review" in the skill). Tell the user when a result is marked `stale`, its `verdict` is `incomplete`, or a reviewer wrote files it shouldn't have (`readonly_violation`). The user only asked for a review, so ask before fixing, unless they've already said to fix them. If the reviewer is the same model as the one that made what's under review, say so in the report.
