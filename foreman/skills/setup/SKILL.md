用户要设置 foreman。参数：

$ARGUMENTS

脚本路径是 `${CLAUDE_PLUGIN_ROOT}/skills/dispatch/scripts/cli.mjs`。配置的写法见 `${CLAUDE_PLUGIN_ROOT}/skills/dispatch/references/config.md`，动手改配置前先读它。

**怎么问用户**（本说明里所有"问"都照这几条）：
- 用主持方自己的提问方式，Claude Code 里是弹窗（AskUserQuestion）；没有提问工具时，在正文里列出问题和选项，等用户回答。
- 每个问题单独看也要看得懂：用户在弹窗里不一定看得到前面的正文，所以问题里写出对象、现在是什么、推荐什么，不写"上面的建议""第 3 项"这种要回头找的说法（编号可以附在后面）。
- 每个选项写一句含义和后果：选了会发生什么、要不要用户自己再做什么。推荐的放第一个，标"（推荐）"。
- 能一起问的合成一次问（一次最多 4 个问题），不要一项一项弹。
- 有安全默认值、不需要用户拍板的不问，照默认做，在 ⑥ 里说明。

## 输出结构
回复固定分成下面六段，每段用二级标题，标题照抄。①②③ 由脚本排好，**原样贴出，不改写、不删行、不重排**；④⑥ 由 Claude 按本说明的格式写。确认弹窗只在 ④ 之后弹一次，让用户先看完前面的全部内容。

| 段 | 标题 | 内容来源 |
|---|---|---|
| ① | `## ① 环境` | `check --format md` 输出的"环境"部分 |
| ② | `## ② 本机能配置的模型` | `models --format md` 的输出 |
| ③ | `## ③ 当前配置` | `check --format md` 输出的"总配置"部分 |
| ④ | `## ④ 修改建议` | Claude 写：两张编号表 |
| ⑤ | （弹窗） | 按上面"怎么问用户"问 |
| ⑥ | `## ⑥ 结果` | Claude 写：备份位置、改动表、检查结果、总结 |

贴脚本输出时，把脚本自己的一级、二级标题换成上表的标题，其余照抄。参数里写了只做某一部分时，④ 只给这一部分的建议，其余各段照常给全。

## 步骤

1. **检查环境**：运行 `node "<脚本路径>" config --cwd "<当前项目目录>"`（JSON，供下面判断用）和 `node "<脚本路径>" check --cwd "<当前项目目录>" --format md`。两条都带 `--cwd`，这样 ③ 和 ④ 看到的是同一份在这个项目里生效的配置。
   - 下面说的"配置文件"一律指 config 输出的 `user_config`（用户可能用 `FOREMAN_CONFIG` 指定了别的路径），`agent-aliases.json` 是它同一目录下的那个。
   - 把 check 输出的环境部分贴成 ①。
   - Node.js 不通过时插件用不了：贴出 ①，转告修法后结束。Git 不通过时可以继续，改动追踪用不了。实时查看不通过只影响桌面版终端面板里自动打开实时进度，可以继续。① 的表里还有"内存"和"网页看板"两行，网页看板开着而内存偏低时会多一条 ⚠ 提醒；要不要放进 ④ 见"推荐原则"里网页看板一条。Codex 沙箱不通过时，派给它的任务会全部失败：修法由用户选，并放进 ④。
   - 两条命令里任何一条输出了"首次使用，已生成配置文件"时（只有先跑的那条会打印），在 ① 后面用一两句话转告它检测到了什么、生成了什么。
   - 两条命令里任何一条打印过"已在配置文件 … 里写明审查每一级要不要补漏席"时，在 ① 后面用一句话转告：补漏席现在可以按等级开关，已按原来的做法写入（只有 3 级审查做补漏轮），备份在哪里。
   - 两条命令里任何一条打印过"已在配置文件 … 里写明讨论和审查每一级的外部席位数"时，在 ① 后面用一句话转告补写了什么、备份在哪里。
   - 两条命令里任何一条打印过"已把 … levels 改写成 modules"时，在 ① 后面用一句话说明，并按下面"推荐原则"里的旧名单规则放进 ④。
   - 两条命令里任何一条打印过"已把配置文件 … 的 modules 改成按场景写"时，在 ① 后面用一句话转告：原来的内容原样放进了 `modules.default`，用起来和以前一样；想按场景配时在 `modules` 下加场景块；原文件备份在哪里。这份备份会出现在旧备份的提醒里，按第 5 步的旧备份规则处理。补漏和按场景写这两条同时出现、备份是同一个文件时，合成一句转告。
   - `summary.warnings` 里有 `project_modules_flat` 或 `project_ignored_keys` 时（这次 `--cwd` 的项目配置有问题），在 ① 后面用一句话转告是哪个文件、什么问题，并按第 5 步放进 ④。
   - `summary.warnings` 里有 `config_rewrite_failed` 时（配置文件需要改写成新写法，这次没改成），在 ① 后面用一句话转告原因（条目的 `message`）：这次在内存里按新写法读，用起来不受影响，文件没改；原因是改写锁超时时，请用户照提示确认没有别的 foreman 在改配置、删掉锁文件后重新运行 `/foreman:setup`。
   - 两条命令里任何一条打印过"这个项目的偏好 … 没有定义场景 …"时，在 ① 后面用一句话转告：这些场景在这个项目里不生效，是项目偏好的场景块决定的。
   - 记下 config 输出的 `model_notes`（模型特长文档 models.md 的状态），第 5 步和第 8 步要用。`summary.warnings` 里的 `models_doc_missing` 不用在 ① 后面转告，第 8 步会生成这份文档。
   - 记下第 8 步"可以自己改的文件"要用的路径：`user_config`（用户配置），`preferences` 里的两项（第一项是用户偏好，第二项是这个项目的偏好，`exists` 说明文件在不在），`project_config.path`（这个项目的配置；没有项目配置时 `project_config` 为 `null`，路径按 `<当前项目目录>/.claude/foreman.json` 写），`model_notes.file`（模型特长文档）。

   - 再运行 `node "<脚本路径>" layout --cwd "<当前项目目录>" --check`（JSON，只读），记下 `one_line` 为 `false` 的文件，按第 5 步放进 ④。

2. **读模型清单**：运行 `node "<脚本路径>" models --format md`，贴成 ②。再运行一次不带 `--format` 的 `models`（JSON），从 `agents.<代号>` 读出配置里的模型在不在清单里：`listed` 为 `false` 说明模型名写错了或已经下线，`closest` 是最接近的写法，放进 ④。
   - 用户要的 opencode 或 pi 模型不在 ② 里：② 末尾已经写了怎么登录，不用再说。
   - pi 遇到模型不支持的档位不报错，会悄悄换一档，所以推理强度只从 ② 里列出的档位里选。
   - agy 的协作方 `model` 写模型族（比如 `gemini-3.8-flash`），档位写在格子的 `effort` 里，只从 ② 里这个模型列出的档位里选；没有档位的不写。

3. **新加 API 模型时查文档**：只在用户要新加 API 模型，或者要把还没放进任何格子的 API 协作方放进格子时做。已经在用的 API 协作方沿用现在的推理强度，不再查。
   - 用网页搜索查厂商的**官方文档**（厂商自己的域名），不用第三方文章。查清：模型名、OpenAI 兼容接口的地址（`base_url`）、是否接受 `reasoning_effort`、可选值有哪些。
   - 只有思考开关、没有强度参数的模型，推理强度写 `null`（比如小米 MiMo）。查不到就写 `null`，告诉用户用的是模型默认设置。
   - 模型名再和 ② 的 API 表核对一遍。④ 里附上文档链接。

4. **当前配置**：把第 1 步 check 输出的总配置部分贴成 ③。

5. **修改建议**：写成 ④。先一句话概括（比如"现在的安排基本不用动，有 3 项建议"），然后是两张表，编号从 1 起连续编，方便用户说"第 3 项改成 …"。没有内容的表不出，写一句"没有"。
   - **这一版的新东西**：第 1 步的 `model_notes.exists` 为 `false` 时（还没有模型特长文档，多半是第一次设置，或者刚升级到这一版），在概括后面、两张表前面加这一小节，按下面"这一版的新东西"逐条写一行：是什么、要不要你做什么。用户已经在用的不用再讲（比如配置里已经有 CodeBuddy 协作方，就跳过 CodeBuddy 那条）。
   - **这几项是什么意思**：两张表后面加这一小节，表里每出现一类对象（暂停确认、场景模式、run 格子里的主持方、网页看板、补漏席、必选、席位数、执行权限、上网……），按下面"重要选项的说明"写一两句：它管什么、推荐的做法会带来什么变化。同一类只写一次；旧备份、旧代号这种看名字就懂的不写。
   - **格子和协作方**：列是"# | 对象 | 现在 | 推荐 | 理由"。对象写格子（"讨论 complex"）或协作方代号；推荐写候选（协作方、模型、推理强度）和是否必选；理由一句话，用到新模型时写出它能选的推理强度和来源（② 的哪张表，或文档链接）。新加协作方、改模型名、没用上的协作方（问放进哪一格还是删掉，用户不在意就保留）、新加 API 时 key 怎么放，都写在这张表里。表后写"其余格子不变"。
   - **旧版本留下的配置**：来自第 1 步 config 输出的 `summary.warnings` 里 kind 为 `obsolete_max_seats`、`obsolete_key_env`、`old_backups`、`legacy_levels_note`、`stale_alias`、`obsolete_projects`、`project_modules_flat`、`project_ignored_keys` 的条目（文件名等细节在这些条目的字段里，③ 只有提醒的文字）。列是"# | 位置 | 内容 | 推荐 | 理由"。推荐：
     - `dispatch.max_seats`：删除。
     - `api_key_env`（和 `api_key` 同时写了）：删除；用户想改用环境变量时，删的是 `api_key`。
     - 旧备份：删除，只留这次新建的备份；`contain_keys` 为 `true` 时在理由里说明备份里有明文 key。
     - `levels` 说明行：保留。理由：旧版插件读到它会报错停下，而不是悄悄改成全由 Claude Code 做；确认每台电脑都升级以后才可以删。
     - 用户配置里的 `projects`（`obsolete_projects`）：每一项列一条，推荐"搬到 `<目录>/.claude/foreman.json`"，要写的内容取这条提醒的 `entries`（已经换成项目配置的写法、去掉了项目配置不认的字段；`dropped` 列出丢掉了哪些，写进理由），不要去读用户配置原文。目录不存在的推荐删除；目标文件已经存在的，在推荐里写出合并后的内容（`projects` 这一项写的格子和时长覆盖原文件里同名的），理由写"`projects` 已经不用了，写在里面不生效"。
     - 项目配置还是平铺写法（`project_modules_flat`）：推荐"改成 `{ "modules": { "default": { … } } }` 写法，内容不变"，"内容"一栏写出它覆盖了哪些格子和时长（config 输出的 `project_config.cells`）。理由写：旧写法照样能读；但从 1.2 及更早的版本升级来的项目配置，现在是覆盖用户配置，不再只能收紧，里面以前会被忽略的放宽项（加候选、调高席位、延长时长）现在会生效，请核对。
     - 项目配置写了只能放在用户配置里的键（`project_ignored_keys`）：推荐删掉这些键，理由写"只能写在用户配置里，项目配置里不生效"。
     - 配置文件不是一项一行的写法（第 1 步 `layout --check` 里 `one_line` 为 `false` 的文件）：每个文件列一条，推荐"改成一项一行的写法（内容不变）"，理由写"每个候选一行、席位和补漏各一行，读起来省事；改之前先备份，写完读回来逐项比对"。
     - 失效的旧代号（`stale_alias`）：改成哪个现在的代号，选和它同一家、同一种接入方式的，拿不准就列出候选让用户选；不再续接升级前的任务时也可以删掉这条。

6. **确认（弹窗）**：①到④都贴完以后问一次。④ 里没有要改或要删的项（全是"保持现状"）时不问，直接到第 8 步。问题写成"foreman 设置：按推荐修改这 N 项吗？"（N 是要改或要删的项数），选项：
   - "按推荐改（推荐）"：描述逐项写出要改和要删的项，每项写编号和一句话的内容，比如"1 讨论 complex 加 deepseek-flash；2 网页看板打开；4–6 删 3 份旧备份"，最后写"其余保持现状"；
   - "逐项调整"：描述写"接下来逐项问你，每项给出推荐和其他做法；也可以直接回复编号和改法，比如'第 1 项改成 …''第 5 项不删'"；
   - "先不改"：描述写"这次不改配置；照样生成或补全模型特长文档，并列出可以自己改的文件"。
   - **附带的确认放进同一个弹窗**：④ 的推荐里有新加 `agy cli` 协作方时，弹窗之前先运行 `node "<脚本路径>" agy-guard status`（只读），需要装守卫时把下面"agy 守卫的同意"作为同一个弹窗的第二个问题；推荐里有给 opencode、pi、agy 或 CodeBuddy 写 `run_access: "shell"` 时，再加一个问题"<协作方> 的 shell 档没有系统沙箱，命令以你的账户权限运行、能访问整台机器，接受吗？"，选项"接受，用 shell 档"、"改用 edit 档（只改项目里的文件，不运行命令）"、"不让它做执行"。主问题选了"先不改"时，附带的问题作废。
   - 选"逐项调整"：只问推荐要改或要删的项，推荐"保持现状"的不问（用户想改可以在"其他"里写）。每个问题写成"<对象>：现在 <现状>，推荐 <推荐>，怎么改？"，选项第一个是推荐的做法（标"（推荐）"），接着一两个可行的其他做法（推理强度只给 ② 里有的档位），最后是"保持现状"；每个选项的描述按下面"重要选项的说明"写含义和后果。一次最多 4 个问题，分几次问完；超过 8 项时先问前 8 项，其余请用户直接回复编号和改法。用户改了某一项后，和它相关的建议跟着重新给（比如换了模型，推理强度要从新模型的档位里选）。
   - 选"先不改"：跳到第 8 步，只写模型特长文档、可以自己改的文件和总结。
   - **agy 守卫的同意**：确认的结果里要新加 `agy cli` 协作方、`agy-guard status` 的 `installed` 为 `false` 时问（能和上面的确认合在同一个弹窗里就合；`installed` 为 `true`、只是 `valid` 为 `false` 时，多半是插件升级后守卫文件旧了：写完配置后的 check 会自动换成新版，不用问；check 仍报守卫没装或不完整时再这样问）"要在 ~/.gemini/config/ 下安装 foreman 的 agy 守卫吗？"。描述写清：会在 agy 的全局 `hooks.json` 里加一个 `foreman-guard` 条目，并写一个启动器和守卫脚本，原来的 `hooks.json` 先备份；平时用 agy 不受影响，每次工具调用多约 0.1 秒；foreman 在某个目录里运行 agy 期间，你在同一目录里自己用 agy 会被拦下工具调用；随时可以用 `agy-guard uninstall` 撤掉。选项："同意安装（推荐）"、"不加 agy"。选"不加 agy"时，这次不加任何 `agy cli` 协作方，其余建议照改。每次运行 setup 都要重新问，不沿用以前的回答。

7. **改配置**：
   - 改写法（用户在 ④ 里同意时）：在其余改动之前运行 `node "<脚本路径>" layout --cwd "<当前项目目录>"`；它给要改的文件各建一份备份（输出里的 `backup`），这份就算这次新建的备份，下面不用再备份同一个文件。用户没同意改写法的文件，不替它改写法：`layout --cwd` 会同时改用户配置和项目配置，用户只同意改项目配置的写法时不用它，按一项一行手改项目配置（先照下面的规则备份）；只同意改用户配置的写法时，运行不带 `--cwd` 的 `layout`。
   - 先备份：这次要改配置文件时，把它复制成同目录下的 `<文件名>.setup-<年月日-时分秒>.bak`；这次要改 `agent-aliases.json` 时，也把它复制成 `agent-aliases.json.setup-<年月日-时分秒>.bak`。只删旧备份、不改这两个文件时不用备份（否则下次 setup 又会把它当成旧备份）。
   - 改用户配置的 `agents` 和 `modules`（默认的那套在 `modules.default` 里，有场景块的按用户要改的场景改），每一格写成候选列表，按一项一行写：每个候选一行，`seats`、`gap` 各一行（见 `references/config.md` 的"写法"）；`discuss` 和 `review` 的 `seats` 三级都保留在文件里，改席位数就改这里，新加必选时把对应等级调到不少于必选数。改写后文件里的 `levels` 是一行说明文字，除非用户在 ④ 里选了删除，否则保留不动。代号用模型名（opencode 和 pi 取 `/` 后面那段）；已经有同名代号时，加上类型后缀，比如 `deepseek-flash-api`、`deepseek-flash-opencode-cli`、`deepseek-flash-pi`。失效的旧代号改在 `agent-aliases.json` 里，只改或删那一条，不删整个文件：续接升级前的任务、项目配置里写的旧代号都靠它。
   - 补漏席：`review` 的 `gap` 三级都保留在文件里，按 ④ 里用户确认的结果改。
   - 场景模式（用户在 ④ 里同意开启时）：先把用户偏好文件（config 输出 `preferences` 里的第一个，即 `preferences.md`）复制成同目录下的 `preferences.md.setup-<年月日-时分秒>.bak`（文件不存在就不用备份），再写场景块：文件里已有 `<!-- foreman:scenes -->` 块时只替换块里的内容，没有就追加到文件末尾，块外面的内容一个字都不改。然后在用户配置的 `modules` 下按 ④ 里确认的内容加 `code`、`research` 两个场景块，只写和 `default` 不同的格子、`seats` 和 `gap`。写完第 7 步的 `config` 校验时，看输出的 `scenes.problems` 为空。
   - 迁移 `projects`（用户在 ④ 里同意时）：按确认的内容写各项目的 `.claude/foreman.json`（已有的先复制成 `foreman.json.setup-<年月日-时分秒>.bak`，没有 `.claude` 目录就建），再从用户配置里删掉 `projects`。写到别的仓库里的文件不会自动提交，在 ⑥ 里列出写了哪几个文件。
   - 改项目配置（用户在 ④ 里同意了 `project_modules_flat`、`project_ignored_keys` 的建议时）：先把它复制成 `foreman.json.setup-<年月日-时分秒>.bak`，再改成 `default` 写法或删掉那几个键，内容不变；同样在 ⑥ 里列出。
   - 暂停确认（用户在 ④ 里改了时）：按 `references/config.md` 的"确认节点"写 `dispatch.confirm`，默认写成那一整套，全自动写 `"auto"`，每步都问写 `"ask"`，自定义的按用户说的节点写；`dispatch` 里的其他字段不动。`confirm` 只写在用户配置里。
   - 实时查看的两个开关：用户配置 `dispatch.watch` 里的 `terminal` 和 `web` 两项都要写上。`terminal` 保持原值（插件加载时已经把旧写法改写过，一般已经写着；没有就写 `true`）；`web` 按 ④ 里用户确认的结果写 `true` 或 `false`，④ 里没有这一项就保持原值。
   - 删旧版本留下的配置：按用户确认的项删。旧备份只删 ④ 里列出的那些，不删这次新建的。
   - API key 的放法：
     - **写在配置文件里**（改完立即生效）：告诉用户打开配置文件（写出 `user_config` 的完整路径），在这个协作方里加一行 `"api_key": "<key>"`，自己填上。提醒用户 key 是明文保存的，这个文件不要提交或分享。
     - **放在环境变量里**：配置里写 `"api_key_env": "<变量名>"`，告诉用户自己设置：Windows 上在"系统属性 → 环境变量"里加一个用户变量，或者在 PowerShell 里运行 `[Environment]::SetEnvironmentVariable('<变量名>', '<key>', 'User')`；macOS 和 Linux 写进 shell 的启动文件。设置后要重启 Claude Code 才能读到。
     - **不要让用户把 key 发到对话里。** 用户已经主动发了、并明确要求写进配置时，可以写进用户配置的 `api_key`（不能写进项目配置），同时提醒用户：这个 key 已经出现在对话记录里，建议之后换一个新的。
   - 用户同意装 agy 守卫时，在写配置之前运行 `node "<脚本路径>" agy-guard install`；失败就不加 agy 协作方，把原因写进 ⑥。写完配置后的 check 如果报 agy 守卫没装或不完整，回到上面的同意弹窗重新问，不要自己直接装。
   - 运行 `config --cwd "<当前项目目录>" --keep-backup "<这次新建的配置备份>"` 校验（这次没在用户配置的目录里新建备份时，比如只改了项目配置，不带 `--keep-backup`；它只认用户配置目录里的文件）（`--keep-backup` 让这次的备份不算进旧备份的提醒）。报错时按报错修正（报错里会给出最接近的写法）；修不好就用备份恢复，告诉用户原因。
   - 再运行 `check --cwd "<当前项目目录>" --format md --keep-backup "<这次新建的配置备份>"`。不通过的项：推理强度不支持的，从 ② 里重新选，回到第 6 步问用户。环境变量方式的 key 要等用户重启后才读得到，这时报 key 没设置是正常的，请用户重启后再运行一次 `/foreman:setup`。

8. **结果**：先运行 `node "<脚本路径>" model-notes --write --host-model <系统提示里 Claude Code 自己的模型 ID>`（比如 `claude-opus-5-5`）。第 6 步选了"先不改"也运行：它只新建 models.md，或者在末尾给哪一节都对不上的模型补一节，不改用户写过的内容。然后写成 ⑥，依次是：
   - 备份位置（改了配置时）。
   - **本次改动**：列是"格子 | 协作方 | 原来 → 现在"（推理强度、必选、加入或去掉）。没改配置就不出。
   - **已删除**：列是"位置 | 内容"。没删东西就不出。
   - **模型特长文档**：写出 models.md 的完整路径（输出的 `file`），这次是新建的（`created`）还是给哪几个模型补了一节（`added`），以及还没写擅长或短处的模型（`unwritten`）。请用户按自己的使用体验补上，比如"擅长后端，但偏防御"：Claude Code 挑人、写任务说明、验收、权衡审查和讨论意见时都会参考，问题成不成立仍以核实为准。标题可以改宽或合并，比如几个 Opus 版本合成一节 `## claude-opus`；文件随时可以改，写法不限。
   - **检查结果**：第 7 步 check 全部通过、提醒里没有新的 ❌ 或 ⚠ 时，写一行"✅ 校验和检查都通过。"；否则把新出现的 ❌、⚠ 提醒行原样贴出，再写怎么处理。不再贴整张总表，最后加一句"想看改动后的完整总表可以说"。
   - **可以自己改的文件**：每次都出，列是"文件 | 位置 | 管什么 | 什么时候生效"，位置写第 1 步记下的完整路径，文件还不存在的在位置后面注明"（还没有，要用时新建）"。五行依次是：
     - 用户配置（`user_config`）：有哪些协作方，讨论、执行、审查、出图各级交给谁、派几家、谁必选，暂停确认、网页看板等开关。插件每次派活或运行命令都重新读，改完下一次就生效。写法见 README 的"配置"。
     - 项目配置（`project_config.path`）：只对这个项目生效，覆盖用户配置里同名的格子和时长；协作方、暂停确认、网页看板只能写在用户配置里。生效时间同上。写法见 README 的"项目配置"。
     - 用户偏好（`preferences` 第一项）：用平常的话写你希望的做法，比如哪类活多讨论、对某个模型的看法，还有场景路由。新开会话时自动带上；在当前会话里改了，让 Claude Code 重新读一遍。写法见 README 的"偏好文件"。
     - 项目偏好（`preferences` 第二项）：只对这个项目生效，和用户偏好冲突时以它为准；它写了场景块时，这个项目只用它的场景。生效时间同用户偏好。写法同上。
     - 模型特长文档（`model_notes.file`）：各模型擅长什么、有什么短处，Claude Code 挑人、写任务说明、验收和权衡意见时参考。生效时间同用户偏好。写法见 README 的"模型特长文档"。
     表后加一句：这些文件都可以直接用编辑器改，也可以让 Claude Code 帮你改；改之前插件不会替你备份，想留底可以先复制一份。
   - **总结**：两三句话：现在哪些能用、还有什么没弄好；平时直接让 Claude Code 做事即可：每件事按讨论、执行、审查分别定级，小事 Claude Code 自己做，达到门槛的从配置的候选里挑人交出去；也可以用 `/foreman:run`、`/foreman:discuss`、`/foreman:review` 点名。开着网页看板时再说一句：以后每次派出都会先给一个网页链接，点开在默认浏览器里看本机所有对话，不再自动打开终端实时查看；想在终端里看或者再要链接，随时用 `/foreman:watch`。这次的 `model-notes` 输出 `created` 为 `true`（第一次在这一版里设置）时，再用一句话带过这一版里不用你操作的变化，取下面"这一版的新东西"里"不用操作"那一条。

## 推荐原则
- 已有的安排默认不变。只在这几种情况推荐改：格子的模型或推理强度不在清单里；这次新装了工具，或者用户要加模型；审查、讨论的某一级是 `"claude code"`，而现在有合适的协作方；配置里还没有图像两格，而本机有能出图的协作方；讨论名单是从旧写法改写来的，还没决定谁必选；Codex 做讨论或审查时没有只读沙箱（提醒里有 `readonly_audited`）；讨论或审查某一级的候选明显少于席位数（看 ③ 的"席位与必选"，"候选不够"的格子）。执行的 simple、normal 交给 Claude Code 是默认安排，不主动改。
- **run 格子里的主持方**（混合候选，写法见 `references/config.md` 的"modules"）：第 1 步的 `model_notes.exists` 为 `false`（还没有模型特长文档，多半是刚升级或第一次设置），run 的 normal 或 complex 又是外部候选列表、里面没有主持方时，在 ④ 列一项，推荐在这几格加上 `{ "agent": "claude code" }`。理由写：插件以前固定由 Claude Code 做界面视觉定稿和给人读的文字，现在按格子和 models.md 决定；加上以后，models.md 里写明 Claude 更擅长的活由 Claude Code 自己做，其余照样派给外部候选；不加的话这几类活也会派出去。文档已经有了时不主动列，用户要加时照加。
- 这次 `--cwd` 的项目配置覆盖了的格子（config 输出的 `project_config.cells`）：③ 显示的是项目里生效的样子。按上面的规则要推荐改它们时，改的是项目配置，在推荐里写明文件；不要为了它们去改用户配置。
- **场景模式**：用户配置的 `modules` 下只有 `default`、`scenes.names` 也为空时，在 ④ 的第一张表里列一项"场景模式"。审查 complex 的候选比这一级的席位数多出两个以上时推荐开启，否则列出、推荐"不开"。推荐开启时，推荐一栏写清：
  - 写进用户偏好的场景块原文，默认两个场景 code 和 research，内容照 `references/config.md` "场景"一节的样板；
  - `modules.code`：审查 complex 只放两个强档模型（必选沿用 `default` 的），推理强度用最高的常用档，`seats` 为 2，`gap` 为 `false`；
  - `modules.research`：审查 normal 和 complex 各放 `default` 同一格的全部候选，`seats` 取候选数和上限里较小的（normal 上限 3，complex 上限 6），`gap` 都为 `true`；讨论不改（一般的研究证据审查是 2 级，所以 normal 也要配）；
  - 理由里说明：开启后，派活时先按偏好里的路由选场景，没写到的情况用 `default`；以后想让某个场景换模型、换推理强度或换必选，直接改它的场景块。
  已经有场景块时不列这一项；`scenes.problems` 不为空时，把每条问题列进 ④，推荐怎么改。
- **补漏席**（`review.gap`）：默认不改。用户问到时说明：开着的等级，各席审完后再请一个没参加过的模型只找"清单还漏了什么"，多花一席的额度；场景模式下可以只在某个场景开。
- **暂停确认**（`dispatch.auto`、`dispatch.confirm`，③ 开头那一段）：在 ④ 的第一张表里列一项"暂停确认"，现状写 ③ 里的预设名（默认、全自动、每步都问、自定义），推荐保持现状。
  - 用户选"逐项调整"时给三个候选：默认（推荐：讨论只在 3 级、审查 2 级及以上整合前问，图像路线要问，其余不问）、全自动、每步都问；想按节点自己定的，让用户写在"其他"里。
  - 用户的 `dispatch.auto` 为 `false` 又选了默认那一套时，在理由里说明：开始前的三个节点会改成不问；想保留开始前先问，就选每步都问，或者按节点自定。
  - 理由里提醒一句：同一台电脑上还有 1.2.x 的旧插件（比如桌面版里上传的旧包）时，它读不懂新写法，会报配置写法不对，先把它们都升级。
- **网页看板**（`dispatch.watch.web`，默认关）：在浏览器里用星图看本机所有对话和派发进度，开着时每次派出都先在对话里给一个网页链接，再启动任务，不再自动打开终端实时查看。另有 `dispatch.watch.web_open`（默认关）：打开后每个对话第一次派出时自动在默认浏览器里打开看板；用户问到或想要看板自动弹出来时告诉他有这一项，不主动建议。开不开网页看板按本机内存定，看 ① 的"网页看板"一行：
  - 写着"未开启（内存够用，可以开启）"：在 ④ 列一项，推荐开启。理由写本机内存（① 的"内存"一行）和占用：看板服务约 100–130 MB，浏览器标签页约 60–90 MB。
  - 写着"未开启（内存偏低，建议保持关闭）"：不用改，不列进 ④；总结里提一句本机内存偏低（总内存不到 8 GB 或可用不到 2 GB），暂不建议开网页看板。用户主动要开时照开，提醒可能变卡。
  - 写着"已开启 · 内存偏低"：推荐关闭，理由同上。
  - 已开启、内存够用：不列。
- 推理强度只从 ② 里列出的档位选，按模型的档位分两种（`config` 输出里候选的 `tier`，或者 `cli.mjs tiers --model <模型>`；未评级的按中档算）：
  - **弱档、中档模型三级都选最高档**（比如 `max`、`xhigh`；只有一档的就用那一档）。它们主要当第 1 轮独立出稿的广度席，想得深一点才更容易查出别人漏的东西；这类模型便宜，开到最高档多花得有限。价格明显偏高的弱档模型照样用最高档，但按下面的规则只放在 complex。
  - **强档模型按等级选**：simple 选偏低的一档（比如 `medium`），normal 选默认档或高一档（比如 `high`），complex 选最高的常用档（比如 `max`）。更高的档位在说明里写着明显更慢、更贵时，用户要求才推荐。
- 执行只能交给 `codex cli`，或者写了 `run_access` 的 `opencode cli` / `pi cli` / `agy cli` / `codebuddy cli`。审查优先用 Codex（能跑只读命令核实，也是目前唯一能看图、能做截图检查的），opencode、pi 和 CodeBuddy 也能审。API 能参加讨论和审查，审查时只审文本材料（补丁、文件内容），不能审截图。
- Codex 的讨论和审查推荐设只读沙箱：在 `agents.<代号>.sandbox` 里把 `review`、`discuss` 设成 `"read-only"`，系统会拦下写入（结果的只读保障是 `sandbox`）；不设时只靠规则和事后对比快照（`audited`）。Windows 上设之前看 ① 的 Codex 沙箱：只读沙箱起不来时，按 `check` 的修法在 `~/.codex/config.toml` 的 `[windows]` 里写 `sandbox = "unelevated"`。执行的沙箱不在这里改。
- 审查尽量和执行用不同的模型：同一个模型审自己写的改动，盲区会重复。能做审查的只有执行用的那个模型时，照常推荐，并在理由里说明这一点（到时 Claude Code 会在汇报里注明是同一个模型审的）。
- 同一家厂商的账号可能被 opencode、pi 和 API 共用，并发按账号算（比如有的 Moonshot 账号同时只允许 1 个请求）：同一级讨论里不要放两个用同一个受限账号的参与方。
- 每一格写的是候选，不是全员名单：讨论和审查每一级派几个外部模型由 `seats` 决定（默认值见 `references/config.md` 的"候选和必选"，实际的数和派法见 ③ 的"席位与必选"），候选少于这个数时全上。用户想多找几家或固定用哪几家时，推荐改 `seats`（固定用哪几家就把席位数设成候选数）。讨论和审查的格子可以多放几个不同厂商的候选，尽量来自不同厂商，观点更多样。同一个模型经 api、pi、opencode 接入只算一个基础模型。额度少的高档模型（比如 OpenCode Go 里的 Kimi K3、Qwen Max）只放在 complex。API 候选会收到附带的代码或补丁，提醒用户一句。
- **必选**（`"required": true`）：这一格用到时一定参加的协作方，算在席位数里。推荐给 3 级的讨论和审查各标一个最强、最可靠的模型（比如 Codex 的强档），保证关键的事至少有它在场；其余格子一般不标。执行、出图、手画一格最多一个必选。必选每次都会占用它的额度，不要标太多，也不要标额度紧的模型。
- 配置是从旧的 `levels` 写法改写来的：旧的讨论名单原来是全员参加，现在变成了候选。问用户要保留全员参加（全部标必选），还是让 Claude Code 挑、只给关键的模型标必选；推荐后者。全部标必选时，要把这一级的 `seats` 一起调到不少于必选数，否则配置读不出来。
- **图像两格**：`generate` 只能放能出图的协作方（目前只有 `codex cli`），推荐 gpt-6.1-sol、`medium`：出图质量主要看图像模型，推理强度调高只是多花额度。`draw` 放能执行的强档模型，推荐 gpt-6-astra、`max`：照定稿图描会弯的部件、写变形要反复推敲。没有 Codex 时两格写 `null`；用户不想出图时 `generate` 写 `null`，不想外派手画时 `draw` 写 `null`（由 Claude Code 自己画）。
- **agy**（`agy cli`）：能参加讨论和审查，写了 `run_access` 还能执行，目前只验证了 Windows 11。它和 Google 账号的订阅额度挂钩、按 5 小时窗口算，默认并发 2，推荐放进讨论和审查的 normal、complex 当候选，不推荐标必选。配置里已经有 agy 协作方、而 `agy-guard status` 报守卫没装，或者 check 报守卫没装、条目不完整时，放进 ④：推荐安装（同样要经上面的同意弹窗）；只是守卫文件和插件里的不一致时，check 和派出会自动换成新版，不用装。check 报项目或全局有别的 agy 钩子、MCP 或插件配置时，在理由里说明这些情况下不会派 agy，要不要处理由用户决定，插件不替用户改这些文件。
- **CodeBuddy**（`codebuddy cli`）：能参加讨论和审查，写了 `run_access` 还能执行，目前只在 Windows 11 上验证过（要装 Git for Windows）。读写由插件注入的守卫钩子限定在项目里。CodeBuddy 的用户设置（`~/.codebuddy/settings.json`）里有 `permissions.allow`、`additionalDirectories`、`hooks` 或启用的插件时，插件拒绝派出；check 报这种情况时，在理由里说明，要不要处理由用户决定，插件不替用户改这个文件。
- **不默认推荐让 opencode、pi、agy 或 CodeBuddy 做执行**。用户想要时讲清两档，用户明确同意并选好一档后才写 `run_access`：
  - `"edit"`：只能改项目里的文件，不能运行命令，测试由 Claude Code 事后跑；
  - `"shell"`：还能运行命令。opencode、pi、agy 和 CodeBuddy 做执行时都没有系统沙箱，命令以用户的账户权限运行、能访问整台机器。选这一档要请用户明确确认接受"没有系统沙箱"。

## 重要选项的说明
④ 的"这几项是什么意思"和弹窗里每个选项的描述，按这里的说法写，用平常的话，一两句讲清管什么、选了会怎样：
- **暂停确认**（`dispatch.confirm`）：Claude Code 在哪几处先停下来问你。默认那一套只在两处问：3 级讨论结束后按结论动手之前，2 级及以上的审查结束后返工之前；另外每个新的图像交付物要你选路线。全自动是哪里都不问，每步都问是讨论、执行、审查开始前和整合前都问。你点名要做的事开始前不再问。
- **场景模式**（code、research）：给不同类型的工作配不同的人选，比如代码审查只用最强的两家，研究结论的审查多找几家、留补漏席。怎么分由偏好文件里的场景路由说明，没写到的情况用默认那套。
- **run 格子里的主持方**（候选里写 `{ "agent": "claude code" }`）：模型特长文档里写明 Claude Code 的模型更擅长的活（默认是界面视觉定稿和给人读的文字），由它自己做；其余照样派给格子里的外部候选。格子里有必选的外部候选时，照常交给必选方。不写的话，这几类活也会派出去。
- **模型特长文档**（`models.md`）：你按使用体验写各模型擅长什么、有什么短处，Claude Code 挑人、写任务说明、验收、权衡意见时参考。每节的标题写模型名就行，不写接入方式，同一个模型经哪种 CLI 或 API 调用都用这一节；可以只写一部分（`claude-opus` 对得上 Opus 的各个版本），也可以用逗号并列几个模型。setup 只给哪一节都对不上的模型补一节，不改你写的内容。
- **讨论和执行能上网**：Codex、opencode、agy 和 CodeBuddy 讨论和执行时能上网查资料，审查时不能，pi 和 API 模型不能。Codex 照你 `~/.codex/config.toml` 里的 `web_search`，没写就实时搜；opencode 只能读已知网址，配了网页搜索服务才能搜；agy 能搜网页，它的浏览器要你的 Chrome 开着远程调试才用得上。网上查到的说法要附链接，Claude Code 核实后才采信。
- **执行权限**（`run_access`）：opencode、pi、agy、CodeBuddy 默认不做执行。`"edit"` 只能改项目里的文件、不能运行命令，测试由 Claude Code 事后跑；`"shell"` 还能运行命令，但没有系统沙箱，命令以你的账户权限运行、能访问整台机器。Codex 做执行时用它自己的沙箱，不靠这一项。
- **必选**：这一格用到时一定参加，算在席位数里；它失败或额度用完时这件事算不完整，不拿别人顶替。
- **席位数**（`seats`）：讨论和审查每一级派几家外部模型。格子里写的是候选，候选比席位多时由 Claude Code 挑，少时全上。
- **补漏席**（`gap`）：各席审完后，再请一个没参加过的模型只找"清单还漏了什么"，多花一席的额度。
- **网页看板**：在浏览器里看本机所有对话和派发进度，开着时每次派出都先给一个网页链接，不再自动打开终端实时查看。服务约占 100–130 MB 内存，浏览器标签页约 60–90 MB。

## 这一版的新东西
④ 的"这一版的新东西"按这里逐条写一行（1.3.0）：
- **暂停确认**：默认会在 3 级讨论和 2 级及以上审查结束后先问你，再按结论动手。不用操作；想换成全自动或每步都问，在 ④ 里改。
- **模型特长文档**：这次 setup 会生成 `models.md`，请你之后补上各模型的擅长和短处。
- **run 格子里可以写主持方**：界面视觉定稿和给人读的文字不再固定由 Claude Code 做，改按 run 的格子和模型特长文档决定。④ 推荐把 `claude code` 加进格子时，要你决定。
- **讨论和执行能上网**：Codex 自动生效。想让 opencode 搜网页，要在 opencode 里配网页搜索服务；想让 agy 用浏览器，要在 Chrome 里开远程调试（`chrome://inspect/#remote-debugging`）。审查不上网。
- **agy 可以做执行**：要你同意并选好 `edit` 或 `shell` 才开，默认不开。
- **CodeBuddy 协作方**：装了 CodeBuddy CLI 才用得上，Windows 上还要装 Git for Windows。
- **不用操作**：opencode 每次运行换一个随机的代理名，你自己的 opencode 配置盖不掉插件给它的只读和写入限制；opencode 的 edit 档不再执行项目配置里的格式化命令；opencode 做执行时，不能经由项目里的链接写文件，也不能写受保护的目录（`.git`、`.claude`、`.opencode` 等）、Git 实际用的目录和项目里登记的工作树，要改链接指向的文件就用真实路径；Windows 上 agy 讨论和审查不跑命令，也不再做几分钟的沙箱检测；审查的改动量只算产品代码；网页看板在 Retina 屏和低配机器上更省资源。

## 特殊情况
**只有 API、没有 Codex、opencode、pi 和 CodeBuddy 时**：在 ④ 前面说明，执行只能由 Claude Code 自己做，讨论和审查可以交给 API（审查只审文本材料，不能看截图）；想让外部模型干活，需要装 Codex、opencode、pi 或 CodeBuddy；看图目前只有 Codex。

**什么都没有时**：只给 ①，然后说明插件现在由 Claude Code 自己完成所有工作。想接入外部模型，可以装 Codex CLI（`npm install -g @openai/codex`，再运行 `codex login`）、装 opencode（`npm install -g @opencode/cli`）、装 pi（`npm install -g @earendil-works/pi-coding-agent`）、装 CodeBuddy（`npm install -g @tencent-ai/codebuddy-code`），或者准备一个 API key。装好后再运行一次 `/foreman:setup`。
