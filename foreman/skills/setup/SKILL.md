用户要设置 foreman。参数：

$ARGUMENTS

脚本路径是 `${CLAUDE_PLUGIN_ROOT}/skills/dispatch/scripts/cli.mjs`。配置的写法见 `${CLAUDE_PLUGIN_ROOT}/skills/dispatch/references/config.md`，动手改配置前先读它。按下面的顺序进行，每一步用简短的中文告诉用户结果。参数里写了只做某一部分时，第 4 步只给这一部分的推荐，其余步骤照做。

1. **检查环境**：运行 `node "<脚本路径>" check` 和 `node "<脚本路径>" config --cwd "<当前项目目录>"`。
   - 用一张表说明本机有什么，来自 `config` 的 `environment`：Codex 有没有、登录没有；opencode 和 pi 各有没有、几个可用模型；检测到哪些 API key 环境变量。
   - Node.js 不通过时插件用不了，转告 `fix` 后结束。Git 不通过时，告诉用户改动追踪用不了、建议安装，但可以继续。实时查看（`watch`）不通过只影响桌面版终端面板里自动打开实时进度，可以继续。Codex 的 `sandbox` 有不通过的，说明它的沙箱在这台电脑上起不来，派给它的任务会全部失败：转告 `fix` 里的几种修法，由用户选，第 4 步的推荐里也带上这一项。
   - 脚本输出了"首次使用，已生成配置文件"时，转告它检测到了什么、生成了什么。
   - 这一步不贴每个协作方的检查结果，留到第 7 步的总表里一起说。

2. **读模型清单**：运行 `node "<脚本路径>" models`（只读，不发模型请求）。
   - `tools."codex cli"`、`tools."opencode cli"`、`tools."pi cli"`：本机工具自带的模型清单，每个模型有 `efforts`（支持的推理强度）、`default_effort`、`context`，opencode 和 pi 还有 `cost`（每百万 token 的美元价格）。`ok` 为 `false` 时说明读不到的原因（比如没装、没登录），这个工具的推荐就跳过。
   - `api.<代号>`：每个 API 协作方的接口列出的模型名。这份清单没有推理强度。
   - `agents.<代号>`：配置里每个协作方的模型在不在清单里（`listed`）。为 `false` 的说明模型名写错了或已经下线，`closest` 是最接近的写法，放进第 4 步的推荐。
   - 给用户看可选的模型：
     - Codex：不列 `hidden` 为 `true` 的。每个模型一行：名称、支持的推理强度（标出默认档）、上下文长度。
     - opencode：只列 `enabled` 不为 `false` 的，按提供方分组，写支持的 variant、上下文和价格（价格为 0 写"免费"）。`efforts` 为空的模型没有可选档位，推理强度只能不写。模型很多时只列推荐里用到的和用户问到的，再说一句"还有 N 个，想看全部可以说"。
     - pi：按提供方分组，写支持的推理强度、上下文和价格。pi 遇到模型不支持的档位不报错，会悄悄换一档，所以推理强度只从这里列出的档位里选。
     - 要的 pi 模型不在清单里时，请用户自己在终端运行 `pi`，在里面用 `/login` 登录那家厂商（或者设置它的 API key 环境变量），再运行一次 `models`。
     - 要的 opencode 模型不在清单里时，请用户自己在终端运行 `opencode`，在里面用 `/connect` 登录（OpenCode Go 选 OpenCode Go），登录后再运行一次 `models`。

3. **新加 API 模型时查文档**：只在用户要新加 API 模型，或者要把自动生成、还没放进任何格子的 API 协作方放进格子时做。已经在用的 API 协作方沿用现在的推理强度，不再查。
   - 用网页搜索查厂商的**官方文档**（厂商自己的域名），不用第三方文章。查清：模型名、OpenAI 兼容接口的地址（`base_url`）、是否接受 `reasoning_effort`、可选值有哪些。
   - 只有思考开关、没有强度参数的模型，推理强度写 `null`（比如小米 MiMo）。查不到就写 `null`，告诉用户用的是模型默认设置。
   - 模型名再和第 2 步 `api` 里列出的核对一遍。第 4 步的推荐里附上文档链接。

4. **一次给出完整推荐**：把下面三块一起给出来，每一项编号，方便用户说"第 3 项改成 …"。
   - **格子表**：讨论、执行、审查各三级，加上图像的出图（generate）和手画（draw）两格。每格写"现在"和"推荐"，推荐里写候选（协作方、模型、推理强度）、哪些标必选，以及一句理由；不改的格子写"不变"。每个用到的模型旁边写出它能选的推理强度和来源（Codex 清单、opencode 清单、pi 清单或文档链接）。
   - **协作方的增删改**：要新加的（代号、类型、模型）、模型名要改的、没用在任何格子里的（问放进哪一格还是删掉，用户不在意就保留）。
   - **其他**：总表提醒里失效的旧代号（`stale_alias`）推荐改成哪个现在的代号，选和它同一家、同一种接入方式的，拿不准就列出候选让用户选，或者删掉这条（不再续接升级前的任务时）；新加 API 时 key 怎么放。

   推荐按这些原则：
   - 已有的安排默认不变。只在这几种情况推荐改：格子的模型或推理强度不在清单里；这次新装了工具，或者用户要加模型；审查、讨论的某一级是 `"claude code"`，而现在有合适的协作方；配置里还没有图像两格，而本机有能出图的协作方；讨论名单是从旧写法改写来的，还没决定谁必选；Codex 做讨论或审查时没有只读沙箱（`summary.warnings` 里有 `readonly_audited`）。执行的 simple、normal 交给 Claude 是默认安排，不主动改。
   - 推理强度只从清单支持的档位里选，按模型在 `references/model-tiers.md` 里的档位分两种（表里查不到的按中档算）：
     - **弱档、中档模型三级都选清单里的最高档**（比如 `max`、`xhigh`；只有一档的就用那一档）。它们主要当第 1 轮独立出稿的广度席，想得深一点才更容易查出别人漏的东西；这类模型便宜，开到最高档多花得有限。价格明显偏高的弱档模型照样用最高档，但按下面的规则只放在 complex。
     - **强档模型按等级选**：simple 选偏低的一档（比如 `medium`），normal 选默认档或高一档（比如 `high`），complex 选最高的常用档（比如 `max`）。更高的档位在说明里写着明显更慢、更贵时，用户要求才推荐。
   - 执行只能交给 `codex cli`，或者写了 `run_access` 的 `opencode cli` / `pi cli`。审查优先用 Codex（能跑只读命令核实，也是目前唯一能看图、能做截图检查的），opencode 和 pi 也能审。API 能参加讨论和审查，审查时只审文本材料（补丁、文件内容），不能审截图。
   - Codex 的讨论和审查推荐设只读沙箱：在 `agents.<代号>.sandbox` 里把 `review`、`discuss` 设成 `"read-only"`，系统会拦下写入（结果的只读保障是 `sandbox`）；不设时只靠规则和事后对比快照（`audited`）。Windows 上设之前看第 6 步的 `check`：只读沙箱起不来时，按它的 `fix` 在 `~/.codex/config.toml` 的 `[windows]` 里写 `sandbox = "unelevated"`。执行的沙箱不在这里改。
   - 审查尽量和执行用不同的模型：同一个模型审自己写的改动，盲区会重复。能做审查的只有执行用的那个模型时，照常推荐，并在理由里说明这一点（到时 Claude 会在汇报里注明是同一个模型审的）。
   - 同一家厂商的账号可能被 opencode、pi 和 API 共用，并发按账号算（比如有的 Moonshot 账号同时只允许 1 个请求）：同一级讨论里不要放两个用同一个受限账号的参与方。
   - 每一格写的是候选，不是全员名单：用到这一格时，Claude 每次从候选里挑，讨论和审查默认 1 级 1 席、2 级 2 席、3 级 3 席，按不同的基础模型补；证据审查和 3 级的高风险审查用这一格里所有不同的基础模型（不超过 `dispatch.max_seats`，默认 6）。所以讨论和审查的格子可以多放几个不同厂商的候选：simple 一个候选或不找外部模型；normal 两三个；complex 三到五个，尽量来自不同厂商，观点更多样。同一个模型经 api、pi、opencode 接入只算一个基础模型。额度少的高档模型（比如 OpenCode Go 里的 Kimi K3、Qwen Max）只放在 complex。API 候选会收到附带的代码或补丁，提醒用户一句。
   - **必选**（`"required": true`）：这一格用到时一定参加的协作方。推荐给 3 级的讨论和审查各标一个最强、最可靠的模型（比如 Codex 的强档），保证关键的事至少有它在场；其余格子一般不标。执行、出图、手画一格最多一个必选。必选每次都会占用它的额度，不要标太多，也不要标额度紧的模型。
   - 配置是从旧的 `levels` 写法改写来的（`config` 打印过"已把 … levels 改写成 modules"）：旧的讨论名单原来是全员参加，现在变成了候选。问用户要保留全员参加（全部标必选），还是让 Claude 挑、只给关键的模型标必选；推荐后者。
   - **图像两格**：`generate` 只能放能出图的协作方（目前只有 `codex cli`），推荐 gpt-6.1-sol、`medium`：出图质量主要看图像模型，推理强度调高只是多花额度。`draw` 放能执行的强档模型，推荐 gpt-6-astra、`max`：照定稿图描会弯的部件、写变形要反复推敲。没有 Codex 时两格写 `null`；用户不想出图时 `generate` 写 `null`，不想外派手画时 `draw` 写 `null`（由 Claude 自己画）。
   - **不默认推荐让 opencode 或 pi 做执行**。用户想要时讲清两档，用户明确同意并选好一档后才写 `run_access`：
     - `"edit"`：只能改项目里的文件，不能运行命令，测试由 Claude 事后跑；
     - `"shell"`：还能运行命令。opencode 和 pi 都没有系统沙箱，命令以用户的账户权限运行、能访问整台机器。选这一档要请用户明确确认接受"没有系统沙箱"。

5. **用户逐项调整**：用 AskUserQuestion 问"按推荐改"（推荐项放第一个）、"逐项调整"、"先不改"。
   - 选"逐项调整"：再问要调整哪几项（项目多于 4 个时请用户直接回复编号和改法），然后每项给出候选（推荐的放第一个，推理强度只给清单里有的档位），一次最多问 4 项。
   - 用户改了某一项后，和它相关的推荐跟着重新给（比如换了模型，推理强度要从新模型的清单里选）。
   - 选"先不改"：跳到第 7 步，只给总配置情况。

6. **改配置并确认**：
   - 先备份：把 `~/.claude/foreman/config.json` 复制成同目录下的 `config.json.setup-<年月日-时分秒>.bak`，告诉用户备份在哪里。
   - 改用户配置的 `agents` 和 `modules`，每一格写成候选列表。配置文件还是旧的 `levels` 写法时，第 1 步运行 `config` 时脚本已经把它改写成 `modules` 了，直接在新写法上改；改写后文件里的 `levels` 是一行说明文字（让旧版插件报错用的），保留不动。代号用模型名（opencode 和 pi 取 `/` 后面那段）；已经有同名代号时，加上类型后缀，比如 `deepseek-flash-api`、`deepseek-flash-opencode-cli`、`deepseek-flash-pi`。失效的旧代号改在 `~/.claude/foreman/agent-aliases.json` 里。
   - API key 的放法：
     - **写在配置文件里**（改完立即生效）：告诉用户打开 `~/.claude/foreman/config.json`，在这个协作方里加一行 `"api_key": "<key>"`，自己填上。提醒用户 key 是明文保存的，这个文件不要提交或分享。
     - **放在环境变量里**：配置里写 `"api_key_env": "<变量名>"`，告诉用户自己设置：Windows 上在"系统属性 → 环境变量"里加一个用户变量，或者在 PowerShell 里运行 `[Environment]::SetEnvironmentVariable('<变量名>', '<key>', 'User')`；macOS 和 Linux 写进 shell 的启动文件。设置后要重启 Claude Code 才能读到。
     - **不要让用户把 key 发到对话里。** 用户已经主动发了、并明确要求写进配置时，可以写进用户配置的 `api_key`（不能写进项目配置），同时提醒用户：这个 key 已经出现在对话记录里，建议之后换一个新的。
   - 运行 `config --cwd "<当前项目目录>"` 校验。报错时按报错修正（报错里会给出最接近的写法）；修不好就用备份恢复，告诉用户原因。
   - 再运行 `check`。不通过的项按 `fix` 处理：推理强度不支持的，从清单里重新选，回到第 5 步问用户。环境变量方式的 key 要等用户重启后才读得到，这时报 key 没设置是正常的，请用户重启后再运行一次 `/foreman:setup`。

7. **总配置情况**：用第 6 步 `check` 输出的 `summary`（没改配置时用第 1 步的），给出：
   - **本次改动**：这次改了配置时，在格子表前先列一张改动表：格子、协作方、原来 → 现在（推理强度、必选、加入或去掉）。没改配置就不列。
   - **格子表**：不论这次只做了哪一部分，都给出全部格子。每格一行，按讨论 simple / normal / complex、审查 simple / normal / complex、执行 simple / normal / complex、图像 generate / draw 的顺序排，三列：格子、候选、检查结果。候选写成"代号（推理强度，必选）"，推理强度不写或 `null` 的说成"默认"；几级的候选完全一样、只是推理强度不同时，可以合成一行，推理强度用 / 分开，比如"gpt-6-astra（medium / high / max，必选）"。表前说明一句：三类任务都还有一个 0 级（不值得找外部模型的小事），固定由 Claude 自己做，不在配置里；一格有几个候选时由 Claude 每次挑，必选的一定参加。`ok` 为 `false` 的写出 `problem`。`"claude code"` 在执行里说成"Claude 自己做"，在审查和讨论里说成"不找外部模型"；图像格子的 `null` 说成"关掉"；`config` 输出里 `image_configured` 为 `false` 时，图像两格说成"还没配置"。
   - **协作方表**：代号、类型、模型、用在哪几格、执行权限、检查结果。执行权限这一列：
     - `opencode cli` 或 `pi cli` 写了 `run_access`：写 `edit`（只改项目里的文件，不能运行命令）或 `shell`（还能运行命令，没有系统沙箱）；
     - `opencode cli` 或 `pi cli` 没写 `run_access`：写"未开启（可以开启 edit 或 shell）"。不要写成"不能执行"：它们能做执行，只是要用户先开启；
     - `codex cli`：写"不需要开启"；
     - `api`：写"—"，API 不做执行（能参加讨论和审查）。
   - **提醒**：`summary.warnings` 逐条用人话转告，已经在第 4 步处理掉的不再说。
   - 最后用两三句话总结：现在哪些能用、还有什么没弄好；平时直接让 Claude 做事即可：每件事按讨论、执行、审查分别定级，小事 Claude 自己做，达到门槛的从配置的候选里挑人交出去；也可以用 `/foreman:run`、`/foreman:discuss`、`/foreman:review` 点名。

**只有 API、没有 Codex、opencode 和 pi 时**：说明执行只能由 Claude 自己做，讨论和审查可以交给 API（审查只审文本材料，不能看截图）；想让外部模型干活或看图，需要装 Codex、opencode 或 pi（看图目前只有 Codex）。

**什么都没有时**：说明插件现在由 Claude 自己完成所有工作。想接入外部模型，可以装 Codex CLI（`npm install -g @openai/codex`，再运行 `codex login`）、装 opencode（`npm install -g @opencode/cli`）、装 pi（`npm install -g @earendil-works/pi-coding-agent`），或者准备一个 API key。装好后再运行一次 `/foreman:setup`。
