---
name: review
description: 请配置的协作方（比如 Codex）对代码改动做一次独立审查
argument-hint: [--base <分支> | --commit <sha>] [--level simple|normal|complex | --effort <推理强度>] [--model <模型>] [审查重点]
disable-model-invocation: true
---

用户要求请协作方审查代码。参数：

$ARGUMENTS

按 `foreman:dispatch` skill 里"五、审查"执行（如果尚未加载，先加载它）。用户已明确要求，所以不做 0 级判断：

1. 确定工作目录和审查对象：默认审查未提交的改动（`--uncommitted`）；参数里给了 `--base` 或 `--commit` 就照用。目录不是 git 仓库时，把要审查的文件和关注点写进审查说明。
2. **总是写一份审查说明**，通过 `--brief` 传入：写明本次改动的意图、风险点和参数里给的审查重点。审查方是 Codex 时，只有带审查说明，结果才是中文、遵守"只审查不改动、说人话"的要求；不带的话会走 Codex 原生审查，输出是英文。opencode 和 pi 总是拿插件算好的补丁审。
3. 确定等级：用户写了 `--level` 或 `--effort` 就照用，否则按 skill 里审查的定级标准从 1–3 级里判断 `--level`；用户写的 `--model` 一起加上。用 `cli.mjs review` 在后台运行，在对话里告诉用户这次用的模型和推理强度（以脚本启动时输出的第一行为准），再按 skill 的"实时查看"打开实时查看。
4. 拿到结果后逐条核实审查方指出的问题：确实存在的列出来，并说明打算怎么修；误报说明为什么不成立。用户只要了审查，修复前先问用户是否要修，除非用户已经说过要修。审查方和改动的执行方是同一个模型时，在汇报里注明。
