# 执行（/foreman:run）

执行定到 1 级以上、要写任务说明或拆工作包之前读这一篇。定级标准在 SKILL.md 的"定级"；这一格有几个候选或有必选时，另读 `references/seats.md`；研究类任务另读 `references/research.md`；交回后的验收和返工见 `references/acceptance.md`。

## 交给谁
- 1–3 级看 `resolved_modules.run.<等级>`：写的是 `"claude code"` 就由 Claude 自己做（脚本也会拒绝派出这一级），写的是候选就按 seats.md 挑一个派出。这一级按场景配了时（见 `references/config.md` 的"场景"），先按偏好里的场景路由选场景，派出时加 `--scene <场景> --scene-why "<依据>"`，看的是这个场景合并后的格子；续接沿用原来的场景。Claude 自己做时，同样按下面的任务说明想清楚范围和完成标准，按 acceptance.md 验收。
- 用户明确要求派出去时（比如用 `/foreman:run` 点名），不做 0 级判断，即使这一级是 `"claude code"` 也照派：加 `--agent <协作方代号>`，选 `capabilities.modes` 里有 `run` 的，不写 `--effort` 时推理强度用内置默认值（结果标 `outside_cell`）。这一级有候选时，`--agent` 只能从候选里选。想换模型再加 `--model`，只能换同一个提供方的模型。
- 混合的任务：一项工作里既有只由 Claude 做的部分（设计决定、文案、命名），又有能派的部分时，先由 Claude 把前者定下来、写进任务说明，再把其余部分派出。前端里布局、配色、字体、间距、动效、交互手感这类视觉和体验上的决定由 Claude 做；按定好的设计或现有组件模式实现的逻辑部分（状态管理、数据请求、表单校验、接口对接、测试）才派。

## 写任务说明
说得越细，协作方做得越好。按下面的结构写：

```markdown
# 目标
要做成什么，为什么做（一两句背景）。

# 范围
- 允许改动：具体文件或目录
- 只读参考：相关文件
- 不要碰：……

# 规模
预计改动多少行、几个文件；这次不需要的东西，比如命令行参数、配置项、兼容旧数据、测试。

# 要求与约束
接口签名、数据格式、要沿用的现有模式和工具函数、性能要求、兼容性等。

# 允许的适配
协作方遇到这些情况可以直接处理，不用停下来问。比如：
- 指定的测试入口跑不起来时，可以改用覆盖同一批测试的等效入口
- 允许修正某个测试夹具，但不得削弱断言
（没有就写"无"）

# 命名与文字
- 命名：新增的文件、类、函数、关键参数和配置项叫什么名字
- 注释：哪里需要写，写什么
- 提示文字：日志、报错、帮助信息、输出表头的原文或模板（要求照抄）
（任务不涉及这些时可以省略本节）

# 禁止事项
本任务特有的禁区。

# 完成标准
怎样才算做完。验证分两项写，都给出具体命令：
- 执行方验证：协作方要跑的定向测试和检查，只覆盖这次改动涉及的部分
- 最终验证：Claude 在最终版本上跑的全量测试或脚本；协作方不跑这一项

# 交付
需要在报告里特别说明的内容。
```

协作方偏爱做全做重：简单任务也会加参数、配置项、抽象层、兼容分支和大量测试。"规模"一节就是用来防这个的：写明预计的规模和这次不需要的东西，验收时也拿它对照。脚本附加的固定约束里也有"按规模做、只写必要的测试、不要过度防御"，任务特别容易做过头时，在任务说明里再强调一遍。任务说明本身也按规模写，简单任务不要写成长篇。

"允许的适配"按含义授权，不按改动大小：一行改动也可能改变样本外边界、费率或断言。凡是没写进这一节的越界，固定约束都会要求协作方停下来，在报告的 `decision_requests` 里提问。可以预见的环境问题（比如项目里有同名的 `tests` 包），提前写进这一节，能少停一次。

验证按"完成标准"的两项分工，同一份代码上的全量只跑一次：协作方跑定向测试，改了代码就重跑受影响的；全量由 Claude 在最终版本上跑。固定约束会要求协作方不跑全量，除非任务说明明确要求；确实需要它自己看全量结果时（比如任务就是修全量里暴露的失败），在"执行方验证"里写明。

**命名与文字**由 Claude 定：外部模型的文字表达弱，经常术语堆砌、翻译腔。新增的文件、模块、类、函数、关键参数和配置项叫什么，直接给出名单，名单之外的沿用项目现有风格；注释写在哪里、写什么，语言和项目一致；日志、报错、命令行帮助、输出表头这类会给人看的文字，给出原文或模板，要求照抄。

## 派出
- 任务说明先写成 UTF-8 文件（有 scratchpad 目录就放在那里，否则放在系统临时目录），用 `run` 在后台运行（Bash 的 `run_in_background`），跑完会自动通知；等待期间可以做别的，不要轮询。脚本会自动附加固定约束：不越界、开工前预检、只跑分给它的定向验证、什么情况下停下来提问、只写必要测试、不 commit/push、不碰密钥、按 schema 汇报。
- 启动后照 SKILL.md 的"派出时"告诉用户模型和推理强度、附看板链接，并处理实时查看。
- 多个任务可以并行，但文件范围不能重叠。**协作方正在改的文件，Claude 不碰。**
- 允许改动的范围里有被 `.gitignore` 忽略的路径（比如 `tests/`、结果目录）时，用 `--track "<路径>"` 指定（可以给多次），否则改动追踪看不到这些文件。续接时沿用上一轮的 `--track`。
- Codex 的沙箱不是 `read-only` / `workspace-write` 时（比如 `danger-full-access`），`--cwd` **不限制写入范围**，范围只能靠任务说明约束，再靠事后审查 diff 把关。

## 并发拆分
协作方任务的等待时间大部分花在模型思考上，跑命令只占一小部分。所以把一个大任务拆给几个会话同时做，能明显缩短等待。代价是总 token 更多（每个会话都要各自读一遍背景），Claude 也要多写几份任务说明、多做几次验收。

**什么时候拆**：下面几条**全部满足**才拆，否则派成一个任务：
1. 能拆成 2 份以上、不超过这个协作方的并发上限（`agents_status.<代号>.max_parallel`，默认 4；其他会话正在运行的同一协作方的任务也占名额），每份**写入的文件互不重叠**，而且**不依赖其他份的产出**。
2. 各份之间的接口（函数签名、数据格式、文件路径），Claude 能在派活前定下来，写进每份任务说明。定不下来就不拆。
3. 每份预计都要 10 分钟以上。太小的任务拆开，固定开销比省下的时间还多。

**不拆**：根因不明、需要排查的 bug；要改共用核心文件的重构；前后衔接的研究阶段；需要整体统一设计的工作；本身就是重计算的任务（同时跑会抢 CPU，这种让协作方写批量脚本并行跑）。适合拆的例子：几个互相独立的脚本或模块；接口定好后，一份写实现、一份补测试；按目录分开的批量修改。

**怎么派**：
- 每份按自己的难度各自定级。某份是 0 级或这一级配置成 `"claude code"` 时，那一份由 Claude 自己做，同样不碰其他份的文件；其余几份照常派出。几份的等级不同、其中某一级还有别的必选时，按等级各建一份计划，用同一个组名。
- 给同组任务起一个组名（英文代号加日期，比如 `factor-scripts-1013`，只用在命令里，实时查看上显示的是各份的 `--title`；同一个对话里每组用不同的组名，不同对话的组名重复没关系，查看时只算当前对话派出的；只能用英文字母、数字和 `. _ -`，实时查看要把它写进终端命令，脚本会拒绝其他字符），每份都用 `run --level <等级> --group <组名> --scope <允许改动的路径>` 派出，`--scope` 可以给多次。几份要交给同一格里不同的协作方、而这一格有必选时，单独派出会被拒绝：先用 `plan --module run --cell <等级> --group <组名> --seat <代号>=<这一份的名字> …` 建计划，每份用 `run --plan <plan_id> --seat <序号> --scope …` 派出。同时派出的几份放在同一条消息里，一起在后台启动。
- 脚本会拒绝两种情况：这个协作方正在运行的任务（不分组、不分会话，全都算）已经达到它的上限；和同组正在运行的执行任务写入范围重叠（讨论和审查不写文件，不查范围）。被拒绝时按报错重新划分，或者等前面的任务结束再派。
- 每份任务说明除了通用结构，还要写明：同组的其他任务在做什么、改哪些文件（这些文件不许碰）；共用的接口约定（原文照抄到每一份里）；这一份单独验证的方法。
- 终端实时查看（网页看板关着时）只开一个标签页：`watch.mjs --group <组名>`，标题写"执行：<短标题>"。
- 告诉用户这次拆成了几份、各做什么，以及每份用的模型和推理强度。
- **验收**：每份先单独验收（看 diff 和这一份的定向验证，不跑全量：其他份还没合进来，全量本来就过不了），不合格的单独返工（resume 沿用原来的组和范围）。全部通过、做完需要的整合步骤后，Claude 跑一次**整体验证**：在合起来的最终版本上跑全量测试或脚本。汇报时按份列出 run_id 和 token 消耗，再给出合计。
