# 挑席位：候选、必选、席位数和 Claude Code 席

第一次要启动外部席之前读这一篇：讨论和审查一律要读；执行这一格有几个候选或有必选时也要读。这里讲从一格的候选里挑谁、席位数、计划怎么建，以及讨论和审查里 Claude Code 自己那一席。

## 一格有多个候选时
一格里可以有几个候选，有的标了必选（`required`）。这一格要用到时，由 Claude 按下面的顺序挑：
1. 先排除做不了的：能力不够（出图、看图、执行权限）、材料不允许发给这一家（偏好文件或项目的要求）、额度已经用完。
2. 必选全部加入。
3. 讨论和审查按配置的席位数补外部席位：每一级找几个外部模型看 `resolved_modules.<discuss|review>.seats.<等级>`（默认值见 `references/config.md` 的"候选和必选"；不含 Claude Code 席和补漏席），这一格能用的候选少于这个数时全上。必选算在这个数里，其余由 Claude 按"不同的基础模型"从候选里挑；同一个模型经 api、pi、opencode 接入只算一个基础模型（脚本按 `scripts/models.json` 的身份表归一，`plan` 和 `stats` 用的是同一张表）。外部席位数和配置不一致时 `plan` 会拒绝；确实要多给或少给时（用户在角色弹窗里调整了分配、某一家的材料不能外发、某一家额度用完），加 `--count-why "<理由>"` 写明原因。中档、弱档也可以占席，作广度席：只参加第 1 轮，由 Claude 逐条核实。普通模式下，中档、弱档的参与方就是广度席；角色模式下看它达没达到角色的建议档位（见 `references/roles.md`）。3 级审查的补漏席在配置的席位数之外另加（见 `references/review.md` 的"补漏轮"）。
4. 执行每个工作包派一个执行方：复杂任务优先选强档、能跑命令、有沙箱的；机械任务可以用便宜的；并发拆分时，不同的份可以交给同一格里不同的协作方，各占各的并发名额。
5. 审查方尽量和执行方用不同的模型；只有同一个模型可选时照常审，汇报时注明。
6. 依据：`config` 输出里每个候选的 `tier` 和 `tiers` 命令给出的长短处作为先验（规则见 `references/model-tiers.md`）；偏好文件可以改，也可以引用本地实测（`stats`）覆盖档位。脚本只汇总，不自动排名。默认不要仅凭速度（tok/s）调整档位：先看核实质量，再比较同类任务的用时和费用；用户明确把速度放在第一位时可以按速度选，但不据此说这个模型能力更强。
7. 每次派出时用一句话告诉用户选了谁、为什么、没选谁。

挑出几席时，先用 `plan` 建一份派发计划，把理由写进 `--why`，再逐席用 `--plan <plan_id> --seat <序号>` 启动（`plan` 的输出里有每一席的启动命令）。同一席不能启动两次：返工用 `resume`；审查席没交回有效结果时可以重新启动（见 `references/review.md`）；第一轮还没拿到会话就失败、没法续接的席位，也可以用同一条命令重新启动。讨论和审查一律建计划，只挑一个外部席也一样（计划里有 Claude Code 席），不带计划的 `discuss`、`review` 会被脚本拒绝。执行只挑一席时可以不建计划，直接用 `--level`（加 `--agent` 点名）；这一格还有别的必选时脚本会拒绝，这时要建计划。
- 必选方达到并发上限时不跳过：派发命令默认自动按先来后到排队（最多等 60 分钟，stderr 里写排在第几位），名额空出来就派出去，所以派发要在后台启动。等不到时以排队超时的提示退出，这时再补发。
- 必选方失败、额度用完或被取消时，这件事算不完整（`status --plan <plan_id>` 的 `state` 为 `incomplete`，`missing_required` 写明缺了谁），按 `references/recovery.md` 处理，不拿其他候选顶替；向用户汇报时写明。
- 项目配置把整格关掉时（`closed_by_project`），这一格的必选那一步算"没做"，如实告诉用户，不能自己做一遍就说已经满足。
- `state` 为 `complete` 只说明必选席位交回了有效结果；3 级审查预留的补漏席还没跑完时看 `gap_unfinished`（见 `references/review.md`）。

## 席位带角色
任何多席位的计划都可以给席位带角色（`--seat <代号>=<角色名>`），角色卡写进这一席的任务说明。各模块的做法不一样：
- 讨论和审查的 2、3 级：角色是检查视角，按 `references/roles.md` 分配（工具能力是硬门槛，档位只作参考，核心角色不合并，外部席位数按这一级配置的 `seats`）。Claude Code 席照同一套规则分配，用 `plan --host-role "<角色名>"` 写进计划。启动前一定要弹窗让用户确认分配，`dispatch.auto` 为 `true` 时也一样。1 级不带角色。审查的补漏席写成 `=补漏`，但它不是检查视角，不因为它弹窗。
- 执行和手画（draw）：角色就是带写入范围的工作包（比如"实现""测试"），按 `references/run.md` 的"并发拆分"派出，用一句话告诉用户怎么分的，不弹窗。
- 出图（generate）：不分角色，画面要求由 Claude 统一定。
- 图像路线弹窗和角色分配弹窗同时要弹时，合成一次弹窗。

## 四类参与方：各自看得到什么
讨论和审查都适用。
- **Codex**：能自己读代码、跑只读命令来核实。
- **opencode 协作方**（`type` 为 `opencode cli`）：通过本机的 Opencode CLI 调用模型。脚本只给它读文件、搜索和列目录的工具，它能自己翻项目里的代码，但不能运行命令，也不能改文件。只能读项目目录里的文件，项目外的材料要摘进说明。它每读一次文件都多一次请求，比 API 协作方费额度；订阅额度紧的高档模型放在 3 级用。结果里的 `cost_usd` 按模型官方 API 价格算；它自己报的费用另存在 `reported_cost_usd`，只留档，汇报时不写。
- **pi 协作方**（`type` 为 `pi cli`）：通过本机的 Pi CLI 调用模型，和 opencode 协作方一样只有读文件、搜索和列目录的工具，读的路径限定在项目目录里（由 foreman 注入的守卫扩展检查）。`cost_usd` 按模型官方 API 价格算；pi 自己报的费用另存在 `reported_cost_usd`，只留档。pi 读用户自己的 pi 配置和登录信息，但不加载用户装的扩展、skill 和 MCP。
- **agy 协作方**（`type` 为 `agy cli`）：通过本机的 Agy CLI（Google Antigravity CLI）调用 Gemini、Claude 等模型，用 Google 账号的订阅额度（5 小时和每周两个窗口，默认并发 2）。守卫只放行读文件，路径限定在项目目录里；本机 agy 的沙箱可用时，还能在沙箱里跑只读命令（改不了项目内外的文件、上不了网，系统临时目录除外），这一点比 opencode、pi 强；沙箱不可用时没有 shell，脚本附上 `git ls-files` 清单，结果的 `notes` 会写明。项目或全局有 agy 的其他钩子、MCP 或插件配置时脚本拒绝派出，报错写明是哪个文件：这时换别的候选，并告诉用户原因，不要替用户改那些文件。`cost_usd` 按模型官方 API 价格算。
- **API 协作方**（`type` 为 `api`，比如 DeepSeek）：只看得到说明和附带的材料，自己翻不了代码。用 `--file "<路径>"` 把相关文件附上（可以给多次，`--file "<路径>:<起始行>-<结束行>"` 只附一段），说明里提到的代码、要讨论或审查的核心模块都要附。材料总量有上限（约 30 万字符），超了脚本会报错，这时精选文件或改用行范围；脚本还会自动附上项目文件清单。附带的材料会发给对应厂商，偏好文件或项目配置不让发的项目，不加 API 协作方。它在 `open_questions` 里要求看的文件，下一轮用 `--file` 补上。`agents_status` 里 `key_set` 为 `false` 的 API 协作方会直接失败：挑它之前提醒用户在 `~/.claude/foreman/config.json` 的这个协作方里填 `api_key`（立即生效），或者设置 `api_key_env` 指向的环境变量并重启 Claude Code。有 API 参与方时，按 `references/recovery.md` 的"API 参与方繁忙时"在后台启动排队检查。
- 给 Codex、opencode、pi 和 agy 协作方传 `--file` 时，脚本只把路径列成"重点文件"，不附内容，它们会自己去读。
- 所有参与方对代码的说法，Claude 都要对照原文核实后才能采信。

## Claude Code 席
讨论和审查只要派了外部席，Claude Code 自己也占一席。除了最终裁决由 Claude Code 负责以外，这一席和外部席位的身份一致：提交同样格式的报告、守一样的时机、接受一样的挑错、一样记去留。
- **范围**：讨论和审查的 1–3 级。0 级，以及格子配置成 `"claude code"`、不找外部模型的等级（Claude Code 自己想清楚或自己审一遍）不走这里；执行和图像不适用。
- **报告**：写成 JSON，格式和外部席位相同：讨论按 `schemas/discuss.schema.json`，审查按 `schemas/review.schema.json`。1 级可以短答：`options`、`critiques` 可以为空，`position`、`open_questions`、`confidence` 必须写；不为了填满报告凑观点。审查报告针对计划固定下来的材料，验收时已经发现并修好的问题不算这一轮的发现。
- **先提交报告，再启动外部席**：建好计划后，先用 `submit --plan <plan_id> --report <报告.json>` 登记，提交之后外部席才能启动，脚本在准入时检查。讨论进入下一轮时也一样：先把这一轮对各方案的质疑写成报告提交，再续接其他席。脚本保存报告快照、指纹和登记时间，`status --plan` 的 `host.before_external_start` 写明是否早于外部席启动；它证明不了"没读过结果"，所以登记之前不读任何参与方的结果。
- **公共说明**：写报告时发现议题或审查说明里缺了外部席位需要的事实（相关的用户偏好、已经否决的路线和原因、验收事实、复现条件、用户报告的问题），先补进说明再启动。说明里写事实，不写 Claude Code 还没证实的具体诊断或倾向，这些只放进自己的报告。补不进去的关键事实（比如不允许外发），在决策记录里注明哪些结论受影响。
- **外发**：报告会在第 2 轮匿名发给外部席位，所以按本场参与方都能接收的材料范围写；涉及用户偏好和私密上下文的只写结论，不能外发的关键证据注明受限。
- **席位数**：不计入每一级的 `seats`。
- **模型**：Claude Code 用的模型由用户在 Claude Code 里选。`submit` 时加 `--model <当前模型 ID>` 写上，用 Claude Code 系统提示里写的模型 ID（比如 `claude-opus-5-5`），每次写法一致，`stats` 按它分行（自报，脚本不核实）。按"不同的基础模型"挑外部席时，Claude Code 的模型也算一个，和它同一个基础模型的外部候选不算新增的独立模型。
- **作者关系**：审查 Claude Code 自己写的改动，或者讨论它自己提出的设计时，`submit` 加 `--author`。这时这一席不算独立来源，外部审查的必要性不因为多了这一席而降低；外部席位和作者是同一个基础模型时也一样。
- **角色**：和外部席位用同一套分配规则，按实际能力拿角色卡（`plan --host-role "<角色名>"`），按角色卡的检查重点写报告（报告格式不变，角色卡原文写进决策记录）；综合对照位可以给它，但不专属于它。分配表和确认弹窗里列出这一席。
- **它不做的**：不能当补漏席（它参加过首轮）；"每席新会话"的要求只针对外部席位。
- **裁决**：最终裁决由 Claude Code 负责。自己的观点同样编号、写去留理由，用 `judge` 记在自己的报告记录上，`stats` 自动标成自评。匿名对 Claude Code 自己无效，它认得出自己的方案，去偏靠先提交报告、逐条证据和写明的理由。下面两种情况在决策记录里显式标出，交用户看：最终方案基本等于自己的原方案、又驳回了外部的反对意见；自己的关键主张被外部的可复现证据反驳，仍然采纳。
- **存档**：2、3 级的决策记录另存成 Markdown 文件，放在记录目录的 `plans/<plan_id>.decision.md`；改判时另存一版（`<plan_id>.decision.2.md`），不覆盖原来的。
