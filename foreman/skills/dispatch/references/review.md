# 审查（/foreman:review）

审查定到 1 级以上、或用户要求审查时，选审查对象、建计划之前读这一篇；挑审查方和 Claude Code 席的规则另见 `references/seats.md`。定级标准在 SKILL.md 的"定级"。

审查评判已经存在的东西，交回一份问题清单（可以为空）。审查对象用 `--target` 指定：

| `--target` | 审什么 | 材料 |
|---|---|---|
| `diff`（默认） | 代码改动 | 脚本用 git 算好的改动范围，见"怎么审" |
| `files` | 已有的文件，没改过也能审，比如写好的设计文档、某个模块、配置 | `--file` 列出的文件 |
| `claims` | 结论和证据，比如研究结论落地前的证据审查（见 `references/research.md`） | 审查说明里逐条列出结论，`--file` 附上证据文件 |
| `visual` | 截图、播放文件、渲染结果，比如动画和页面交付前的视觉检查 | `--file` 列出的图片；只派给能看图的协作方（`capabilities.reads_images`，目前只有 Codex） |

`resolved_modules.review.<等级>` 是 `"claude code"` 时，这一级不找外部模型，Claude 自己再仔细审一遍，发现的问题同样按"审查之后"处理。

## 定级
等级表在 SKILL.md 的"定级"，判断时按下面的顺序：
- 先看是否命中 3 级：改动改变了金额和计费、数据删除和迁移、并发、鉴权和安全、不可逆操作的行为；或者有具体的调用链、配置或故障证据表明可能影响这些行为，又排除不了。只是文件放在相关目录里、只改注释和格式、经核实不改变行为的机械改动，不算命中。改动小、有测试、容易回滚，都不能把命中的 3 级降下来。
- 没命中 3 级的再分 0–2 级。审查拿不准时不自动往高一级：先查调用链、影响的对象和已有的验证，高风险影响排除不了就按 3 级，其余按已经确认的影响定级，没确认的点写进审查说明。
- 不继承执行的等级、作者和排查难度：根因不明、查了很久才修好的 bug，看修完的改动碰到了什么。Claude 自己做的 3 级执行任务至少按 2 级审（作者自审不算独立来源），但不因此升到 3 级。
- 定级理由写进 `plan --why`：3 级写出碰到的高风险类别和位置，2 级写一句为什么不是 3 级。
- 审查方在报告里指出材料其实属于 3 级、Claude 核实成立时，按 3 级补审一次（新计划），汇报时说明。

## 怎么审
- 协作方交付的改动用 `review` 发起一个**新会话**审查，不在执行的那个会话里自审。
- 审查方按 seats.md 挑：尽量和执行方用不同的模型；只有同一个模型可选时照常审，汇报时注明"同一个模型、新会话审的"。`visual` 只挑能看图的。API 协作方也能审（只审文本，不能审 `visual`），它会收到补丁或文件内容：偏好文件或项目不让把材料发给它的厂商时不挑它；挑了它时，按 `references/recovery.md` 的"API 参与方繁忙时"在后台启动排队检查。
- 审查一律建计划，只挑一个审查方也一样：用 `plan --module review --cell <等级> --group <组名> --target <对象> [--file …] [--base <分支> | --commit <sha>] --seat … [--host-role "<角色名>"]` 建计划，审查对象和材料在建计划时固定下来，脚本记下材料的指纹。这一格按场景配了时，再加 `--scene <场景> --scene-why "<依据偏好里的哪一条>"`（见 seats.md 第 3 步的"场景"）。
- 接着 Claude Code 按 seats.md 的"Claude Code 席"写自己的问题清单（审查 schema），用 `submit` 提交；审的是 Claude Code 自己写的改动时加 `--author`。验收时已经发现并修好的问题不写进去。材料在建计划之后变了，`submit` 和外部席都会被拒绝，这时按现在的材料重建计划。
- 然后每个外部席各发一次 `review --plan <plan_id> --seat <序号> --brief …`，不再写 `--target`、`--file` 和范围参数。需要不同的检查视角时（比如证据审查），可以给席位带角色（`--seat <代号>=<角色名>`），角色卡写进各自的审查说明，分配规则和启动前的弹窗确认照 `references/roles.md`。
- 每个外部席都是新会话。审查不能续接，追问和复审都开新的审查（新计划，Claude Code 席照样先提交报告）；有争议的问题也可以这样另开一次审查定向复核，Claude Code 席自己报的问题也一样。计划里的外部审查席失败、卡死或没审完（没交回有效结果）时，用同一条 `review --plan <plan_id> --seat <序号>` 命令重新启动这一席（材料要和建计划时一样）；已经交回有效结果的席位不能再启动。Claude Code 席的报告每个审查计划只交一次。
- 发起审查时总是用 `--brief` 附上审查说明：改动意图、风险类别和要看的范围，以及已知的事实（失败日志、复现条件、用户报告的问题）和验证情况（哪些命令在哪个版本上通过了，哪些没覆盖）；Claude Code 自己还没证实的具体诊断不写进说明，只放进它的报告。审查要求会让审查方不重跑说明里写明已通过的测试，只为具体疑点跑定向的只读命令；需要写文件的复现它会写进 `unverified`，由 Claude 来跑。`claims` 要逐条列出结论，每条写明证据的位置和关键数字。`--file` 在四类对象里都生效：Codex、opencode 和 pi 只拿到路径（列成"重点文件"），自己去读；API 协作方拿到文件内容。opencode、pi 和 agy 只能读项目目录里的文件：材料在项目目录外（比如放在 scratchpad 里的补丁）时，计划里有它们就建不了计划，先把材料复制到项目目录里，或者这几席改用 Codex、API 协作方。Codex 只有在审 `diff`、既不带审查说明也不带 `--file` 时才走它的原生审查：输出是英文文字，没有结构，也不受审查要求约束，所以总要带说明。
- `diff` 的范围由脚本先用 git 算好，和 Codex 原生审查的含义一致；没有任何改动时脚本直接报错，不会派出去：
  - `--uncommitted`（默认）：已暂存、未暂存的改动，加上未跟踪的新文件；
  - `--base <分支>`：从和那个分支的分叉点到当前工作区，包括已提交和未提交的改动，不含未跟踪文件；
  - `--commit <sha>`：那次提交引入的改动。
- `files`、`claims`、`visual` 不要求仓库里有改动，也不要求目录是 git 仓库；非 git 目录里审已有文件用 `--target files`。
- 结果里的 `review_target` 和 `review_scope` 写明审的是什么、文件数和材料指纹；`diff` 的完整补丁保存在记录目录的 `review.patch`。审查期间材料又变了，结果标 `stale: true`，`warnings` 里也有提示：这份审查可能没覆盖最新的版本，需要时重审。
- Codex 自己读改动和文件。opencode、pi 和 agy 拿到的是脚本算好的补丁（`diff`）或文件路径，外加只读工具查上下文；opencode 和 pi 不能跑命令，agy 在本机沙箱可用时能在沙箱里跑只读命令。API 协作方只看得到附带的材料：补丁或文件内容，加上项目文件清单。opencode、pi 和 agy 的补丁超过约 20 万字符、API 的材料超过约 30 万字符时会被拒绝：按提交（`--commit`）或按文件分开审，或者改用 Codex 审查。

## 补漏轮
这一级的补漏开关（`resolved_modules.review.gap`，选了场景时取这个场景的值）开着时，多席审查在各席结束、Claude Code 去重以后（Claude Code 席的清单一起去重），再做一次补漏轮：交给这一格里还没参加过的合适模型（基础模型和前面各席都不同，包括 Claude Code 席；工具够审这份材料），新开一次审查，只问"这份清单还漏了什么"。Claude Code 席不能当补漏席。
- **席位**：补漏席算原计划的一席，在配置的 `seats` 之外另加（不用 `--count-why`），一份计划最多一个。开关开着、这一格还有合适的候选时，建计划时就要列进去，写成 `--seat <代号>=补漏`，`plan` 会检查；开关关着时不加。先启动其余各席，等它们都结束、Claude 去重后，再启动这一席。这一格的候选都已经用在独立审查里时，不做补漏轮。建计划时预留了补漏席，就要把它跑完：补漏席用的协作方没标必选、计划里又有必选席时，`state` 只看必选席，补漏席没跑完也会显示 `complete`；`status --plan` 的 `gap_unfinished` 和实时查看的计划行（"gap seat not finished"）会把还没交回有效结果的补漏席标出来。
- **说明**：原来的审查说明，加上去重后的问题清单（包括 Claude Code 席报的；每条写位置和一句话的问题，不写 Claude Code 核实的结论），要求只报清单里没有的问题，没有就交回空的 `findings`。
- **核实**：它报的问题同样逐条核实、用 `judge` 记下去留；其实和清单里某一条是同一个问题的，用 `--same` 连到那一条。
- 补漏席不是检查视角，不为它单独弹窗；角色模式本来就要弹窗时，在分配表里列上它。
- 这一格里没有合适的模型时不做，在汇报里注明"没有做补漏轮"和原因。开关关着的等级不做补漏轮。

## 只读
讨论和审查都不许改项目文件。结果里的 `readonly` 写明这次实际的保障：

| `readonly` | 谁 | 含义 |
|---|---|---|
| `tools` | opencode、pi、agy、API | 只有读文件、搜索、列目录的工具，或者根本没有工具；agy 另有沙箱里的只读命令 |
| `sandbox` | 这类任务配了 `read-only` 沙箱的 Codex | 系统沙箱拦下写入 |
| `audited` | 没配只读沙箱的 Codex | 只靠规则约束，事后对比快照 |

- `audited` 必须拍改动快照：拍不了就不启动，也不能用 `--no-snapshot`。`config` 和 `check` 的 `summary.warnings` 里有 `readonly_audited` 时，把提示里的改法转告用户。
- 发现有证据的写入（工具事件，或者它自己在报告里说改过）时，这一方记为失败：`status` 为 `failed`，`readonly_violation` 列出改了哪些文件，diff 在记录目录的 `diff.patch`。它交回的意见还在结果里，可以参考，汇报时写明它越界了。改动不会自动还原：归属是按整个文件判断的，同一个文件里可能也有用户或其他任务的改动，所以只还原能证明是它这次改的部分；分不清的不动，告诉用户由用户处理。
- 归属未知（`by: unknown`）的改动不算违规，多半是别人改的，不要还原；被审的材料这样变了，审查结果会标 `stale`。

## 审查之后
1. **逐条核实**：审查意见在结果的 `report` 里：`verdict`（`issues_found` 发现问题、`no_issues` 没发现、`incomplete` 没审完）、`findings`（每条有编号、位置、问题、触发场景、严重程度、证据和修复建议）、`coverage`（查了哪些、没覆盖哪些）和 `unverified`（拿不准的地方）。几席的结果（包括 Claude Code 席的报告）按问题去重后逐条核实，确实存在的才算，Claude Code 席自己报的问题同样要核实；误报直接忽略，在汇报里简要说明为什么不成立。`verdict` 为 `incomplete`、或者 `coverage.not_checked` 里有关键部分时，这份审查不完整，需要时补审。没有 `report` 时（Codex 原生审查，或者两次都没交回合格的格式），意见在 `last_message` 的原文里。
2. **记下去留**：核实完，每一席都用 `judge` 记下每条的去留，Claude Code 席的记在它的报告记录上：`judge --run <run_id> --accept "F1,F3" --reject "F2"`（部分成立的用 `--partial`），编号用报告里的。几席报的是同一个问题时，在其中一席加 `--same "F1=<另一席的 run_id>:F4"` 连起来，`stats` 靠它判断"只有它发现"。越界写入、记为失败的席位，交回的意见照样记。没有结构化报告的（Codex 原生审查），按 Claude 在汇报里给的编号记。结构化报告是 `no_issues`、一条都没报的席位不用记，`stats` 自动按 0 条算。
3. **谁来修**：
   - Claude 主动发起的审查：小问题 Claude 直接改；问题多或涉及逻辑的，把核实后的问题写进返工说明，用 `resume --reason rework` 续接原来的执行方去改，算一次返工（次数按 `references/acceptance.md` 的"返工"）。改动本来就是 Claude 做的，由 Claude 改。
   - 用户用 `/foreman:review` 发起的审查：用户只要了审查，先把核实后的问题和打算怎么修告诉用户，用户同意（或已经说过要修）再修。
4. **修完重新验证**：在最终版本上重新跑构建、测试或脚本。要不要复审看修复增量本身的风险，不看原审查的等级：增量按"定级"命中 3 级的复审一次，其余不复审（有争议的问题照样可以另开定向复核）。复审这样做：
   - 新建计划（新会话），组名在原组名后加 `-rr`，标题带"复审"；Claude Code 席照常先提交报告。
   - 只查三件事：上一轮接受的问题修好没有、修复有没有引入新问题、修复和原改动的直接交互。审查说明列出上一轮接受的每条问题（编号、位置）和各自的修法，以及受影响的调用方和数据约束；允许审查方读增量以外的文件，写明上一轮已核实的问题不要重复报。
   - 修复边界清楚、没有扩大接口或风险范围时，只开这一格的必选强模型一席（必选里没有强模型时挑一个强档候选），加 `--count-why "定向复审，只审修复增量"`，不带角色、不做补漏轮。修复扩大了接口或风险范围，或者边界说不清时，按这一级的正常席位和补漏规则审。
   - 审查对象用修复增量：修复单独成了一个提交时用 `--commit <sha>`；上一轮审的版本已经提交、之后只有修复时，用 `--base <上一轮的提交>`（不含未跟踪文件，修复新加的文件先 `git add`，或用 `--file` 附上）或 `--uncommitted`（工作区里只有修复时）；都不满足时用 `--target files --file <修复改过的文件>`，这时审的是整个文件、不是差分，说明里写明修复的位置。
   - 最多复审一次；仍有问题或关键部分没覆盖时，照实报告为没解决或不完整。
5. **向用户汇报时注明**：审查方和执行方是同一个模型、审查结果标了 `stale`、审查方越界写入、没做补漏轮。
