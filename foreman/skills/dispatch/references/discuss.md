# 讨论（/foreman:discuss）

讨论定到 1 级以上、或用户要求和其他模型讨论时，写议题、挑参与方之前读这一篇；挑席位和 Claude Code 席的规则另见 `references/seats.md`。定级标准在 SKILL.md 的"定级"。

**最终裁决由 Claude Code 负责**：各参与方的意见，包括 Claude Code 席自己的报告，都只作参考，接受还是拒绝按论据决定，不因为谁坚持就让步，也不按多数票。为了写议题说明，可以先读代码和数据、做只读的统计，把事实弄清楚。`resolved_modules.discuss.<等级>` 是 `"claude code"` 时，这一级不找外部模型，Claude 自己想清楚即可。

## 选模式
定完级、要找外部模型讨论时，再选用普通模式还是角色模式：
- 1 级只用普通模式。2、3 级默认用普通模式：同一份议题，各方独立出方案（见下面的"流程"）。
- 2、3 级下面任一条成立时，提议用**角色模式**：议题里有几个目标互相拉扯（比如安全和便利、实现成本和体验、兼容维护和重构）；用户点名要用；偏好文件写了这类议题用角色模式。事实核对、根因不明的 bug、有客观答案的问题，不用角色模式。
- 角色模式：每个参与方带一张角色卡，按工具能力（硬门槛）、长处和模型档位（只作参考）分配角色，优先一个模型扮一个角色；达不到角色建议档位的参与方作广度席，只参加第 1 轮。启动前**一定要弹窗让用户确认分配**，`dispatch.auto` 为 `true` 时也一样。具体做法先读 `references/roles.md`（角色卡、预设角色、分配规则、弹窗、第 2 轮、决策记录），模型档位见 `references/model-tiers.md`。
- 用户在弹窗里选了"改用普通讨论"，就按普通模式进行。

## 流程（轮数上限见配置 `dispatch.discuss_max_rounds`，默认 2）
1. **第 1 轮，独立出方案**：议题说明只写背景、要解决的问题、约束、已知事实、相关代码位置，以及要回答的具体问题，**不写 Claude Code 自己的倾向**，以免参与方顺着说。按 `references/seats.md` 从 `resolved_modules.discuss.<等级>` 里挑出参与方，用 `plan --module discuss --cell <等级> --group <组名> --seat <代号>[=<角色名>] … [--host-role "<角色名>"]` 建计划（这一级按场景写了 `seats` 时再加 `--scene <场景> --scene-why "<依据偏好里的哪一条>"`，见 seats.md 第 3 步的"场景模式"；组名是英文代号加日期，比如 `config-rework-1013`，只用在命令里；同一个对话里每场讨论用不同的组名，后续轮次沿用；只挑一个外部参与方也要建计划）。接着按 seats.md 的"Claude Code 席"写好自己的报告，用 `submit` 提交，写报告时发现议题缺的事实先补进议题。最后给每个外部席各发一次 `discuss --plan <plan_id> --seat <序号>`：同一份议题（角色模式下是相同的公共主干，各自末尾带一张角色卡），放在同一条消息里一起在后台启动。
2. **第 2 轮，交叉挑错**：各方方案（包括 Claude Code 席的）有实质分歧，或者某一方的结论里有 Claude Code 还没核实、又会影响结论的地方时才做；基本一致时直接裁决（角色模式的触发条件见 `references/roles.md`）。先把这一轮自己对各方案的质疑写成报告，用 `submit` 提交（脚本要求它早于其他席的续接）。再把各方方案匿名成"方案 A / 方案 B / …"，Claude Code 席的方案也在里面，用 `resume --run <这一方第 1 轮的 run_id>` 分别续接每个外部参与方（广度席不续接；同样放在同一条消息里并行），要求它找出其他方案最薄弱的地方，并和自己的方案对比。只发方案摘要和分歧点，不发完整报告。
3. **第 3 轮及以后（可选）**：只有关键分歧还没解决、多一轮确实可能改变结论，并且没有超过轮数上限时才做。脚本拒绝续接时，就按已有结果裁决。
4. **Claude Code 裁决**：逐条决定接受还是拒绝各参与方的观点（包括自己报告里的），写明理由，形成最终方案。按证据、约束和可逆性判断，几方一致的结论也可能一起错。
5. **记下去留**：裁决后，用 `judge` 把每个参与方每条观点的去留记进它那一轮的记录，Claude Code 席的记在它的报告记录上（`submit` 输出的 run_id），编号用决策记录里的观点编号：`judge --run <run_id> --accept "P1,P3" --partial "P4" --reject "P2"`。同一个参与方在后面的轮次里重复的观点，沿用原来的编号，只记在它第一次提出的那一轮上，后一轮不要再记这个编号（`--same` 也不能把同一席的两轮连起来，脚本会拒绝）；两个参与方说的是同一件事时，在其中一方加 `--same "P1=<另一方的 run_id>:P5"`。`stats` 靠这些记录统计各模型的实测表现。

- **1 级（一次性问答）从简**：Claude Code 照样先提交一份短报告（自己的判断、把握和依据），再启动外部席；不做第 2 轮，也不写决策记录和 `judge`，外部席位也一样不记。核实参与方的回答后，用人话直接告诉用户结论和依据，自己原先的判断和最后的结论不一样时说明为什么改。附带文件、实时查看和繁忙处理照常。
- 续接下一轮时沿用第 1 轮的等级（`resume` 也要写 `--level`，讨论的续接不写 `--reason`），续接会沿用原来的计划和席位。每个参与方单独一个 run_id，轮数上限对每个参与方各自生效。每个参与方各占自己协作方的一个并发名额；某一方的协作方名额满了时，它的派发命令会自动排队，等到名额再启动，不要跳过这一方，也不要换协作方。
- 某个参与方失败（比如余额不足 `quota_exhausted`、接口报错、key 没设置、被终止 `cancelled`）不影响其他参与方：告诉用户哪一方失败、原因是什么，用其余参与方的结果继续。失败的是必选方时，这场讨论算不完整，按 seats.md 处理。不要为了凑齐参与方去改配置。`agents_status` 里 `key_set` 为 `false` 的 API 参与方会直接失败：讨论前提醒用户在 `~/.claude/foreman/config.json` 的这个协作方里填 `api_key`（立即生效），或者设置 `api_key_env` 指向的环境变量并重启 Claude Code。
- 讨论是只读的：Codex 可以读代码、跑只读命令来支撑观点，但不能改文件。结果的 `readonly` 写明这次的只读保障；有证据的写入会让这一方记为失败，怎么处理见 `references/review.md` 的"只读"。API、opencode、pi 和 agy 协作方改不了文件。
- 有 API 参与方时，启动后在后台启动排队检查（见 `references/recovery.md` 的"API 参与方繁忙时"）。

## 向用户汇报：决策记录
不贴原始对话，用人话整理成下面的格式（1 级的问答不用）：
- **议题**：一句话
- **候选方案**：Claude Code 席的和每个参与方的，各自的核心思路和取舍
- **各参与方的主要观点**：按参与方分开列，用模型名称呼（比如 gpt-6-astra、deepseek-v4-pro），Claude Code 席写成"Claude Code"（自评）。整份记录统一编号（P1、P2…），每条注明 ✅ 接受 / ❌ 拒绝 / ⚠ 部分接受，并写明理由；`judge` 用的就是这些编号
- **最终方案**：以及和 Claude Code 席最初的方案相比改了什么。seats.md"Claude Code 席"里"裁决"一条说的两种情况，在这里显式标出
- **待确认**：需要用户拍板或先验证的事
- 附上计划的 plan_id，以及每个参与方的 run_id、模型、推理强度和 token 消耗（Claude Code 席写自报的模型，用量不统计），决策记录文件的位置，方便用户回看原始记录
- 角色模式另加分配表、角色卡和缺席的视角，观点写成"模型［角色］"，见 `references/roles.md`

## 讨论之后
- 用户只是来要建议的：停在决策记录，由用户决定做不做。
- 用户要把事情做成的：最终方案里没有要用户拍板的事项，就按最终方案进入执行（先按 SKILL.md 的"分工"判断由谁做）；有业务取舍、偏好、风险承受度、扩大范围、要额外花钱或不可逆的事项，先交给用户决定，不要替用户拍板。
- 讨论的是已做出的改动的效果：结论是在原定目标内改做法的，用 `resume --reason rework` 续接原执行方返工（按 `references/acceptance.md` 的"返工"计次）；方向或目标变了的，或者要做原任务说明里没有、写明这次不做的事，当作新任务重新定级（见 `references/acceptance.md` 的"返工"最后一条）；效果已经达标的，按审查定级。
