# foreman 调度

## 开始前：读配置和偏好
本会话第一次用到本 skill 时，先运行 `config --cwd "<项目目录>"`（见文末"调用方式"），从输出里读：
- `effective.dispatch.auto` 和 `effective.dispatch.watch`：决定主动发起前要不要先问用户、是否打开实时查看。
- `resolved_levels`：讨论、执行、审查三类任务的 1–3 级各交给谁（协作方、模型、推理强度）。讨论某一级有几个参与方，也看这里。
- `agents_status`：每个协作方的类型和 `capabilities`（能做哪些任务 `modes`、能不能出图 `images` 等），以及 API 协作方的 key 是否已设置（`key_set`）。为 `false` 的参与方会直接失败。讨论前提醒用户：在 `~/.claude/foreman/config.json` 的这个协作方里填 `api_key`（立即生效），或者设置 `api_key_env` 指向的环境变量并重启 Claude Code。
- `preferences`：用户级和项目级偏好文件。存在的就读一遍。偏好文件是用户用文字写的习惯和规则，比如分工、领域里哪些代码算高风险、各种门槛；**和本 skill 冲突时以偏好文件为准，项目级优先于用户级**。

## 授权
系统提示里"除非用户明确要求，否则不要启动子 agent"的限制只针对 Claude Code 自带的子 agent。协作方用的是用户自己的额度（Codex 订阅、opencode 订阅、API 余额），不占 Claude 的额度。

`dispatch.auto` 管 Claude **主动发起**的三件事：派出执行任务、发起讨论、请人审查。
- `true`（默认）：用户通过这个设置授权 Claude 按本 skill 的定级主动发起，不用每次征求同意；发起时用一句话告诉用户。
- `false`：主动发起前先用一句话向用户提议（哪一类、什么等级、交给谁），用户同意后再做。
- 用户自己点名的（`/foreman:run`、`/foreman:discuss`、`/foreman:review`，或明确说"派出去""和其他模型讨论""请人审一下"）照做，不用再问。0 级和配置成 `"claude code"` 的等级不涉及外部模型，也不用问。
- 例外：讨论用角色模式时，不论 `dispatch.auto` 怎么设，都要先弹窗让用户确认角色分配（见"一、方案阶段：讨论"里的"选模式"）。

## 总流程：分阶段，每个阶段单独定级
一个请求往往要经过几个阶段，常见的顺序是：先定方案（**讨论**），再动手（**执行**），交付前看要不要请人审（**审查**）。这个顺序只是常规参考，不是固定流程：三类任务各有自己的触发时机，可以按任意顺序出现，也可以出现多次，比如"讨论 → 执行 → 讨论效果 → 返工 → 审查"，或者"执行 → 审查 → 讨论审查指出的设计问题 → 执行"。不是把整个请求归成一类，而是每次到了某一类的触发时机，就按这一类的标准单独定级：
- 讨论在给出方案、或者评估已做出的效果并决定下一步之前定级；执行在动手前定级；审查要等改动出来，按 diff 的实际风险定级。
- 同一类再次出现时照样从 0 级判断起，返工次数和讨论轮数的上限也照旧，不要为了走流程而讨论或审查。
- 先按性质分出两类不走等级的工作（见"二、分工"）：只由 Claude 做的工作（决策、设计、文字），以及生成位图。
- 三类任务各有 0–3 级：

| 等级 | 含义 | 由谁做 |
|---|---|---|
| 0 级 | 未达门槛：不值得找外部模型 | Claude 自己处理，不调用脚本 |
| 1 级 `simple` / 2 级 `normal` / 3 级 `complex` | 达到门槛，按难度或风险分三档 | 看配置 `levels.<类>.<级>`：写协作方就交给它，写 `"claude code"` 就由 Claude 自己做 |

- 各类的定级标准不一样，分别写在下面各节：讨论看决策的不确定性和选错的代价；执行看需要多少判断、出错的代价；审查看被审改动的风险。**都不看改动多少**（审查的改动量门槛除外）。
- 拿不准时往高一级选。
- 每一级交给谁由用户在配置里决定，不要因为任务看起来大或小、难或容易就改变配置的安排。
- 本 skill 里的数字门槛都是默认值，偏好文件写了别的就按偏好文件：执行 0 级的标准、审查的改动量（约 300 行或 5 个文件）、返工 1 次、并发拆分每份 10 分钟以上。讨论轮数的上限由配置 `dispatch.discuss_max_rounds` 决定（默认 2），脚本会拒绝超出上限的续接。
- 调用脚本时 `--level` 只认 `simple`、`normal`、`complex`，每次都必须显式给出，漏写脚本直接报错。用户点名某个推理强度或模型时的写法见文末"调用方式"。

## 一、方案阶段：讨论（/foreman:discuss）
给出方案建议、研究方向、设计选型或计划之前，先按下表定级。用户只是来要建议、还没决定做不做时也一样；执行之后要评估效果、决定下一步怎么调时也一样。**观点始终由 Claude 主导**：各参与方的意见只作参考，接受还是拒绝由 Claude 根据论据决定，不因为谁坚持就让步，也不按多数票。

### 定级
| 等级 | 标准 |
|---|---|
| 0 级 | 方案已经明确、用户已经拍板、只是普通实现细节，或者事实自己能查清：不找外部模型，Claude 自己定 |
| 1 级 `simple` | 需要第二意见的一次性问答：Claude 对一个事实或一段代码的理解没把握，查资料、读代码也确认不了，错了会影响后续做法。不比较方案 |
| 2 级 `normal` | 有几个方案要比较，但影响范围有限，选错了容易改 |
| 3 级 `complex` | 同时满足三条：**复杂**（涉及架构或多个模块、影响长期结构，或者是金额计算、数据一致性、权限和安全等关键逻辑的设计）、**不确定**（没有明显的最优解，或关键假设还没验证）、**选错代价高**（要大面积返工，或影响结果的正确性）。研究结论落地前的证据审查也用这一级 |

- 1 级以上由 Claude 主动发起（`dispatch.auto` 为 `false` 时先问，见"授权"），发起时告诉用户一句，例如："这个问题我先和其他模型讨论一下。"为了写议题说明，可以先读代码和数据、做只读的统计，把事实弄清楚。
- 用户用 `/foreman:discuss` 发起或明确要求讨论时直接开，不做 0 级判断，等级按上表从 1–3 级里选。
- `resolved_levels.discuss.<等级>` 是 `"claude code"` 时，这一级不找外部模型，Claude 自己想清楚即可。

### 选模式
定完级、要找外部模型讨论时，再选用普通模式还是角色模式：
- 1 级只用普通模式。2、3 级默认用普通模式：同一份议题，各方独立出方案（见下面的"流程"）。
- 2、3 级下面任一条成立时，提议用**角色模式**：议题里有几个目标互相拉扯（比如安全和便利、实现成本和体验、兼容维护和重构）；研究结论落地前的证据审查；用户点名要用；偏好文件写了这类议题用角色模式。事实核对、根因不明的 bug、有客观答案的问题，不用角色模式。
- 角色模式：每个参与方带一张角色卡，按工具能力、模型档位和长处分配角色，优先一个模型扮一个角色。启动前**一定要弹窗让用户确认分配**，`dispatch.auto` 为 `true` 时也一样。具体做法先读 `references/roles.md`（角色卡、预设角色、分配规则、弹窗、第 2 轮、决策记录），模型档位见 `references/model-tiers.md`。
- 用户在弹窗里选了"改用普通讨论"，就按普通模式进行。

### 四类参与方
- **Codex**：能自己读代码、跑只读命令来核实。
- **opencode 协作方**（`type` 为 `opencode cli`）：通过本机的 opencode CLI 调用模型。脚本只给它读文件、搜索和列目录的工具，它能自己翻项目里的代码，但不能运行命令，也不能改文件。只能读项目目录里的文件，项目外的材料要摘进议题。它每读一次文件都多一次请求，比 API 协作方费额度；订阅额度紧的高档模型放在 3 级用。结果里的 `cost_usd` 是这一轮按厂商价格折算的费用（OpenCode Go 的额度就按这个扣），汇报用量时一起写上。
- **pi 协作方**（`type` 为 `pi cli`）：通过本机的 pi CLI 调用模型，和 opencode 协作方一样只有读文件、搜索和列目录的工具，读的路径限定在项目目录里（pi 本身没有权限系统，由 foreman 注入的守卫扩展检查）。结果里的 `cost_usd` 是 pi 按厂商价格算出的费用。pi 读用户自己的 pi 配置和登录信息，但不加载用户装的扩展、skill 和 MCP。
- **API 协作方**（`type` 为 `api`，比如 DeepSeek）：只看得到议题和附带的材料，自己翻不了代码。用 `--file "<路径>"` 把相关文件附上（可以给多次，`--file "<路径>:<起始行>-<结束行>"` 只附一段），议题里提到的代码、要讨论的核心模块都要附。材料总量有上限（约 30 万字符），超了脚本会报错，这时精选文件或改用行范围；脚本还会自动附上项目文件清单。附带的材料会发给对应厂商，偏好文件或项目配置不让发的项目，不加 API 协作方。它在 `open_questions` 里要求看的文件，下一轮用 `--file` 补上。
- 给 Codex、opencode 和 pi 协作方传 `--file` 时，脚本只把路径列成"重点文件"，不附内容，它们会自己去读。
- 所有参与方对代码的说法，Claude 都要对照原文核实后才能采信。

### 流程（轮数上限见配置 `dispatch.discuss_max_rounds`，默认 2）
1. **第 1 轮，独立出方案**：议题说明只写背景、要解决的问题、约束、已知事实、相关代码位置，以及要回答的具体问题，**不写 Claude 自己的倾向**，以免参与方顺着说。在读任何参与方的结果之前，Claude 先把自己的方案写进一个文件（scratchpad 目录或系统临时目录），以免反过来被带偏。然后按 `resolved_levels.discuss.<等级>`，给每个参与方各发一次 `discuss`：同一份议题（角色模式下是相同的公共主干，各自末尾带一张角色卡）、同一个 `--group`（英文短标题加日期，比如 `config-rework-1013`；同一个对话里每场讨论用不同的组名，后续轮次沿用），每次用 `--agent <名字>` 指定参与方，放在同一条消息里一起在后台启动。这一级只有一个参与方时可以不写 `--agent` 和 `--group`。
2. **第 2 轮，交叉挑错**：各方方案（包括 Claude 的）有实质分歧，或者某一方的结论里有 Claude 还没核实、又会影响结论的地方时才做；基本一致时直接裁决（角色模式的触发条件见 `references/roles.md`）。把各方方案匿名成"方案 A / 方案 B / …"，用 `resume --run <这一方第 1 轮的 run_id>` 分别续接每个参与方（同样放在同一条消息里并行），要求它找出其他方案最薄弱的地方，并和自己的方案对比。只发方案摘要和分歧点，不发完整报告。同时 Claude 也写出对各方方案的质疑。
3. **第 3 轮及以后（可选）**：只有关键分歧还没解决、多一轮确实可能改变结论，并且没有超过轮数上限时才做。脚本拒绝续接时，就按已有结果裁决。
4. **Claude 裁决**：逐条决定接受还是拒绝各参与方的观点，写明理由，形成最终方案。按证据、约束和可逆性判断，几方一致的结论也可能一起错。

- **1 级（一次性问答）从简**：不用先写自己的方案，不做第 2 轮，也不写决策记录；核实参与方的回答后，用人话直接告诉用户结论和依据。附带文件、实时查看和繁忙处理照常。
- 续接下一轮时沿用第 1 轮的等级。每个参与方单独一个 run_id，轮数上限对每个参与方各自生效。每个参与方各占自己协作方的一个并发名额；某一方因为达到并发上限被拒绝时，等它正在运行的任务结束后再补发这一方，不要跳过。
- 某个参与方失败（比如余额不足 `quota_exhausted`、接口报错、key 没设置、被用户终止 `cancelled`）不影响其他参与方：告诉用户哪一方失败、原因是什么，用其余参与方的结果继续。不要为了凑齐参与方去改配置。
- 讨论是只读的：Codex 可以读代码、跑只读命令来支撑观点，但不能改文件。`warnings` 里报出 Codex 改了文件时，检查 diff，还原 Codex 改的部分。`notes` 里归属未知的改动不要还原，多半是别人改的。API、opencode 和 pi 协作方改不了文件。
- 讨论同样要处理实时查看（见"三、执行"里的"实时查看"）。

### API 参与方繁忙时
API 协作方的服务繁忙时，请求会在服务端排队，迟迟不开始处理，最后可能被服务端断开。别让用户干等：
- 发起（或续接）的讨论里有 API 参与方，并且 `effective.dispatch.busy_ask_min` 大于 0 时，紧接着在后台再启动一次 `await-busy --group <组名>`（这一级只有一个参与方、没用组时用 `--run <run_id>`）。它不发请求，只在有参与方排队超过 `busy_ask_min` 分钟、或者全部结束时退出，退出时会通知你。脚本启动时输出的"排队检查"一行给出了完整命令。
- 它退出后读输出：`busy` 为空就不用管。不为空时由 Claude 直接决定，不问用户：
  - 其他参与方已经有可用的结果，或者这一方已经排队超过 10 分钟：运行 `cancel --run <run_id>` 终止它，用其他参与方的结果继续。这一方的结果标为 `cancelled`，裁决时说明少了它。
  - 否则再等 5 分钟：后台再启动 `await-busy --run <run_id> --after <已排队分钟数 + 5>`，到时还在排队就终止。
  - 事后用一句话告诉用户终止了哪一方、为什么。
- 用户也可以在实时查看里对排队中的模型按 x 终止，效果和 `cancel` 一样。收到 `cancelled` 的结果时照常继续。

### 向用户汇报：决策记录
不贴原始对话，用人话整理成下面的格式（1 级的问答不用）：
- **议题**：一句话
- **候选方案**：Claude 的和每个参与方的，各自的核心思路和取舍
- **各参与方的主要观点**：按参与方分开列，用模型名称呼（比如 gpt-6-astra、deepseek-v4-pro），每条注明 ✅ 接受 / ❌ 拒绝 / ⚠ 部分接受，并写明理由
- **最终方案**：以及和 Claude 最初方案相比改了什么
- **待确认**：需要用户拍板或先验证的事
- 附上每个参与方的 run_id、模型、推理强度和 token 消耗，方便用户回看原始记录
- 角色模式另加分配表、角色卡和缺席的视角，观点写成"模型［角色］"，见 `references/roles.md`

### 讨论之后
- 用户只是来要建议的：停在决策记录，由用户决定做不做。
- 用户要把事情做成的：最终方案里没有要用户拍板的事项，就按最终方案进入"二、分工"和"三、执行"；有业务取舍、偏好、风险承受度、扩大范围、要额外花钱或不可逆的事项，先交给用户决定，不要替用户拍板。
- 讨论的是已做出的改动的效果：结论是在原定目标内改做法的，用 `resume` 续接原执行方返工（按"返工与失败"计次）；方向或目标变了的，当作新任务重新定级；效果已经达标的，按"五、审查"定级。

## 二、分工
一项要动手的工作由谁做，按下面的顺序判断：
1. **只由 Claude 做的工作**：核心决策和整体规划（做什么、架构怎么定）、创意设计（界面和视觉、文案、找灵感），以及下面"文字类工作由 Claude 把关"里列出的文字工作。外部模型的设计和前端效果差，文字表达也弱，这些工作不分等级，都不派。
   - **画插画不在这一条里**：角色、吉祥物、场景、插画风图标这类要画出来的图形内容，即使最后交付的是 SVG、HTML、canvas 或动画，也照第 2 条交给能出图的协作方画，再用进作品。例外是本身要弯、转动时接缝会露出来、要和代码画的东西精确接触的部件，这类由 Claude 画成 SVG（见"图片生成"的"按部件分"）。Claude 定风格、写代码（布局、动画、交互）。
   - **前端的边界**：布局、配色、字体、间距、动效、交互手感这类视觉和体验上的决定，以及要反复看效果来调的页面工作，由 Claude 做；按 Claude 定好的设计或现有组件模式实现的逻辑部分（状态管理、数据请求、表单校验、接口对接、测试），按执行定级。
   - **混合的任务**：一项工作里既有只由 Claude 做的部分（设计决定、文案、命名），又有能派的部分时，先由 Claude 把前者定下来、写进任务说明，再把其余部分按执行定级。
2. **只由能出图的协作方做的工作**：需要模型画或重画的图形内容，比如照片、插画、贴图、精灵图、封面和主视觉、角色和场景、要切成单个素材或转成 SVG 的素材（包括 SVG、HTML、canvas 作品和动画里整块使用的插画）、给现有图片去背景、修改现有图片。只有 `capabilities.images` 为 `true` 的协作方能出图（目前是 `codex cli` 类型），所以这类工作不看等级配置给了谁，一律加 `--agent <它的代号>` 派出（`dispatch.auto` 为 `false` 时先问）。配置里没有这样的协作方时，告诉用户这次做不了，不要改用别的办法凑。画什么仍由 Claude 定；出图之后的去背景、切部件、矢量化这类确定性处理由 Claude 用 `assets` 子命令做，不派出去。做法见下面"图片生成"。
3. **其余执行类工作**：按"三、执行"的定级标准定 0–3 级。0 级 Claude 自己做；1–3 级看 `resolved_levels.run.<等级>`：写的是 `"claude code"` 就由 Claude 自己做（脚本也会拒绝派出这一级），写的是协作方就派出。用户明确要求派出去时（比如用 `/foreman:run` 点名），不做 0 级判断，即使这一级是 `"claude code"` 也照派：加 `--agent <协作方代号>`，选 `capabilities.modes` 里有 `run` 的；推理强度用内置默认值，想换模型再加 `--model`。

### 文字类工作由 Claude 把关
外部模型的文字表达弱，经常不说人话：术语堆砌、翻译腔、绕来绕去，读的人看不懂。凡是给人读的文字，都由 Claude 负责：
- **Claude 自己写，不派**：README、使用说明、设计文档、报告和总结、用户可见的界面文案。这类工作以文字为主，派出去再返工反而更费事。
- **派活前在任务说明里规定好**（写进"命名与文字"一节）：
  - 新增的文件、模块、类、函数、关键参数和配置项叫什么名字，直接给出名单；名单之外的沿用项目现有风格。
  - 注释写在哪里、写什么，语言用中文还是英文与项目保持一致。
  - 日志、报错信息、命令行帮助、输出表头这类会给人看的文字，给出原文或模板，要求照抄。
- **验收时复核**：命名是否直白、前后一致；注释和提示文字能否一眼看懂，有没有啰嗦、翻译腔、过度注释。不合格的小地方 Claude 直接改，不必返工；文字问题多的，在返工说明里给出改好的原文。
- **向用户转述**：协作方的报告、审查意见和遗留问题，由 Claude 理解后用人话转述给用户，不要原样转贴。

### 图片生成
要把图拆成部件、转成 SVG、做透明素材、改图或照参考图出图时，先读 `references/image-assets.md`（提示词模板、背景方案、格子模板、先整图还是直接出部件表、局部返工）。
- **范围**：要模型画的图形内容走这里，不论最后交付的是位图，还是 SVG、HTML、canvas 或动画：照片、插画、贴图、精灵图、主视觉、角色和吉祥物、场景、插画风图标、UI 组件的视觉。用在代码作品里时，按下面"按部件分"决定哪些部件出图，出图后用 `assets cut` 切成带名字的素材（转不转 SVG 见"矢量化"），再由 Claude 写进页面或动画。做法见 `references/image-assets.md` 的"用在 SVG、HTML 和动画里"。
- **按部件分：出图的部件当刚体用**：图像模型擅长单独看的画，不擅长和别的东西精确对上。2026 年 10 月实测，关节转轴、和代码画的东西接触、两次出图之间的接缝、分开画的部件统一比例，偏差动辄是部件长度的几成，改提示词、加引导图都压不下来。所以作品里每个看得见的部件单独判断：
  - **出图**：部件在作品里整块动（平移、旋转、缩放、改透明度，或者叠一块局部变体），而且它和别的部件相接的地方，要么被前面的东西盖住（另一个部件、头发、衣服、遮挡物），要么两者相对不动。比如背景和远景层、道具、角色的头、基本不动的躯干。
  - **Claude 画成 SVG**：部件本身要弯（弯曲的四肢、尾巴、布料），转动时接缝会露出来，或者要和代码画的东西精确接触（手握物体、脚踩踏板）。
  - **代码画**：作品要求按物理逐帧模拟形状的（模拟的头发和布料、程序生成的绳子）、要和机械对齐的（链条、齿轮、按计算转动的曲柄）、文字、按钮和输入框这类 UI 控件、几何线性图标、图表和流程图。
  - 用户明确要求手写 SVG 或纯代码时不出图。用户明确要逐帧精灵动画（不和其他东西接触的循环动作）时可以试，先说明这是实验性做法。
- **接缝放在参考图里本来就被盖住的地方**：跟着动的衣物和配件（袖子、裤脚、手套）归会动的那个部件。不要让模型从出图部件里删掉一个插在里面或挡在前面的部件（比如从袖子里删掉手臂）：它会把本来看不见的开口、内沿和断面画出来，接缝的位置和形状也会变。也不要让模型删掉一个部件再把边收好（比如去掉手臂后把肩收成圆肩），实测两次都没照做。接缝放在参考图里已有的遮挡物边上（衣服的带子、领口、袖口、柜台），接缝旁边露出来的一小段由手画部分照参考图描出来盖住。
- **先出整体参考图，统一画风**：作品里既有出图部件、又有手画或代码画的部件时，先出一张整体参考图（整个角色或整幅画面，最终的构图、配色和画风），验收后，出图部件都以它为参考图出，手画和代码画的部分照它的配色、线宽和阴影层次画。从参考图取出的部件常被放大、挪位，用 `assets align` 对回参考图，再看接缝处的区域色差：接缝和参考图对不上就重出。装好后按实际尺寸看一次：出图部件明显比手画部分精细时，先减出图部件的细节（重出时写得更简化，或者减色转 SVG），还不协调就告诉用户。
- **手画部分照参考图描**：以参考图里这个部件的轮廓和阴影形状为底稿描下来，再让它动；只取颜色，画出来会比出图部分平。
- **局部变体只叠补丁**：眨眼、张嘴这类局部变化，从原部件改图出变体，只取改动的区域（边缘羽化）叠在原部件上，不整张换图。改图会让全图轮廓有 1 像素级的位移，整张来回切换时会闪。
- **动手前告诉用户**：用一两句话说明哪些部件出图、哪些手画或代码画、为什么，以及手画的部分会比出图的朴素一些。
- **分工**：画什么由 Claude 定：主体、风格、用途、画幅、部件清单和名字、色板、参考图；图上要有文字的，给出原文、要求照抄。Codex 只出图。去背景、切部件、命名、减色、矢量化和检查由 Claude 在本机跑 `assets` 子命令（见"附：调用方式"），不派出去，也不让 Codex 做。不许用脚本冒充模型出图，但可以用脚本处理模型出的图。
- **等级**：出图质量取决于图像模型，和推理强度关系不大，一般用 `simple`。同一个任务还要改代码（比如把图接进页面）时，按代码部分定等级。
- **任务说明**：
  - 写明调用方式。全新出图：`tools.image_gen__imagegen({prompt, transparent_background})`。改图、照参考图出图、拆图、分层：再加 `referenced_image_paths: ["<绝对路径>", …]`，提示词里用 "Image 1"、"Image 2" 按顺序指代。不传这个参数，工具会当成全新出图，参考图不起作用（Codex 先用 view_image 看过也一样）。`num_last_images_to_include` 只在参考图没有本地文件时用，两个参数不能同时传。参考图会上传给模型服务，敏感或未授权的图不要用。
  - 不写像素尺寸：工具没有尺寸参数，只出约 157 万像素的几档。只写画幅（1:1、3:2、2:3、3:1）；要别的尺寸，用 SVG 或者交付时另行缩放。
  - 要透明背景的素材写 `transparent_background: true`，背景、间距、风格和禁止项照模板写。
  - 两个以上部件：用 `assets template` 在项目里生成编号格子图，作为 Image 1 传入，提示词写"第 N 格放 X，不要画格子和数字"，切图时按格子命名。不按排列顺序命名：模型会打乱顺序。
  - 写明每张图保存到项目里的路径，原图照原样复制，不转换、不压缩。用户没要求变体时，每张源图只出一次。
- **验收**：
  1. 结果里的 `generated_images` 列出这一轮新出现的图片原文件，`image_calls` 列出每次出图实际传的参数（从 Codex 的会话记录里读出）。该传参考图的步骤在 `image_calls` 里没有 `referenced_image_paths`，说明参考图没起作用，要返工（`warnings` 会提示）。两个字段都没有时，出图来源未经验证，先查记录目录和输出再下结论。
  2. 要切图或矢量化的素材跑 `assets cut`：结果的 `checks` 里有 `fail` 的直接返工；`needs_review` 的项由 Claude 看图判断。
  3. 用 Read 看图（切过的看 `sheet.png` 对照拼图）：每一格是不是那个部件，细节、风格和配色对不对，图上的文字是否照抄。
- **返工**：出图不设固定次数，不合格就重出，每次重出都要改点什么（提示词、参考图、取法），不原样重试。接缝处的位置或形状和参考图对不上也算不合格：重出，不挪手画部分去迁就，也不用遮罩、裁剪去改出图部件的轮廓。同一个问题连续三次重出都没有改善时停下，把问题、试过的做法、已经出了几次图和可选的做法交给用户决定；用户给了出图次数上限时按用户的。出图不套用"返工与失败"里由 Claude 接手的规则，Claude 不能出位图。局部返工把原图作为参考图传入，提示词写"只改 X，其余不变"；交付时只替换被改的那个部件，其余部件沿用上一版的文件。
- **矢量化**：只有扁平、颜色少的素材（图标、道具、扁平插画）转 SVG。角色、带渐变或细节多的画转出来又大又有色带（实测一个动漫头像 384 条路径、170 KB），默认保留 PNG，用 `<image>` 嵌进 SVG 或页面，交付时告诉用户这部分不是纯路径。`assets cut --vector` 依赖两个原生包。没装时先问用户是否同意安装，同意后运行 `assets setup`（装到用户目录下的 `~/.claude/foreman/tooling`，不进插件目录和用户项目）；不同意就只交付 PNG 部件和 manifest，并说明没有矢量化。
- 出一张图要几十秒，这段时间实时查看停在上一步是正常的；图生成后时间线上会出现一行"生成图片 …"。

## 三、执行（/foreman:run）

### 定级
**等级看需要多少判断、出错的代价有多大，不看改动多少**：同样改 20 个文件，照清单机械地改名是 `simple`，改模块之间的接口是 `complex`；只改几行、但根因不明的 bug 也是 `complex`。

| 等级 | 判断标准 | 例子 |
|---|---|---|
| 0 级 | 一处就能改完、不用设计，写任务说明加验收比 Claude 自己改还费事 | 改错字、改一行配置、在一个文件里改名、补一个漏掉的 import；验收和返工里的小修小补 |
| 1 级 `simple` | 做法已经确定，几乎不需要判断，结果能逐项核对 | 做法明确的小功能或小脚本、改法已经明确的小修、照现成模式补齐同类代码、按清单批量改名或替换、格式或目录迁移、跑现成脚本整理数据 |
| 2 级 `normal` | 有规格或原因已经清楚，但具体做法和局部细节要自己设计，出错了测试或实际运行容易发现 | 按规格实现功能、写脚本和工具、原因已经清楚但改法要设计的 bug 修复、常规重构、补测试 |
| 3 级 `complex` | 满足任意一条：根因不明、需要排查；出错了测试不容易发现，后果又重；要改模块之间的接口或约定；性能、并发这类需要反复权衡和验证的 | 根因不明的 bug、金额和计费计算、数据迁移、权限判断、跨模块的接口改动、性能优化、并发 |

- **0 级要从严**：不要因为嫌派活麻烦，把 1 级的活算成 0 级。用户把 `simple` 配给协作方，就是希望小活也派出去。拿不准时按 1 级。
- 用户点名要某个推理强度或模型时的写法，见文末"调用方式"。

### 写任务说明
说得越细，协作方做得越好。按下面的结构写：

```markdown
# 目标
要做成什么，为什么做（一两句背景）。

# 范围
- 允许改动：具体文件或目录
- 只读参考：相关文件
- 不要碰：……

# 规模
预计改动多少行、几个文件；这次不需要的东西，比如命令行参数、配置项、兼容旧数据、测试。

# 要求与约束
接口签名、数据格式、要沿用的现有模式和工具函数、性能要求、兼容性等。

# 允许的适配
协作方遇到这些情况可以直接处理，不用停下来问。比如：
- 指定的测试入口跑不起来时，可以改用覆盖同一批测试的等效入口
- 允许修正某个测试夹具，但不得削弱断言
（没有就写"无"）

# 命名与文字
- 命名：新增的文件、类、函数、关键参数和配置项叫什么名字
- 注释：哪里需要写，写什么
- 提示文字：日志、报错、帮助信息、输出表头的原文或模板（要求照抄）
（任务不涉及这些时可以省略本节）

# 禁止事项
本任务特有的禁区。

# 完成标准
怎样才算做完，需要跑哪些命令验证（给出具体命令）。

# 交付
需要在报告里特别说明的内容。
```

协作方偏爱做全做重：简单任务也会加参数、配置项、抽象层、兼容分支和大量测试。"规模"一节就是用来防这个的：写明预计的规模和这次不需要的东西，验收时也拿它对照。脚本附加的固定约束里也有"按规模做、只写必要的测试、不要过度防御"，任务特别容易做过头时，在任务说明里再强调一遍。任务说明本身也按规模写，简单任务不要写成长篇。

"允许的适配"按含义授权，不按改动大小：一行改动也可能改变样本外边界、费率或断言。凡是没写进这一节的越界，固定约束都会要求协作方停下来，在报告的 `decision_requests` 里提问。可以预见的环境问题（比如项目里有同名的 `tests` 包），提前写进这一节，能少停一次。

### 并发拆分
协作方任务的等待时间大部分花在模型思考上，跑命令只占一小部分。所以把一个大任务拆给几个会话同时做，能明显缩短等待。代价是总 token 更多（每个会话都要各自读一遍背景），Claude 也要多写几份任务说明、多做几次验收。

**什么时候拆**：下面几条**全部满足**才拆，否则派成一个任务：
1. 能拆成 2 份以上、不超过这个协作方的并发上限（`agents_status.<代号>.max_parallel`，默认 4；其他会话正在运行的同一协作方的任务也占名额），每份**写入的文件互不重叠**，而且**不依赖其他份的产出**。
2. 各份之间的接口（函数签名、数据格式、文件路径），Claude 能在派活前定下来，写进每份任务说明。定不下来就不拆。
3. 每份预计都要 10 分钟以上。太小的任务拆开，固定开销比省下的时间还多。

**不拆**：根因不明、需要排查的 bug；要改共用核心文件的重构；前后衔接的研究阶段；需要整体统一设计的工作；本身就是重计算的任务（同时跑会抢 CPU，这种让协作方写批量脚本并行跑）。适合拆的例子：几个互相独立的脚本或模块；接口定好后，一份写实现、一份补测试；按目录分开的批量修改。

**怎么派**：
- 每份按自己的难度各自定级。某份是 0 级或这一级配置成 `"claude code"` 时，那一份由 Claude 自己做，同样不碰其他份的文件；其余几份照常派出。
- 给同组任务起一个组名（英文短标题加日期，比如 `factor-scripts-1013`；同一个对话里每组用不同的组名，不同对话的组名重复没关系，查看时只算当前对话派出的；只能用英文字母、数字和 `. _ -`，实时查看要把它写进终端命令，脚本会拒绝其他字符），每份都用 `run --group <组名> --scope <允许改动的路径>` 派出，`--scope` 可以给多次。同时派出的几份放在同一条消息里，一起在后台启动。
- 脚本会拒绝两种情况：这个协作方正在运行的任务（不分组、不分会话，全都算）已经达到它的上限；和同组正在运行的任务写入范围重叠。被拒绝时按报错重新划分，或者等前面的任务结束再派。
- 每份任务说明除了通用结构，还要写明：同组的其他任务在做什么、改哪些文件（这些文件不许碰）；共用的接口约定（原文照抄到每一份里）；这一份单独验证的方法。
- 实时查看只开一个标签页：`watch.mjs --group <组名>`，标题写"任务组：<组名>"。
- 告诉用户这次拆成了几份、各做什么，以及每份用的模型和推理强度。
- **验收**：每份先单独验收，不合格的单独返工（resume 沿用原来的组和范围）。全部通过后，Claude 再做一次**整体验证**：把各份合起来跑完整的测试或脚本，因为每份只是单独验证过。汇报时按份列出 run_id 和 token 消耗，再给出合计。

### 研究与分析类任务
研究类任务指结论要靠实验和数据支撑的工作，比如策略和因子研究、数据分析、方案对比实验、性能调查。这类任务的风险不在代码写错，而在结论超出了证据。

把研究派出去时，在通用结构之外，任务说明还要包含下面几项。某一项不适用时，写明不适用和原因，不要直接省略。讨论阶段已经定下的问题和假设，直接写进来，不用重新讨论。
- **问题与假设**：要回答的问题；每条假设和它的判读标准。判读标准事先定好，不能看到结果再改。
- **对照组**：需要哪些对照和基准，各自回答什么问题。
- **稳健性**：怎么检验结论不是某个参数点或某段时间的偶然，比如参数邻域、时间段切分、换起点。
- **混淆因素**：列出可能干扰结论的因素，要求逐项排查或说明为什么不适用。常见的有：资金或规模路径（本金变化、整手限制）、样本曝光（看过结果后再选）、多重检验、幸存者偏差、数据口径变化。
- **统计判断**：怎么判断差异是否显著，比较多组时怎么校正。
- **交付**：每条结论对应的证据（文件、数字、可以复算的方法），以及没能验证的部分。

**结论落地前的证据审查**：研究结论写进长期档案、报告或文档，或者作为定论交给用户之前，不管研究是谁做的，都发起一次 3 级讨论做证据审查（开新会话，不在做研究的那个会话里自审）：议题说明逐条列出结论，每条附上证据的位置和关键数字；要求各参与方逐条判断证据够不够、有没有说过头、有没有没控制住的混淆因素、统计上站不站得住；Claude 按讨论的流程逐条裁决，修正结论后再写入。已经写进档案的结论被推翻时，以追加修订的方式更正，不改原记录。

### 派出
- 任务说明先写成 UTF-8 文件（有 scratchpad 目录就放在那里，否则放在系统临时目录），用 `run` 在后台运行（Bash 的 `run_in_background`），跑完会自动通知；等待期间可以做别的，不要轮询。脚本会自动附加固定约束：不越界、开工前预检、什么情况下停下来提问、只写必要测试、不 commit/push、不碰密钥、按 schema 汇报。
- **在对话里明确告诉用户用的是哪个模型、推理强度多少**，例如"已派出：gpt-6-astra（Codex CLI，effort max），等级 complex"。以脚本启动时输出的第一行（"<模式> 开始｜<模型>（<接入方式>，effort …）｜等级 …｜记录目录 …"）为准，不要凭配置自己推断；模型来自 Codex 配置时照实说明。讨论、审查和续接也一样，多方讨论时逐个写出。最终汇报里再写一次。
- **启动后下一步必须立即处理实时查看**（见下面），测试、小任务和审查也不例外。
- 多个任务可以并行，但文件范围不能重叠。**协作方正在改的文件，Claude 不碰。**
- 允许改动的范围里有被 `.gitignore` 忽略的路径（比如 `tests/`、结果目录）时，用 `--track "<路径>"` 指定（可以给多次），否则改动追踪看不到这些文件。续接时沿用上一轮的 `--track`。
- Codex 的沙箱不是 `read-only` / `workspace-write` 时（比如 `danger-full-access`），`--cwd` **不限制写入范围**，范围只能靠任务说明约束，再靠事后审查 diff 把关。

### 实时查看（每次派出都做）
只要派给了其他模型，也就是用后台方式启动 `run`、`resume`、`discuss` 或 `review` 之后，立即让用户能看到实时进度。`dispatch.watch` 为 `off` 时跳过本节，只告诉用户可以用 `/foreman:watch` 查看。
- **先打开终端面板，再开标签页**（Claude 桌面版）：先调用显示面板的工具（名字带 `show_pane`，和 `run_in_terminal` 一起用一次 ToolSearch 加载），`pane` 填 `terminal`，不填 `tab_id`；等它返回后再用 `run_in_terminal` 开标签页。面板开着时，新开的标签页会自动切到前台，watch 开头几秒的启动动画用户能从头看到；反过来先开标签页再显示面板，两次调用之间常常隔十几秒，面板出来时动画已经放完了。没有显示面板的工具就直接开标签页。
- **用 `run_in_terminal` 打开**：运行 `node <记录目录>/watch.mjs --run <run_id>`，标题写"<模型>：<短标题>"。多方讨论用同一个组，只开一个标签页：`node <记录目录>/watch.mjs --group <组名>`，标题写"讨论：<短标题>"；审查的标题写"<模型>：审查 <范围>"。记录目录默认是 `~/.claude/foreman/runs`，在 Windows 上写成 `C:\Users\<用户名>\.claude\foreman\runs`，以 `config` 的输出为准。这个启动器由脚本自动生成，插件路径含非 ASCII 字符时也能满足 `run_in_terminal` 只接受 ASCII 的要求。`config` 输出里 `watch_launcher_ascii` 为 `false` 时（记录目录路径含中文等非 ASCII 字符），`run_in_terminal` 会拒绝这条命令：改为把命令放在代码块里发给用户，请用户在自己的终端里运行，并转告 `check` 输出里 `watch.fix` 的处理办法。
- run_id 在启动后后台输出的第一行（"记录目录 …/<run_id>"）里。不加 `--run` 时它会跟踪正在运行的任务，但其他会话可能也在跑任务，所以尽量指定。
- 标签页开好后，再调用一次显示面板的工具，`pane` 填 `terminal`、`tab_id` 填刚才的 tab_id，确保面板停在这个标签页上（中途用户切走了面板，或者面板被别的面板挡住时，这一下能切回来）。然后把标签页链接 `[<标题>](#terminal/<tab_id>)` 发给用户。
- **没有 `run_in_terminal` 时**（比如命令行版 Claude Code），把完整的 watch 命令放在 bash 代码块里发给用户，请用户在另一个终端里运行。
- 讨论里有 API 参与方时，同时在后台启动排队检查 `await-busy`（见"API 参与方繁忙时"）。
- 任务结束后 watch 会自动退出，标签页保留，供用户回看，不要关闭它。退出后的标签页不会再显示新任务，所以每次续接（讨论的下一轮、返工）都要按上面的做法新开一个标签页；讨论的下一轮照样用 `--group <组名>`，标题写"讨论：<短标题>（第 N 轮）"。
- 默认是简洁显示。用户要看完整细节时，加 `--verbose`。

### 协作方要人回答时
调度是无人值守的：协作方运行时没有人能回答它。脚本保证它们不会因为等人而卡住：Codex 默认不需要审批；opencode 不开放提问工具和需要确认的权限；pi 没有提问工具，foreman 注入的守卫扩展只放行这次任务需要的工具；以后接入的 CLI 如果在终端打出"(y/n)"之类的提示后没了动静，3 分钟后自动结束，状态为 `needs_input`。

所有提问都收集在结果的 `questions` 里。`needs_decision` 为 `true` 时说明有事要决定；任务已经结束，不是卡住了。

**由 Claude 直接决定，不问用户。** 决定后写进续接说明，用 resume 继续；小的收尾也可以 Claude 自己做掉。
- 技术做法和取舍，只要在用户已有的授权和任务范围内；
- 任务说明自相矛盾或没写清楚的地方：这通常是 Claude 自己写的说明的问题，按本意澄清；
- 缺材料、缺信息：Claude 自己查清楚后补给它。

**交给用户决定**，把问题、选项和 Claude 的推荐一起给用户：业务取舍和偏好、风险承受度、扩大范围或授权、要额外花钱、不可逆的操作。

按 `source` 分别处理：
- `decision_request`：执行报告里交回的问题。`recommendation` 里写了它已经按哪个做了。Claude 同意就不用改，不同意就在续接说明里写明要怎么改。
- `permission_denied`：工具想做的操作被权限挡住了，比如 opencode 想读项目目录外的文件，或者 pi 的操作被 foreman 的守卫挡下。权限是有意设的边界，不要为了放行去改配置；它需要的材料由 Claude 读出来，写进续接说明，或者用 `--file` 附上。
- `final_question`：最终回答是一个问题，不是报告。Claude 回答它，用 resume 续接，并要求按格式交报告。
- `input_prompt`（状态 `needs_input`）：工具在等终端输入。看提示内容：属于上面 Claude 能决定的，用 resume 续接，在说明里写明答复；否则交给用户。
- `asked_mid_run`：运行中提过的问题，没人回答，它已按自己的判断继续了。验收时对照报告看它选的做法，不合适就按返工处理。这类不计入 `needs_decision`。
- `open_question`：讨论报告里的待定问题，按讨论的流程处理。

为了回答问题的续接不算返工次数。

## 四、验收与返工

### 验收（每次必做）
1. 先看 `status` 和 `report.status`：不是 `completed` 就先读 `open_issues`。
2. 读 `run_dir/diff.patch`，并核对 `changes.files`：
   - 有没有改到范围外的文件；`report.files_changed` 和实际改动是否一致。
   - `by` 为 `reported` 的文件，对照 diff 确认确实是这次任务该改的即可。`by` 为 `unknown` 的文件，可能是 Claude 自己、其他会话改的，也可能是协作方用命令写了却没报告。先弄清是谁改的，**不要直接还原**。其中标了 `group_run` 的落在同组另一个任务的写入范围里，多半是那个任务改的，归到它验收。
   - 逻辑对不对，有没有过度防御、多余抽象、冗余测试。
   - **有没有做过头**：实际改动明显超过"规模"一节的预计（比如两倍以上），或者出现了没要求的参数、配置项、抽象层、兼容分支、测试。小处 Claude 直接删减；多的话用 resume 返工，在返工说明里列出要删掉的东西。
   - 命名、注释和提示文字是否符合任务说明，是否说人话（见"文字类工作由 Claude 把关"）。
   - 只追踪工作目录内的改动；如果任务涉及工作目录外的路径，要另外检查。
3. **实际运行验证**：跑构建、测试或脚本本身，不能只看协作方自己说"通过了"。
4. **没有系统沙箱的执行**（结果里 `isolation` 为 `tools`，目前是 opencode 和 pi）要多看几眼：
   - `run_access` 为 `edit` 时，它不能运行命令：测试和脚本一律由 Claude 自己跑，报告里写"已通过"的也不算。
   - `run_access` 为 `shell` 时，它的命令能碰到工作目录以外的地方，改动追踪看不到那里。diff 要逐个文件看；任务涉及外部路径、安装依赖、联网的，要单独核对它实际做了什么（`run_dir` 里的 `opencode.jsonl` 或 `pi.jsonl` 有它跑过的每条命令）。
   - 写文件的工具事件算改动归属的证据（`by: agent`），报告里自称改过的不算。
5. 验收通过（包括返工之后），通常接着按"五、审查"定级；效果还需要和其他模型讨论的，先按"一、讨论"定级。审查是 0 级的，直接向用户汇报。

### 返工与失败
- 不合格时用 `resume` 返工一次，在返工说明里写清楚哪里不对、要怎么改。原因是任务难度估低了的话，返工时把等级升一级（simple → normal → complex）；升上去的那一级在配置里是 `"claude code"` 时不再续接，由 Claude 自己接手。其余情况沿用原来的等级。
- 返工后还不合格，或者协作方超时、报错，由 Claude 自己接手完成，并告诉用户原因。出图除外，见"图片生成"里的"返工"。
- 结果状态为 `stalled`（卡死：超过 `dispatch.stall_min` 分钟没有任何活动，且没有命令在执行，脚本已自动终止；分钟数以 `config` 输出为准）时，多半是网络或服务的临时问题。用 `resume` 让它从断点继续一次；再卡死就由 Claude 接手。可以用 `--stall <分钟>` 调整阈值，`--stall 0` 关闭检测。总超时是 `dispatch.timeout_min`，用 `--timeout` 调整。
- 怀疑任务卡住时，先运行 `status` 看"最后活动 X 分钟前"和当前步骤，不要凭感觉判断。正在执行命令（比如跑大计算）时，长时间没有新事件是正常的。`interrupted` 表示调度进程已经不在了（比如会话或应用被关闭），这时 Claude 收不到完成通知，需要手动查看 `status --run <run_id>`，再决定是续接还是重来。
- `needs_decision` 为 `true`（包括 `report.status` 为 `blocked`、状态为 `needs_input`）时，按"协作方要人回答时"处理。
- 结果状态为 `quota_exhausted` 时，是额度用完了：Codex 是订阅额度，API 协作方是账户余额不足。不要重试，也不要自动改由 Claude 重做；告诉用户额度用完和预计恢复时间（`quota_resets_at`），由用户决定是等额度恢复后用 resume 继续，还是改由 Claude 接手。
- Claude 接手或用户决定放弃的任务，状态是 `interrupted`、`stalled`、`timeout`、`quota_exhausted` 或 `needs_input` 时，运行 `cancel --run <run_id>` 标记为已处理：会话开始时的提醒只列还没处理的执行任务。
- 会话开始时的提醒如果列出了执行没有正常结束的任务，在合适的时候告诉用户一句，按用户的意思处理。

## 五、审查（/foreman:review）
交付改动之前，不论改动是协作方做的还是 Claude 自己做的，在验收通过后按被审改动的风险定级：

| 等级 | 标准 |
|---|---|
| 0 级 | 小改动、文档、注释、样式、文案、纯配置；已经实际运行验证过的一次性脚本或原型；低风险、有测试覆盖的改动。Claude 的验收就够了，不请外部审查 |
| 1 级 `simple` | 改动量大但很机械，比如批量改名和替换、目录迁移 |
| 2 级 `normal` | 改动较大（约 300 行或 5 个文件以上）的一般功能和修复；Claude 自己做的 3 级执行任务（包括配置里那一级交给 Claude 的情况） |
| 3 级 `complex` | 高风险代码：金额和计费、数据删除和迁移、并发、鉴权和安全、不可逆操作；根因不明的修复 |

- 同时符合几级时取最高的。1 级以上由 Claude 主动发起（`dispatch.auto` 为 `false` 时先问，见"授权"）。
- 用户用 `/foreman:review` 或明确要求审查时直接审，不做 0 级判断，等级按上表从 1–3 级里选。
- `resolved_levels.review.<等级>` 是 `"claude code"` 时，这一级不找外部模型，Claude 自己再仔细审一遍，发现的问题同样按"审查之后"处理。
- 研究结论落地前的证据审查用讨论来做，见"研究与分析类任务"。

### 怎么审
- 协作方交付的改动用 `review` 发起一个**新会话**审查，不在执行的那个会话里自审。
- 审查方和执行方是同一个模型时（比如执行和审查都配给了同一个模型），照常审，不要换成别的协作方；汇报时注明"同一个模型、新会话审的"。
- 发起审查时总是用 `--brief` 附上审查说明（改动意图、风险点、审查重点）。Codex 不带说明时会走它的原生审查，输出是英文，也不受审查要求约束；opencode 和 pi 总是拿插件算好的补丁审。
- 审查范围由脚本先用 git 算好，和 Codex 原生审查的含义一致；没有任何改动时脚本直接报错，不会派出去：
  - `--uncommitted`（默认）：已暂存、未暂存的改动，加上未跟踪的新文件；
  - `--base <分支>`：从和那个分支的分叉点到当前工作区，包括已提交和未提交的改动，不含未跟踪文件；
  - `--commit <sha>`：那次提交引入的改动。
- 完整补丁保存在记录目录的 `review.patch`。结果里的 `review_scope` 写明范围、文件数和指纹；审查期间改动又变了，`warnings` 里会提示，这份审查可能没覆盖最新的改动。
- Codex 自己读改动。opencode 和 pi 拿到的是脚本算好的补丁，外加只读工具查上下文，不能跑命令。补丁太大（约 20 万字符）时，opencode 和 pi 审查会被拒绝：按提交分开审（`--commit`），或者改用 Codex 审查。

### 审查之后
1. **逐条核实**：审查意见在结果的 `last_message` 里（审查没有结构化的 `report`）。审查方指出的问题，确实存在的才算；误报直接忽略，在汇报里简要说明为什么不成立。
2. **谁来修**：
   - Claude 主动发起的审查：小问题 Claude 直接改；问题多或涉及逻辑的，把核实后的问题写进返工说明，用 `resume` 续接原来的执行方去改，算一次返工（次数按"返工与失败"）。改动本来就是 Claude 做的，由 Claude 改。
   - 用户用 `/foreman:review` 发起的审查：用户只要了审查，先把核实后的问题和打算怎么修告诉用户，用户同意（或已经说过要修）再修。
3. **修完重新验证**：重新跑构建、测试或脚本。修复改了核心逻辑、而改动又属于 3 级的，再审一次（同样开新会话），最多再审一次；其余不再复审。

## 六、向用户汇报
- 哪些部分是协作方做的：附 run_id，以及每次调用的协作方、模型和推理强度（以结果里的 `agent`、`model_shown` 和 `effort` 为准）。
- 每次调用的用量：本次的输入和缓存比例、输出（`usage_scope` 为 `session_total` 时注明是会话累计）；opencode 和 pi 写上 `cost_usd`。
- 各阶段定的级，0 级的写明是 Claude 自己处理的；有讨论的附上决策记录。
- Claude 验收了什么、怎么验证的；有没有请人审查、结果怎样（审查方和执行方是同一个模型时注明）。
- 遗留问题。
- 协作方的报告、审查意见由 Claude 转述成人话，不要原样转贴。

## 附：调用方式
唯一入口是本 skill 目录下的 `scripts/cli.mjs`（即 `${CLAUDE_PLUGIN_ROOT}/skills/dispatch/scripts/cli.mjs`）。

- **没有例外**：测试、验收、试跑、一次性问答，也都必须走这个脚本，只读的问答用 `discuss`。插件带有钩子，直接调用 `codex exec`、`codex review`、`opencode run` 或用 pi 跑任务的命令会被拦下。
- **遇到沙箱问题时停下来**：Codex 因为沙箱无法启动命令或报错时（结果的 `notes` 会提示"Codex 的沙箱启动不了命令"，常见原文是 `windows sandbox failed`、`setup refresh had errors`），不要重试，也不要自己换沙箱、改配置文件、想办法绕开脚本。先运行 `check`，它会不调模型地测一遍沙箱，`fix` 里列出可选的修法；把错误原文、你的判断和这些选项告诉用户，由用户决定。不要建议改 `approval`：派出去的任务没人能批准，`never` 是对的，问题在沙箱。

```bash
node "<脚本路径>" run    --cwd "<项目目录>" --brief "<任务说明.md>" --title "<短标题>" --level <simple|normal|complex> [--add-dir "<目录>"] [--track "<路径>"] [--group <组名> --scope "<路径>"] [--timeout 分钟]
node "<脚本路径>" resume --run <run_id|last> --brief "<返工说明.md>" --level <simple|normal|complex> [--track "<路径>"] [--file "<路径>[:起始行-结束行]"]
node "<脚本路径>" discuss --cwd "<项目目录>" --brief "<议题.md>" --title "<短标题>" --level <simple|normal|complex> [--agent <协作方>] [--file "<路径>[:起始行-结束行]"] [--group <组名>]
node "<脚本路径>" review --cwd "<项目目录>" [--uncommitted | --base <分支> | --commit <sha>] [--brief "<审查重点.md>"] --level <simple|normal|complex>
node "<脚本路径>" status [--run <run_id|last> | --group <组名>] [--limit n]
node "<脚本路径>" watch  [--run <run_id|last> | --group <组名>]
node "<脚本路径>" config [--cwd "<项目目录>"]
node "<脚本路径>" check  [--agent <协作方>]
node "<脚本路径>" models
node "<脚本路径>" await-busy (--group <组名> | --run <run_id>) [--after 分钟]
node "<脚本路径>" cancel --run <run_id>
node "<脚本路径>" assets template --out "<模板.png>" --cols <列> --rows <行> [--aspect 1:1|3:2|2:3|3:1] [--names "<名字1,名字2,…>"]
node "<脚本路径>" assets cut --image "<图.png>" --out "<输出目录>" [--slots "<模板.slots.json>"] [--names "<名字1,…>"] [--matte hard|soft] [--key auto|#rrggbb] [--palette "#rrggbb,…" [--snap]] [--colors <N>] [--vector]
node "<脚本路径>" assets check --dir "<输出目录>"
node "<脚本路径>" assets diff --before "<原图.png>" --after "<新图.png>" [--slots "<模板.slots.json>"]
node "<脚本路径>" assets align --ref "<参考图.png>" --image "<部件.png>" --out "<输出目录>" [--regions "<x0,y0,x1,y1;…>"]
node "<脚本路径>" assets setup
```

- `--agent <协作方>` 指定这次交给配置 `agents` 里的哪一方。不写时用这一级配置的那一方；讨论的某一级有多个参与方时必须写。每个协作方能做哪些任务看 `capabilities.modes`：`api` 协作方只能参加 `discuss`；`opencode cli` 和 `pi cli` 能做 `review` 和 `discuss`，配置里写了 `run_access` 的还能做 `run`。升级前的旧代号（比如 `codex`）照样认，脚本会提示新代号。
- 用户点名要某个推理强度（比如"用 ultra 跑"）时，改用 `--effort <强度>` 直接指定，不再按等级换算，模型用这个协作方在 `agents` 里的默认模型。不写 `--agent` 时用这一级配置的协作方；这一级是 `"claude code"` 或者没给等级时，能做这种任务的协作方只有一个就用它，有多个就必须写 `--agent`。`--effort` 也可以和 `--level` 一起给：交给这一级配置的协作方，推理强度换成指定的。
- 用户点名要某个模型时，加 `--model <模型>`，它覆盖配置里的模型，可以和 `--level` 或 `--effort` 一起用。
- 续接时模型按新给的等级重新确定，所以返工升级时可能换成另一个模型；配置里哪里都没写模型时，沿用上一轮的模型。
- 交给谁、模型、推理强度、沙箱、审批、超时由配置文件决定；Codex 没有配置的项沿用它自己的 `~/.codex/config.toml`。拿不准当前设置时先运行 `config --cwd "<项目目录>"`。
- `check` 检查环境（Node.js、Git、每个协作方能不能用、推理强度、Codex 沙箱），`models` 列出各工具自带的模型清单。派活或讨论因为环境问题失败（找不到命令、没登录、API 报 401 等）时，先跑 `check` 确认原因，把结果里的 `fix` 转告用户。两者的细节、`summary` 总表的转告方式，以及结果 JSON 的各个字段，见 `references/cli.md`。
- `assets` 是出图之后的确定性处理，不调用任何模型：`template` 画编号格子模板，`cut` 去背景、切部件、命名、出 manifest 和对照拼图（加 `--vector` 再转 SVG），`check` 重新判定已切好的结果，`diff` 比较改图前后每一格的变化，`align` 把从参考图取出的部件对回参考图（缩放、偏移、整体和各区域的色差、同画布的对齐图和对照图），`setup` 安装矢量化用的原生包（先问用户）。参数和输出见 `references/image-assets.md`。

## 附：配置
用户配置是 `~/.claude/foreman/config.json`，项目配置是 `<项目目录>/.claude/foreman.json`，后者只能收紧前者。各字段的含义和默认值见 `references/config.md`，用户问到或要改配置时再读。
- 脚本输出"首次使用，已生成配置文件"时，转告用户检测到了什么（Codex、opencode、pi、API key）、现在各类任务交给谁，并建议运行 `/foreman:setup` 选择要用的模型。
- 脚本输出"已把配置文件 … 改成新写法"时，告诉用户：配置换成了新写法（`type` 改为 `codex cli` / `opencode cli` / `api`，`"claude"` 改为 `"claude code"`），协作方代号改成了模型名（转告脚本列出的对照），实际用的模型和推理强度都没变，原文件备份在哪里。
- **Windows 上不要把 Codex 的 `sandbox` 设成 `read-only`**：Codex 的 Windows 沙箱在只读模式下可能连读文件的命令都启动不了。讨论和审查的只读要求靠脚本附加的规则约束，脚本事后也会检查有没有文件被改动。
- 用户要改配置时，直接编辑对应的 JSON 文件，改完运行 `config` 确认生效。
